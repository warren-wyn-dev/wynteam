## 1. สถานะปัจจุบัน (ตรวจโค้ด)

- `web/components/food/wynos-food-developer-app.tsx`
  - ฟอร์มที่อยู่จัดส่งบังคับให้ปักหมุดก่อนบันทึก (`กรุณาปักหมุดโลเคชั่นก่อนบันท…`, `DeliveryPinPicker`, ~บรรทัด 2336–2540)
  - พิกัด (`form.location`) ใช้ 3 อย่าง: เติมจังหวัด/อำเภอ/รหัสไปรษณีย์อัตโนมัติ, เช็กว่าร้านส่งถึงที่อยู่นี้ไหม (availability), และ quote ค่าส่งตามระยะทาง/พื้นที่บริการ (~บรรทัด 2399–2430, 2626–2690)
  - ที่อยู่ที่ไม่มีพิกัดขึ้น "ที่อยู่นี้ยังไม่ได้ปักหมุดตำแหน่ง" และสั่งซื้อไม่ได้
- `web/components/food/food-delivery-map-picker.tsx` (2,467 บรรทัด) คือแผนที่ปักหมุด ใช้ร่วมกับ Wyn Maps แบบ standalone ด้วย → **ห้ามลบไฟล์ทั้งไฟล์** ต้องแยกการใช้งานฝั่ง ZOKY ออก
- ฝั่งฐานข้อมูล: พื้นที่บริการและ quote ใช้พิกัด (migration `zoky_service_area_thailand`, `zoky_service_area_admin`, `zoky_fulfill_001`) — ต้องตรวจ RPC ว่ารับพิกัดจาก GPS ได้เหมือนพิกัดจากหมุดโดยไม่ต้องแก้ schema
- เทสที่เกี่ยวข้อง: `tests/browser/wynos-food-developer-preview.spec.ts` (3 เทส map pin ที่ล้มอยู่ใน browser-qa เพราะอ่านไฟล์ `maps-v*.css` ที่ถูกรวมแล้ว — ปัญหาแยกจากเรื่องนี้ แต่ต้องปรับตามเมื่อเปลี่ยน flow)

## 2. ข้อเสนอ

ให้ลูกค้ากด **"ใช้ตำแหน่งปัจจุบัน"** ในฟอร์มที่อยู่ แทนการเปิดแผนที่ลากหมุด:

1. ขอสิทธิ์ตำแหน่งจากเบราว์เซอร์ (เมื่อกดปุ่มเท่านั้น ไม่ขอตอนเปิดหน้า)
2. ได้พิกัด GPS → ใช้ค่าเดียวกับที่ `form.location` ใช้ทุกวันนี้ (availability, ค่าส่ง, เติมจังหวัด/อำเภอ) จึง **ไม่เปลี่ยนการคำนวณฝั่ง server**
3. แสดงความแม่นยำ (เช่น "แม่นยำ ~20 ม.") และปุ่ม "ลองอีกครั้ง"
4. ซ่อน/ลบ `DeliveryPinPicker` และข้อความ "ปักหมุด" ทั้งหมดใน flow ที่อยู่ของ ZOKY
5. Wyn Maps และ `FoodDeliveryMapPicker` ไม่ถูกแตะ

## 3. Requirements

### P0
- ปุ่ม "ใช้ตำแหน่งปัจจุบัน" ในฟอร์มที่อยู่ ใช้ geolocation ที่มีอยู่แล้ว (watchPosition + เลือกค่าแม่นที่สุด — มีโค้ดอยู่ใน picker บรรทัด ~419–470 ให้ reuse ไม่เขียนใหม่)
- ปุ่มบันทึกที่อยู่ต้องมีพิกัดจาก GPS ก่อน (คงกติกา "ต้องมีพิกัด" เดิม เพื่อไม่ให้ quote/พื้นที่บริการพัง)
- ข้อความ error ภาษาไทยสำหรับ: ไม่ให้สิทธิ์, GPS ไม่พร้อม, ตำแหน่งไม่แม่น, อยู่นอกพื้นที่บริการ
- ที่อยู่เดิมที่มีพิกัดอยู่แล้ว ใช้ต่อได้ ไม่ต้องบันทึกใหม่
- ข้อความใหม่ทุกอัน มีคำแปลใน `lib/i18n/en.ts` (เทส i18n บังคับ)
- Accessibility: ปุ่มและสถานะอ่านออกโดย screen reader, touch target ≥ 44px

### P1
- ตั้งเกณฑ์ความแม่นยำขั้นต่ำ (เสนอ ≤ 100 ม.) ถ้าเกินให้เตือนแต่ยังให้ใช้ได้
- แก้พิกัดด้วยตนเองไม่ได้ในรอบนี้ (ผลของการเอาหมุดออก)

## 4. ผลกระทบและความเสี่ยง

| ความเสี่ยง | ระดับ | การรับมือ |
|---|---|---|
| ลูกค้าสั่งที่บ้านแต่อยู่ที่อื่น (GPS = ที่ที่ยืนอยู่ ไม่ใช่ที่ส่ง) | สูง | แสดงพิกัดเป็นที่อยู่/จังหวัดให้ยืนยันก่อนบันทึก; ลูกค้าต้องไปยืนที่ปลายทางหรือกดใช้ที่อยู่ที่บันทึกไว้ |
| GPS ในอาคารคลาดเคลื่อน ทำให้ค่าส่ง/พื้นที่ผิด | กลาง | เกณฑ์ความแม่นยำ + เตือน + ลองใหม่ |
| ผู้ใช้ที่ปฏิเสธสิทธิ์ตำแหน่ง สั่งซื้อไม่ได้ | สูง | ข้อความอธิบายวิธีเปิดสิทธิ์ใน iOS/Android; **ต้องให้ Founder ตัดสินว่ามีทางสำรองไหม (เช่นเลือกที่อยู่จากรายการค้นหา)** |
| คนขับ/ร้านเคยดูหมุดบนแผนที่ | กลาง | ตรวจว่าแอปร้าน/คนขับอ่านพิกัดจาก field เดิม — พิกัด GPS เก็บ field เดียวกัน |
| รายได้ลดเพราะ conversion ตก | กลาง | วัดอัตราจบการสั่งซื้อ + ที่อยู่ที่บันทึกสำเร็จ ก่อน/หลัง |

## 6. แผนทดสอบ

- Unit/regression: ฟอร์มบันทึกที่อยู่, quote เมื่อมี/ไม่มีพิกัด, ข้อความ error ทุกกรณี
- Browser (Playwright, mock geolocation): สำเร็จ, ปฏิเสธสิทธิ์, timeout, ความแม่นยำต่ำ, นอกพื้นที่บริการ
- iPhone Safari จริงบน staging (สิทธิ์ตำแหน่งต่างจาก Chrome)
- QA & Security: ไม่ log พิกัดลูกค้า, ไม่ส่งพิกัดไปบุคคลที่สาม, server validate พิกัดเสมอ (ไม่เชื่อ client)

## 7. Rollback

Revert PR; ไม่มี data migration → ที่อยู่ที่บันทึกด้วย GPS ยังใช้ได้กับ flow เดิม (พิกัดอยู่ field เดิม)
