## Feature
ระบบเช็คอินสถานที่ (Location Check-in) ให้ใช้งานได้จริงตอนสร้างโพสต์ — ค้นหา/เลือกสถานที่จริงผ่าน LocationIQ แล้วแนบเข้ากับโพสต์ แสดงชื่อสถานที่บนการ์ดโพสต์

## Goal
ปุ่มปักหมุดสถานที่ (ที่ตอนนี้เป็นแค่ UI เปล่าไม่ทำงาน) ใช้งานได้จริงครบวงจร: ค้นหาสถานที่แบบพิมพ์แล้วขึ้นผลลัพธ์ทันที (autocomplete) หรือใช้ตำแหน่ง GPS ปัจจุบัน → เลือกสถานที่ → แนบเข้าโพสต์ → แสดงชื่อสถานที่บนโพสต์ที่โพสต์ไปแล้ว

## Target User
ผู้ใช้ WYN Social ทุกคนที่ต้องการติดแท็กสถานที่ตอนโพสต์ (ร้านอาหาร, สถานที่ท่องเที่ยว, มหาวิทยาลัย, สถานที่จัดงาน ฯลฯ)

## Problem
Founder ระบุ (ข้อ 3/28): "ปุ่มวงสีแดง คือจุดเช็คอินสถานที่ยังใช้งานไม่ได้" — ปุ่มมีอยู่ใน UI ตอนสร้างโพสต์แต่กดแล้วไม่มีอะไรเกิดขึ้น ไม่มีการเชื่อมต่อ location-data provider ใดๆ เลย

## Requirements

### 1. Data model

ตรวจ `supabase/schema.sql` แล้วพบว่า **`public.drops` มีคอลัมน์ `location text` เตรียมไว้แล้วตั้งแต่ WYN-019** พร้อมคอมเมนต์ในโค้ดระบุชัดว่า "free-text location, not a structured place lookup -- no UI reads or writes this column yet, schema-only prep per the Founder's 'เตรียมโครงสร้างไว้สำหรับอนาคต' request" — งานนี้คือช่วงเวลาที่ "อนาคต" นั้นมาถึงแล้ว ให้ **reuse คอลัมน์ `location` เดิมเป็นชื่อสถานที่ที่ผู้ใช้เห็น** (ไม่ต้อง rename ไม่ต้องเพิ่มคอลัมน์ใหม่ซ้ำซ้อน) และเพิ่มคอลัมน์ใหม่อีก 3 ตัวบน `public.drops` เพื่อเก็บ metadata ที่จำเป็นสำหรับการอ้างอิงกลับไปยัง LocationIQ และพิกัดจริง (เก็บไว้ใน backend เท่านั้น ไม่ใช่สิ่งที่ต้องโชว์ผู้ใช้ — ดูเหตุผลในหัวข้อ Privacy):

| คอลัมน์ใหม่บน `public.drops` | ชนิดข้อมูล | Nullable | ความหมาย |
|---|---|---|---|
| `location` (มีอยู่แล้ว) | `text` | ใช่ | ชื่อสถานที่ที่แสดงผลให้ผู้ใช้เห็น (เช่น "สยามพารากอน") — มาจาก LocationIQ's `display_name`/`address` แบบตัดให้สั้นอ่านง่าย ไม่ใช่ raw string เต็มความยาว |
| `location_lat` | `double precision` | ใช่ | ละติจูด — เก็บไว้เผื่ออนาคต (nearby feed, discovery) แต่ **ไม่แสดงผลตรงๆ ให้ผู้ใช้เห็นในรอบนี้** |
| `location_lon` | `double precision` | ใช่ | ลองจิจูด — เหตุผลเดียวกับด้านบน |
| `location_place_id` | `text` | ใช่ | LocationIQ's `place_id` (หรือ `osm_id`+`osm_type` ตามที่ endpoint ส่งกลับมา) — เก็บไว้สำหรับ debug/dedup ในอนาคต ไม่ใช้แสดงผล |

Constraint ที่ควรมี (ให้ AI Coding ตัดสินใจ syntax ที่เหมาะกับ Postgres):
- `location_lat`/`location_lon` ต้อง null พร้อมกันหรือไม่ null พร้อมกันเท่านั้น (ห้ามมีแค่ตัวเดียว)
- ถ้ามี `location_place_id` ต้องมี `location` (ชื่อ) ด้วยเสมอ — กันเคส metadata ID มีแต่ไม่มีชื่อให้แสดง
- **ไม่บังคับว่ามี `location` แล้วต้องมี lat/lon/place_id** เพราะต้องการเผื่อเคสอนาคตที่อาจให้ผู้ใช้พิมพ์ชื่อสถานที่เองแบบ free-text ล้วนๆ โดยไม่ผ่าน LocationIQ (นอก scope รอบนี้ แต่ไม่อยากให้ constraint ปิดตายเส้นทางนั้นไว้)

ไม่ต้องสร้างตารางใหม่สำหรับตัวเช็คอินเอง (1 โพสต์ = 1 สถานที่เท่านั้นในรอบนี้ ไม่รองรับหลายสถานที่ต่อโพสต์) ไม่ต้องมี index บนคอลัมน์เหล่านี้ในรอบนี้ เพราะไม่มี query แบบ "หาโพสต์ใกล้พิกัดนี้" ในสโคป (ดู Out of Scope)

### 2. LocationIQ integration design

**Endpoint ที่ต้องใช้ (2 ตัว):**
- **Forward geocoding / Autocomplete** (`/v1/autocomplete` หรือ `/v1/search` ตาม LocationIQ's REST API) — สำหรับช่องค้นหาแบบพิมพ์แล้วขึ้นผลลัพธ์ทันที (search-as-you-type) ตอนผู้ใช้กดปุ่มปักหมุด
- **Reverse geocoding** (`/v1/reverse`) — สำหรับปุ่ม "ใช้ตำแหน่งปัจจุบันของฉัน" ที่รับพิกัด GPS จากอุปกรณ์แล้วแปลงกลับเป็นชื่อสถานที่/ที่อยู่ที่อ่านออก

**API key management — ต้องผ่าน Supabase Edge Function เท่านั้น ห้าม hardcode หรือฝัง key ในแอป Flutter โดยเด็ดขาด:**
- โปรเจกต์นี้มี precedent อยู่แล้ว: `supabase/functions/send-push-notification/` เก็บ secret (`FCM_SERVICE_ACCOUNT`) ไว้ฝั่ง server ผ่าน `supabase secrets set` ไม่เคยส่งให้ client เห็น — ให้ทำ Edge Function ใหม่ (เช่น `location-search`) ที่รับ request จากแอป Flutter (ผ่าน `supabase.functions.invoke`, มี JWT ของผู้ใช้แนบมาด้วยอัตโนมัติ) แล้วค่อยยิงต่อไปยัง LocationIQ โดยแนบ `LOCATIONIQ_API_KEY` (secret, เก็บด้วย `supabase secrets set LOCATIONIQ_API_KEY=...`) เอง — ถ้าฝัง key ในแอปโดยตรง ใครก็ decompile แอปแล้วขโมย key ไปใช้ยิง quota ฟรีของ WYN จนหมดได้ทันที ซึ่งเป็นความเสี่ยงที่ยอมรับไม่ได้กับ provider ที่มี quota จำกัดต่อวัน
- **[BLOCKED — ต้องรอ Founder/DevOps]**: ต้องมีคนสมัคร LocationIQ account จริง (ฟรี ไม่ต้องผูกบัตรตามที่ตกลงกัน) แล้วให้ API key มาก่อนถึงจะ implement ให้ทำงานจริงได้ — เหมือน pattern เดิมที่เคยทำกับ Firebase (WYN-016) รอบนี้ควรระบุ "บล็อกด้วย Founder action" ไว้ใน backlog เหมือนเดิม

**Rate limit ของ LocationIQ (free tier) — สมมติฐานที่ใช้วางแผน ต้องเช็คซ้ำกับหน้าราคาจริงตอน implement:**
- ณ เวลาที่เขียนสเปกนี้ LocationIQ free tier โดยทั่วไปให้ประมาณ **5,000 request/วัน และจำกัด ~2 request/วินาที** ต่อ API key (ตัวเลขนี้เป็นค่าที่ Founder เห็นแล้วตอนถามคำถามคืน ไม่ใช่ตัวเลขที่ยืนยันจากหน้าเว็บ LocationIQ ตรงๆ ในเซสชันนี้) — **AI Coding/DevOps ต้องเปิดหน้า pricing/docs ของ LocationIQ จริงตอนเริ่ม implement เพื่อยืนยันตัวเลขล่าสุด** เพราะ provider เปลี่ยนเงื่อนไข free tier ได้ตลอดเวลาโดยไม่แจ้งล่วงหน้า และ 5,000/วันเป็น**โควตารวมของทั้งแอป** (ทุกผู้ใช้ WYN ใช้ key เดียวกันผ่าน Edge Function) ไม่ใช่ต่อผู้ใช้คนเดียว — นี่คือเหตุผลที่ต้องมี rate-limit ฝั่ง WYN เอง (หัวข้อถัดไป) ไม่งั้นผู้ใช้คนเดียวพิมพ์ค้นหาถี่ๆ (search-as-you-type ยิง request ทุกตัวอักษร) ก็ทำให้โควตาทั้งวันของทั้งแอปหมดได้ภายในไม่กี่นาที

### 3. Rate-limiting/abuse prevention ฝั่ง WYN

ต้องป้องกัน 2 ชั้น:

**ชั้นที่ 1 — Debounce ฝั่ง client (UX + ลด request โดยรวม):** ช่องค้นหาต้อง debounce (เช่น ยิง request หลังผู้ใช้หยุดพิมพ์ ~400-500ms ไม่ใช่ยิงทุก keystroke) — ลด request ที่ไม่จำเป็นตั้งแต่ต้นทาง แต่ไม่ใช่มาตรการความปลอดภัยจริง (client ถูก bypass ได้ง่ายถ้ามีคนตั้งใจยิง Edge Function ตรงๆ)

**ชั้นที่ 2 — Rate limit จริงฝั่ง server ใน Edge Function เอง (บังคับ ไม่ optional):** ทุก request เข้า `location-search` Edge Function ต้องเช็คก่อนว่า `auth.uid()` ของผู้เรียก (จาก JWT ที่ Supabase client แนบมาอัตโนมัติ) ยิง request ไปกี่ครั้งในหน้าต่างเวลาล่าสุด ถ้าเกินเพดานให้ตอบ HTTP 429 กลับไปทันทีโดยไม่ยิงต่อไปยัง LocationIQ เลย (กันไม่ให้ quota รวมของแอปถูกผู้ใช้คนเดียวใช้หมด) — ต้องมีตารางเล็กๆ เก็บ log การยิง request เพื่อให้เช็ค rate ข้าม invocation ของ Edge Function ได้ (Edge Function เป็น stateless ไม่มี in-memory counter ที่เชื่อถือได้ข้าม cold start) ออกแบบตาม pattern เดียวกับ `drop_views`/`record_drop_view()` (WYN-038/WYN-083) ที่ทำ rate-limit แบบ "นับจำนวนแถวใน window เวลาล่าสุดก่อน insert":

- ตารางใหม่ `public.location_search_requests(id, user_id, requested_at)` — เก็บ log ทุกครั้งที่มีการยิง request จริงไปยัง LocationIQ (ไม่ใช่ทุกครั้งที่ client เรียก Edge Function เฉยๆ) เปิด RLS แต่ **ไม่มี policy ให้ client ฝั่งไหนเลย** (เข้าถึงได้เฉพาะผ่าน service-role key ที่ Edge Function ใช้เท่านั้น) — มิเรอร์แพทเทิร์นตารางแบบ "audit/internal only, deliberately no policy grants" ที่มีอยู่แล้วในโปรเจกต์ (เช่น moderation audit tables)
- แนะนำเพดาน: **20 request/นาที ต่อผู้ใช้ 1 คน** (ใจกว้างพอสำหรับ search-as-you-type ปกติของคนคนเดียว แต่กันการยิงรัวถี่ผิดปกติ) — ตัวเลขนี้เป็นข้อเสนอเริ่มต้นจาก AI Product Manager ปรับได้ตามพฤติกรรมจริงหลัง Beta ไม่ใช่ตัวเลขศักดิ์สิทธิ์
- เมื่อโดน rate-limit ฝั่ง client แสดงข้อความ "ค้นหาบ่อยเกินไป กรุณารอสักครู่" (ดู Thai UI copy)

### 4. Privacy considerations

- **ข้อมูลเช็คอินสถานที่ต้องเคารพ visibility ของโพสต์เดิมทุกประการ** เพราะเป็นแค่คอลัมน์เพิ่มเติมบนแถวเดียวกันของ `public.drops` (ไม่ใช่ตารางแยก ไม่ใช่ policy แยก) — RLS select policy ที่มีอยู่แล้วบน `drops` (block-aware visibility, `deleted_at`, Draft เป็น private ฯลฯ) ครอบคลุมคอลัมน์ location โดยอัตโนมัติอยู่แล้วไม่ต้องเขียน policy เพิ่ม — **สำคัญสำหรับอนาคต**: เมื่อ WYN-097 (audience selector: ทุกคน/เพื่อน/เพื่อนที่สนิท/ซ่อนเพื่อนบางคน/เฉพาะฉัน) เริ่มพัฒนา ระบบ location นี้จะ "ได้" audience rule ใหม่นั้นมาฟรีๆ โดยอัตโนมัติเช่นกัน เพราะยังเป็นคอลัมน์เดียวกันของแถวเดียวกัน — นี่คือเหตุผลสำคัญที่เลือก reuse คอลัมน์บน `drops` แทนที่จะแยกตารางใหม่ที่ต้องเขียน RLS policy ของตัวเองซ้ำซ้อน (เสี่ยง policy ไม่ตรงกันระหว่างสองตาราง)
- **เก็บชื่อสถานที่ (named place) เป็นสิ่งที่แสดงผลให้ผู้ใช้เห็น ไม่ใช่พิกัด GPS ดิบ (raw lat/long)** — เหตุผล: (ก) พิกัดดิบละเอียดเกินไปสำหรับสิ่งที่ผู้ใช้ตั้งใจสื่อสาร คนกดเช็คอิน "ร้านกาแฟ X" อยากบอกว่า "ฉันอยู่ร้านนี้" ไม่ได้อยากประกาศพิกัดแม่นยำระดับเมตรที่ตามตัวได้ (ข) ชื่อสถานที่จากผลค้นหาของผู้ใช้เองมีความตั้งใจ (ผู้ใช้เลือกเอง) ในขณะที่พิกัด GPS ดิบจากปุ่ม "ใช้ตำแหน่งปัจจุบัน" เป็นข้อมูลที่แม่นยำเกินความจำเป็นและละเอียดอ่อนกว่ามากถ้าหลุดออกไป (ค) เก็บ lat/lon ไว้ backend เฉยๆ (ไม่ auto-expose ผ่าน UI) ยังเปิดทางให้ทำฟีเจอร์อนาคตที่ต้องใช้พิกัดจริง (nearby feed) ได้โดยไม่ต้องขอผู้ใช้เพิ่มพิกัดใหม่ — สรุป: เก็บทั้งคู่ (ชื่อ+พิกัด) แต่**แสดงผลเฉพาะชื่อ**เท่านั้นในรอบนี้
- ปุ่ม "ใช้ตำแหน่งปัจจุบันของฉัน" ต้องขอ permission ผ่าน mechanism มาตรฐานของระบบปฏิบัติการ (iOS/Android location permission) ตามปกติ ไม่มี fallback ที่ข้ามการขอ permission

### 5. UI flow

**ตอนสร้างโพสต์ (แนบสถานที่):**
1. ผู้ใช้กดปุ่มปักหมุดสถานที่ (ปุ่มเดิมที่มีอยู่แล้วในหน้าสร้างโพสต์ — ตอนนี้กดแล้วไม่ทำงาน)
2. เปิด bottom sheet/หน้าจอค้นหาสถานที่ มีสองทางเลือก:
   - **ช่องค้นหาแบบพิมพ์** (search-as-you-type ผ่าน LocationIQ Autocomplete, debounce ~400-500ms) — ขึ้นรายการผลลัพธ์ให้เลือก
   - **ปุ่ม "ใช้ตำแหน่งปัจจุบันของฉัน"** อยู่ด้านบนของรายการผลลัพธ์เสมอ — กดแล้วขอ GPS permission (ถ้ายังไม่เคยอนุญาต) → ได้พิกัด → ยิง Reverse geocoding → แสดงชื่อสถานที่ที่ใกล้ที่สุดเป็นตัวเลือกแรกให้กดยืนยัน (ไม่ auto-select ทันทีโดยไม่ให้ผู้ใช้เห็น เพราะ reverse geocoding อาจได้ผลลัพธ์ที่ไม่ตรงกับที่ผู้ใช้ตั้งใจ)
3. ผู้ใช้แตะเลือกสถานที่จากรายการ → ปิด bottom sheet → กลับไปหน้าสร้างโพสต์ แสดง chip/แถบเล็กๆ ใกล้ช่องแคปชันบอกชื่อสถานที่ที่เลือก พร้อมปุ่ม X เอาออกได้ (เปลี่ยนใจ/ลบทิ้งก่อนโพสต์จริง)
4. กดโพสต์ตามปกติ → `location`/`location_lat`/`location_lon`/`location_place_id` ถูกบันทึกไปพร้อมแถว `drops` เดียวกัน

**ตอนแสดงผลบนโพสต์ที่โพสต์ไปแล้ว:**
- แสดงชื่อสถานที่ (ไอคอนหมุด + ชื่อ เช่น "📍 สยามพารากอน") ใต้ชื่อผู้โพสต์/เหนือแคปชัน บนการ์ดโพสต์และหน้ารายละเอียดโพสต์ ก็ต่อเมื่อโพสต์นั้นมี `location` (โพสต์เก่า/โพสต์ที่ไม่ได้เช็คอินไม่แสดงส่วนนี้เลย)
- **การแตะที่ชื่อสถานที่: นอกสโคปรอบนี้** (ดู Out of Scope) — แสดงผลเป็น text ธรรมดา ไม่ tappable ไม่เปิดแผนที่ ไม่แสดงโพสต์อื่นที่สถานที่เดียวกัน

## Out of scope รอบนี้ (ชัดเจน)

- **ไม่มีแผนที่แบบ live/interactive** ตอนเลือกสถานที่ (ไม่มีปักหมุดบนแผนที่ให้ลากเอง) — เลือกจากรายการผลลัพธ์ข้อความเท่านั้น
- **แตะชื่อสถานที่บนโพสต์แล้วไม่เปิดอะไรทั้งสิ้น** ไม่เปิดแผนที่ ไม่แสดงโพสต์อื่นที่สถานที่เดียวกัน (ไม่มี location-based discovery feed)
- **ไม่มีหน้ารวม "โพสต์จากสถานที่นี้"** หรือหน้า location profile ใดๆ
- **1 โพสต์ผูกได้ 1 สถานที่เท่านั้น** ไม่รองรับหลายสถานที่ต่อโพสต์
- **ไม่มีการแก้ไขสถานที่หลังโพสต์แล้ว** (เอาสถานที่ออกได้ก่อนกดโพสต์เท่านั้น การแก้ไข location ของโพสต์ที่โพสต์ไปแล้วไม่อยู่ในสโคป เว้นแต่มีฟีเจอร์ "แก้ไขโพสต์" อยู่แล้วในระบบซึ่งควรรวม location เข้าไปด้วยถ้ามี — ให้ AI Design ตรวจสอบว่าระบบมี edit-post flow อยู่แล้วหรือไม่)
- **ไม่มี auto-suggest สถานที่จากประวัติที่เคยเช็คอิน** (ทุกครั้งค้นหาใหม่ผ่าน LocationIQ เสมอ)
- **ไม่ทำ purge/archival job สำหรับ `location_search_requests`** ในรอบนี้ (เหมือนที่ `drop_views` เองก็ไม่มี purge job — ยอมรับความเสี่ยงตารางโตเรื่อยๆ ไว้ก่อน เป็น fast-follow ได้ในอนาคต)

## Edge cases

| กรณี | พฤติกรรมที่คาดหวัง |
|---|---|
| ผู้ใช้ไม่ให้สิทธิ์ GPS | แสดงข้อความ "WYN ไม่มีสิทธิ์เข้าถึงตำแหน่งของคุณ..." พร้อมปุ่มพาไปหน้าตั้งค่าเครื่อง (ถ้าแพลตฟอร์มรองรับ) — ผู้ใช้ยังค้นหาด้วยการพิมพ์ได้ตามปกติ ไม่ block ทั้ง flow |
| LocationIQ API ล่ม/timeout | Edge Function ต้องมี timeout ที่เหมาะสม (เช่น 5-8 วินาที) แล้ว fail gracefully — client แสดง "ค้นหาสถานที่ไม่สำเร็จตอนนี้..." — **โพสต์ยังโพสต์ได้ตามปกติโดยไม่มีสถานที่แนบ** ไม่ block การโพสต์ทั้งหมดเพราะ dependency ภายนอกล่ม |
| LocationIQ ตอบ 429 (rate-limited ฝั่ง provider เอง เพราะโควตารวมของทั้งแอปหมด) | เหมือนเคส API ล่ม — แสดงข้อความเดียวกัน ไม่โยน error technical ให้ผู้ใช้เห็น — ควรมี logging ฝั่ง server ให้ Founder/DevOps รู้ว่าโควตาใกล้หมดก่อนจะกระทบผู้ใช้จริงเยอะ (นอกสโคป UI แต่ Design/Coding ควรพิจารณา) |
| ผลการค้นหาสถานที่กำกวม/ซ้ำกันหลายรายการ (เช่น ค้นหา "starbucks" ได้หลายสาขา) | แสดงรายการทั้งหมดที่ LocationIQ ส่งกลับมา ให้ผู้ใช้เลือกเอง — ไม่พยายาม auto-disambiguate หรือเดาให้ — ถ้า LocationIQ ส่ง address/ที่อยู่ย่อยมาด้วยให้แสดงเป็นบรรทัดรองใต้ชื่อเพื่อช่วยแยกความแตกต่าง (เช่น "Starbucks — สยามพารากอน" กับ "Starbucks — เซ็นทรัลเวิลด์") |
| ผู้ใช้พิมพ์แล้วลบอย่างรวดเร็ว (typing เร็ว) | Debounce ฝั่ง client จัดการอยู่แล้ว (ข้อ 3) — request เก่าที่ยังไม่ตอบกลับควรถูกยกเลิก/ignore ผลลัพธ์เมื่อมี request ใหม่กว่าแทนที่ (กัน race condition แสดงผลลัพธ์เก่าทับผลลัพธ์ใหม่) |
| โพสต์ที่มี location ถูกลบ (`deleted_at` ถูกตั้งค่า) | ไม่มีอะไรต้องทำเพิ่ม — RLS visibility เดิมของ `drops` จัดการอยู่แล้ว (ข้อ 4) |

## Acceptance Criteria

- [ ] กดปุ่มปักหมุดสถานที่ตอนสร้างโพสต์ → เปิดหน้าค้นหาจริง พิมพ์แล้วขึ้นผลลัพธ์จาก LocationIQ จริง (ไม่ mock)
- [ ] กด "ใช้ตำแหน่งปัจจุบันของฉัน" → ขอ GPS permission ถ้ายังไม่เคยอนุญาต → ได้ชื่อสถานที่ใกล้เคียงจริงผ่าน reverse geocoding
- [ ] เลือกสถานที่แล้วแนบเข้าโพสต์สำเร็จ → บันทึกลง `drops.location`/`location_lat`/`location_lon`/`location_place_id` ถูกต้อง
- [ ] โพสต์ที่เช็คอินแล้วแสดงชื่อสถานที่บนการ์ดโพสต์และหน้ารายละเอียดโพสต์ (ไอคอนหมุด + ชื่อ)
- [ ] โพสต์ที่ไม่ได้เช็คอินไม่แสดงส่วนสถานที่เลย
- [ ] ลบสถานที่ที่เลือกออกก่อนกดโพสต์ได้ (ปุ่ม X บน chip)
- [ ] LocationIQ API key ไม่ปรากฏในโค้ด Flutter หรือ build artifact ใดๆ (ยิงผ่าน Edge Function เท่านั้น) — ตรวจสอบผ่าน code review/`flutter build` ไม่มี string ของ key หลุดออกมา
- [ ] ยิง request ค้นหาถี่เกินเพดานที่ตั้งไว้ (ทดสอบตรงผ่าน Edge Function ไม่ผ่าน UI) → ได้ HTTP 429 กลับมา ไม่ยิงต่อไปยัง LocationIQ จริง
- [ ] ปิด GPS permission แล้วกดปุ่มใช้ตำแหน่งปัจจุบัน → แสดงข้อความแจ้งเตือนที่ถูกต้อง ไม่ crash แอป
- [ ] LocationIQ ตอบ error/timeout (จำลองได้) → แอปไม่ crash, ผู้ใช้ยังโพสต์ต่อได้โดยไม่มีสถานที่
- [ ] Regression: ทุกฟีเจอร์เดิม (Drop/Pop/Club/Home/Follow/Profile/Search/Notification) ยังทำงานปกติ

## Dependencies

- **บล็อกด้วย Founder/DevOps action**: ต้องมี LocationIQ account + API key จริงก่อนต่อจริงได้ (provider เลือกแล้ว — LocationIQ — เหลือแค่สมัคร/ให้ key) เหมือน pattern WYN-016 (Firebase service account)
- ใช้ device GPS permission ของแพลตฟอร์ม (iOS/Android) — ต้องตรวจสอบว่า `app/` มี dependency สำหรับ location permission/GPS อยู่แล้วหรือต้องเพิ่มใหม่ (เป็นงานของ AI Coding ตรวจ ไม่ใช่ AI Product Manager)
- WYN-097 (Audience selector) — **ไม่ block กัน** งานนี้ทำได้ก่อน/หลัง/พร้อมกันก็ได้ เพราะ location เป็นคอลัมน์บน `drops` ที่ inherit visibility rule ของโพสต์เดิมโดยอัตโนมัติเสมอ (ดูข้อ 4)

## Priority
กลาง-สูง — เขียนโค้ดส่วน UI/data-model ทำได้ทันทีในทางเทคนิค แต่ทดสอบ end-to-end จริง (ยิง LocationIQ จริง) ต้องรอ API key จาก Founder/DevOps ก่อน เหมือนที่ backlog เดิมระบุไว้

## Risks

| # | ความเสี่ยง | ระดับ | การป้องกัน |
|---|---|---|---|
| R1 | **Dependency ภายนอกใหม่ (LocationIQ)** — เป็น third-party service ตัวแรกของโปรเจกต์ที่ไม่ใช่ Supabase/Firebase — มีความเสี่ยงเรื่อง API key management (ต้องหมุน key ได้ถ้าหลุด), uptime อยู่นอกการควบคุมของ WYN (ถ้า LocationIQ ล่ม ฟีเจอร์นี้ใช้ไม่ได้ทั้งหมด), และเงื่อนไข free tier เปลี่ยนได้ตลอดเวลาโดย provider ฝ่ายเดียว | กลาง | เก็บ key เป็น secret ผ่าน Edge Function เท่านั้น (ไม่มี fallback ฝัง key ในแอป), ออกแบบให้การเช็คอินเป็น optional เสมอ (ล่มแล้วโพสต์ยังทำได้ตามปกติ ไม่ block), บันทึกไว้ชัดเจนว่าต้องเช็ค pricing page จริงตอน implement ไม่เชื่อตัวเลขสมมติฐานในสเปกนี้ 100% |
| R2 | **Migration บน `drops` ต้องยึดวินัยเดียวกับ WYN-071/072/083** — schema.sql มีปัญหารู้อยู่แล้ว (บันทึกไว้ใน DECISIONS.md 2026-09-02: "schema.sql โหลดสดเข้า PostgreSQL ว่างเปล่าไม่ผ่าน") จาก view definition ที่สะสมทับกันหลายรอบ — **ห้ามเชื่อ column order ใน `schema.sql` ตรงๆ ว่าตรงกับ production จริง** ต้องตรวจสอบ production schema จริงก่อน apply migration เพิ่มคอลัมน์ เหมือนวิธีที่ AI Deploy & DevOps เคยใช้แก้ P0 incident 2 ครั้งก่อนหน้า (WYN-071 2026-08-25, WYN-072 2026-09-01) | สูง (migration risk, ไม่ใช่ risk ของฟีเจอร์เอง) | AI Coding/Deploy ต้อง query production schema จริงผ่าน Supabase Management API/Dashboard ก่อน apply `alter table drops add column` ใดๆ ไม่ใช่แก้ `schema.sql` แล้วสมมติว่าโหลดตรงกับ production เป๊ะ — เพิ่มคอลัมน์ nullable ใหม่ล้วนๆ ในงานนี้ (ความเสี่ยงต่ำกว่า WYN-083 ที่เปลี่ยน primary key ของตารางที่มีข้อมูลจริงอยู่แล้ว เพราะ `drops` เดิมไม่มีข้อมูลในคอลัมน์ location ใหม่ทั้ง 3 ตัวอยู่แล้ว เป็นการเพิ่มคอลัมน์ล้วนๆ ไม่ใช่แก้ไขโครงสร้างเดิม) |
| R3 | Rate-limit เพดานที่ตั้งไว้ (20 req/นาที/ผู้ใช้) เป็นค่าประมาณ อาจไม่พอดีกับพฤติกรรมจริง (แคบไปจนผู้ใช้ปกติโดนบล็อกผิด หรือกว้างไปจนโควตารวมหมดเร็ว) | ต่ำ-กลาง | ปรับได้ภายหลังจากข้อมูลการใช้งานจริงช่วง Beta ไม่ใช่ค่าตายตัว |

## Recommendation

1. เริ่ม AI Design ทันทีสำหรับส่วน UI (bottom sheet ค้นหาสถานที่, chip แสดงสถานที่ที่เลือก, การแสดงผลบนการ์ดโพสต์) — ไม่ต้องรอ API key เพราะ UI/UX ออกแบบและ implement ได้จากโครงสเปกนี้เลย โดยใช้ mock/placeholder data ระหว่างพัฒนา
2. แจ้ง Founder/DevOps ให้เริ่มสมัคร LocationIQ account คู่ขนานไปเลย (ไม่ต้องรอ Design/Coding เสร็จก่อน) เพื่อให้ end-to-end testing จริงเริ่มได้เร็วที่สุด
3. Coding เพิ่มคอลัมน์ใหม่บน `drops` แบบ nullable ล้วนๆ (ความเสี่ยง migration ต่ำ) แต่ต้องตรวจ production schema จริงก่อน apply ตามวินัยที่ระบุใน Risks R2
4. QA ต้องทดสอบเป็นพิเศษ: (ก) API key ไม่หลุดออกมาที่ client ไม่ว่าวิธีใด (ข) rate-limit ฝั่ง server บล็อกได้จริงไม่ใช่แค่ debounce ฝั่ง client (ค) ทุก edge case ในตารางด้านบนไม่ทำให้แอป crash หรือ block การโพสต์ปกติ (ง) regression กับฟีเจอร์เดิมทั้งหมด

## Handoff

**ส่งต่อ AI Design ก่อน AI Coding** เพราะนี่คือฟีเจอร์ใหม่ที่ผู้ใช้เห็นและใช้งานโดยตรง (user-facing) ตาม WORKFLOW ปกติของโปรเจกต์ (Product → Design → Coding → QA) — AI Design ต้องออกแบบ: (1) หน้าจอ/bottom sheet ค้นหาสถานที่ (ช่องค้นหา + ปุ่มใช้ตำแหน่งปัจจุบัน + รายการผลลัพธ์ + empty/error/loading state) (2) chip แสดงสถานที่ที่เลือกบนหน้าสร้างโพสต์ (3) การแสดงผลสถานที่บนการ์ดโพสต์และหน้ารายละเอียดโพสต์ (4) ใช้ Design system เดิมของ WYN (Blue+White+Soft Gray, Rounded Cards) ไม่ต้องออกแบบใหม่จากศูนย์ — จากนั้นส่งต่อ AI Coding (data model + Edge Function + rate limiting + UI implementation) แล้ว AI QA & Security ก่อน deploy
