## Feature

ZOKY Auto PromptPay + Auto Refund

## Goal

1. ลูกค้าจ่ายด้วย QR พร้อมเพย์แล้ว **ระบบรู้เองว่าจ่ายแล้ว** — ไม่ต้องแนบสลิป ไม่ต้องให้ร้านตรวจเอง
2. เมื่อออเดอร์ที่จ่ายแล้วถูกยกเลิก **เงินคืนลูกค้าอัตโนมัติ** — ร้านไม่ต้องกดคืนเอง
3. (Founder 2026-10-22) **ทุกออเดอร์จ่ายผ่าน Stripe เท่านั้น** — ไม่มี QR ร้าน/สลิป/การยืนยันเงินเข้าด้วยมือ ซึ่งทำให้ทุกออเดอร์ที่จ่ายแล้วคืนเงินอัตโนมัติได้

## Target User

- ลูกค้า ZOKY (zoky.wynos.online)
- ร้านค้าบน WYNOS Merchant (merchant.wynos.online)
- WYNOS Admin (ดูสถานะ/แก้ปัญหาเมื่อการคืนเงินล้มเหลว)

## Problem

- ทางที่ลูกค้าเห็นชัดที่สุดตอนนี้คือ "QR พร้อมเพย์ของร้าน + แนบสลิป" ซึ่ง**ไม่ยืนยันอัตโนมัติจริง** ส่วนใหญ่ต้องรอร้านตรวจสลิป (ดู Current State ข้อ A2)
- พร้อมเพย์ที่ยืนยันอัตโนมัติมีอยู่แล้วแต่ "ซ่อน" อยู่ในปุ่ม "จ่ายด้วยบัตร" ของ Stripe และขึ้นกับว่าบัญชี Stripe ของร้านเปิด PromptPay แล้วหรือยัง
- เมื่อร้านยกเลิกออเดอร์ที่จ่ายแล้ว ระบบแค่ตั้งสถานะ "รอคืนเงิน" — **ร้านต้องกดคืนเงินเอง** ถ้าร้านลืม ลูกค้าไม่ได้เงินคืน
- มีช่องโหว่ที่ลูกค้าอาจจ่ายเงินสำเร็จหลังออเดอร์ถูกยกเลิกไปแล้ว และไม่มีการคืนเงินอัตโนมัติ (ดู Current State ข้อ C3)

### B. ใครจ่ายค่าธรรมเนียม / เงินเข้าใคร

- Stripe เป็น **direct charge บนบัญชี Stripe ของร้าน** (header `Stripe-Account` ใน `food-stripe-checkout/index.ts` บรรทัด 31) → เงินเข้า balance Stripe ของร้าน แล้วโอนเข้าบัญชีธนาคารร้านตามรอบ payout (ร้านจะ "ready" ได้ต้องตั้ง payout อัตโนมัติ — `stripe-webhook/index.ts` ~238–240)
- ค่าธรรมเนียม Stripe ของ direct charge ปกติหักจากบัญชีร้าน — อัตราจริงสำหรับ PromptPay/บัตรในไทย **ต้องตรวจสอบกับ Stripe**
- GP ของ WYNOS = 0% ตอนนี้ (Founder 2026-10-11, `.wyn/company/DECISIONS.md` "GP v1") เก็บผ่าน application fee เมื่อเปิดใช้; QR/สลิปเข้าบัญชีร้านตรง **เก็บ GP ไม่ได้**
- WYNOS ไม่ได้ถือเงินลูกค้าในทางใดเลย

### D. หมดเวลาชำระเงิน (10 นาที)

- `food_orders.payment_due_at` = สร้างออเดอร์ + 10 นาที (`supabase/migrations/20261008113000_food_unpaid_payment_timeout.sql`)
- cron ทุก 1 นาที เรียก `supabase/functions/food-unpaid-timeout/index.ts` → ถ้ามี Stripe session ต้อง **expire session ที่ Stripe ก่อน** แล้วจึงเรียก `food_timeout_cancel`; ถ้า Stripe ตอบว่าจ่ายแล้วจะไม่ยกเลิก (defer) — มี test `web/tests/food-payment-timeout.test.mjs`
- สลิปที่ส่งทันเวลา (`submitted`) ไม่ถูกยกเลิก; ส่งสลิปหลังหมดเวลาถูก trigger `food_guard_late_slip` ปฏิเสธ
- **QR พร้อมเพย์ของร้าน (A1) ไม่มีวันหมดอายุ** ลูกค้ายังโอนตาม QR ได้แม้ออเดอร์ถูกยกเลิกแล้ว → เงินเข้าร้านโดยไม่มีออเดอร์ และไม่มีทางคืนอัตโนมัติ

### E. ช่องโหว่ที่พบ (ต้องแก้ใน feature นี้)

1. **จ่ายสำเร็จหลังยกเลิก (Stripe)**: `food_cancel_order` (ลูกค้า) และ `food_transition_order` (ร้านยกเลิกออเดอร์ที่ยังไม่จ่าย) **ไม่ได้ expire Stripe Checkout session** ถ้าลูกค้ายังเปิดหน้า Stripe ค้างไว้แล้วจ่าย webhook จะตั้ง `payment_status='paid'` บนออเดอร์ที่ `cancelled` (เงื่อนไขใน `food_apply_stripe_event` ไม่เช็ค `status`, `migrations_wynos_stripe_payment_core_v1.sql` ~199–212) และไม่ตั้ง `refund_status` → เงินค้างโดยไม่มีใครรู้
2. การคืนเงินล้มเหลว (`refund.failed`) ไม่สะท้อนในออเดอร์/ไม่แจ้งใคร
3. ไม่มีตัวจับ "ออเดอร์ยกเลิกแล้วแต่ยังค้างคืนเงิน" (refund pending นาน)
4. ไม่มีหน้า Admin สำหรับการคืนเงิน (ระบุเป็น "เร็วๆ นี้" — `.wyn/company/DECISIONS.md` ~2214; `docs/engineering/WYNOS-ADMIN-MASTER-GAP-ANALYSIS.md` D2)

|---|---|---|

## Requirements

> หลักการ: ใช้ของเดิม (Stripe Connect direct charge, webhook, idempotency, timeout worker) — ไม่เปลี่ยนผู้ให้บริการชำระเงิน ไม่ให้ WYNOS ถือเงิน ไม่เพิ่มฟีเจอร์นอกคำขอ

### User Stories

**ลูกค้า**
- US-C1: ในฐานะลูกค้า ฉันต้องการเห็นตัวเลือก "จ่ายด้วยพร้อมเพย์ (ยืนยันอัตโนมัติ)" ชัดเจน สแกนด้วยแอปธนาคาร แล้วออเดอร์เปลี่ยนเป็น "ชำระเงินแล้ว" เองโดยไม่ต้องแนบสลิป
- US-C2: ในฐานะลูกค้า ถ้าออเดอร์ที่ฉันจ่ายแล้วถูกยกเลิก ฉันต้องการได้เงินคืนเข้าช่องทางเดิมโดยไม่ต้องขอ และเห็นสถานะ "กำลังคืนเงิน" → "คืนเงินแล้ว" พร้อมแจ้งเตือน
- US-C3: ในฐานะลูกค้า ถ้าฉันจ่ายเงินหลังออเดอร์ถูกยกเลิก/หมดเวลา ฉันต้องได้เงินคืนอัตโนมัติ
- US-C4: ในฐานะลูกค้า ถ้าการคืนเงินมีปัญหา ฉันต้องเห็นข้อความที่เข้าใจได้และช่องทางติดต่อ

**ร้านค้า**
- US-M1: ในฐานะร้าน ฉันต้องการรู้ว่าร้านฉันรับพร้อมเพย์อัตโนมัติได้หรือยัง และถ้ายังต้องทำอะไร
- US-M2: ในฐานะร้าน เมื่อฉันยกเลิกออเดอร์ที่จ่ายแล้ว (ผ่าน Stripe) ระบบคืนเงินให้ลูกค้าทันทีโดยฉันไม่ต้องกดปุ่มคืนเงินอีกครั้ง และฉันเห็นผลคืนเงินในออเดอร์และหน้าการเงิน
- US-M3: ในฐานะร้าน ฉันต้องถูกแจ้งเตือนเมื่อการคืนเงินล้มเหลว (เช่น ยอดใน Stripe ของร้านไม่พอ)

**Admin**
- US-A1: ในฐานะ WYNOS Admin ฉันต้องการเห็นรายการคืนเงินที่ค้าง/ล้มเหลว เพื่อติดตามกับร้าน (อ่านอย่างเดียวใน P1 — การกดคืนเงินจาก Admin ต้องให้ Founder ตัดสิน)

**ร้านค้า (เพิ่มตามคำตัดสิน 2026-10-22)**
- US-M4: ในฐานะร้านที่ยังไม่มี Stripe ฉันต้องรู้ชัดว่าทำไมร้านรับออเดอร์ไม่ได้ และกดปุ่มเดียวไปตั้งค่ารับเงิน
- US-M5: ในฐานะร้านที่มีออเดอร์สลิปค้างอยู่ตอนเปลี่ยนระบบ ฉันยังตรวจ/ยืนยัน/คืนเงินออเดอร์เหล่านั้นจนจบได้

### Functional Requirements

**R0 — ตัดช่องทาง QR ร้าน + แนบสลิปออก (P0, Founder 2026-10-22)**
- R0.1 ฝั่งลูกค้า ZOKY: ลบ QR พร้อมเพย์ของร้าน, ข้อมูลบัญชี/ปุ่มคัดลอก, การแนบสลิป และข้อความ "โอนเข้าบัญชีร้าน" ออกจากหน้าชำระเงิน (`web/components/food/wynos-food-developer-app.tsx` ~2534, 2871–2888, 2914–2940, 2963, 3012–3035, 3046–3078) — เหลือเฉพาะปุ่ม Stripe (พร้อมเพย์ / บัตร)
- R0.2 ฝั่ง server ต้องปิดจริง ไม่ใช่แค่ซ่อนปุ่ม: ออเดอร์ใหม่ต้องเรียก `food_submit_payment` ไม่ได้, `food-payment-qr` และ `food-verify-slip` ไม่ให้บริการออเดอร์ใหม่ (กัน direct-API bypass) — **ต้องมี DB migration** (แก้ RPC) และ deploy edge functions
- R0.3 ฝั่งร้าน: ลบปุ่ม "ยืนยันเงินเข้า / ทำเครื่องหมายว่าชำระแล้ว / สลิปมีปัญหา" สำหรับออเดอร์ ZOKY ใหม่ (`web/components/merchant/wynos-merchant-app.tsx` ~2106–2184) และฟอร์มตั้งค่าพร้อมเพย์/บัญชี/รูป QR สำหรับรับเงินลูกค้า (~2666, 2804–2852, 3058) ให้เหลือ "ตั้งค่ารับเงินผ่าน Stripe" (`merchant-payment-setup.tsx`)
- R0.4 `food_set_payment_status` (ร้านตั้ง paid เอง) ต้องใช้ไม่ได้กับออเดอร์ `source='app'` ใหม่ — **DB migration**
- R0.5 ไม่ลบคอลัมน์/ข้อมูลเดิม (`promptpay_id`, `payment_slip_path`, ไฟล์สลิปใน `food-private`) ในงานนี้ — เก็บไว้เพื่อ audit/คืนเงินออเดอร์เก่า การลบเป็น destructive operation ต้องขออนุมัติแยก
- R0.6 นอกขอบเขตจนกว่า Founder ยืนยัน: ออเดอร์ที่ร้านสร้างเอง (`food_create_manual_order`, `source='manual'`) และการเติมเงินโฆษณาของร้านที่ใช้ PromptPay + สลิป (WYN-207, `.wyn/company/APPROVALS.md` ~375, 404) — ดู D7, D8

**R5 — รับออเดอร์ได้เฉพาะร้านที่ Stripe พร้อม (P0)**
- R5.1 เงื่อนไข "ร้านพร้อมรับเงิน" = `food_stripe_accounts.status='ready'` และ `charges_enabled` (และ `promptpay_enabled` ถ้า Founder เลือกใน D9)
- R5.2 บังคับฝั่ง server ตอนสร้างออเดอร์ (`food_create_order`) ไม่ใช่แค่ UI — **DB migration**
- R5.3 แก้ readiness ที่ปัจจุบันนับพร้อมเพย์/บัญชีธนาคาร/รูป QR เป็น "พร้อมรับเงิน": `internal.food_store_publish_readiness_json` (`migrations_wynos_stripe_payment_core_v1.sql` ~406–462), `internal.food_store_readiness_missing` (`migrations_wynos_food_service_area_v1.sql` ~165–191 — ฟังก์ชันนี้ไม่นับ Stripe เลย), checklist ร้าน `wynos-merchant-app.tsx` ~1033 — **ต้องตรวจว่าเวอร์ชันไหนอยู่บน production**
- R5.4 ZOKY แสดงร้านที่ยังไม่พร้อมเป็น "ยังไม่เปิดรับออเดอร์" หรือซ่อน (ตาม D10) และห้ามใส่ตะกร้า/สั่ง
- R5.5 ถ้าบัญชี Stripe ของร้านถูกจำกัดภายหลัง (webhook sync ตั้ง `stripe_payments_enabled=false`) ร้านต้องหยุดรับออเดอร์ใหม่อัตโนมัติ

**R6 — ออเดอร์สลิปที่ค้างอยู่ตอนเปลี่ยนระบบ (P0)**
- R6.1 ไม่ยกเลิกหรือแก้ไขออเดอร์เก่าย้อนหลัง
- R6.2 ออเดอร์ `payment_status='submitted'` (รอตรวจสลิป): ร้านยังยืนยัน/แจ้งปัญหาได้จนจบ (คงฟังก์ชันเดิมเฉพาะออเดอร์ที่สร้างก่อนวันเปลี่ยน)
- R6.3 ออเดอร์ `pending/issue` ที่ยังไม่จ่ายและยังไม่หมดเวลา: ให้ลูกค้าจ่ายผ่าน Stripe ได้ถ้าร้านพร้อม; ถ้าร้านไม่พร้อม ปล่อยให้ timeout 10 นาทีเดิมยกเลิก
- R6.4 ออเดอร์สลิปที่จ่ายแล้วแล้วถูกยกเลิก: คง flow ร้านโอนคืนเอง + ยืนยัน (`merchant_set_refund_status`) — คืนอัตโนมัติไม่ได้เพราะเงินไม่ได้ผ่าน Stripe
- R6.5 ก่อนเปิดใช้ ทีมต้องรายงานจำนวนออเดอร์ค้างแต่ละสถานะด้วย read-only check (ไม่ดึงข้อมูลส่วนบุคคล)

**R7 — ร้านที่ยังไม่มี Stripe เห็นอะไร (P0)**
- R7.1 แบนเนอร์ใน Merchant: "ตั้งแต่ <วันที่> ZOKY รับเงินผ่าน Stripe เท่านั้น ร้านต้องเปิดรับชำระเงินก่อนจึงจะรับออเดอร์ได้" + ปุ่ม "เปิดรับชำระเงิน"
- R7.2 แจ้งล่วงหน้าก่อนวันบังคับ (ระยะเวลาตาม D11) ผ่าน merchant notification
- R7.3 สถานะร้านแสดงเหตุผลที่ปิดรับออเดอร์ชัดเจน (onboarding ค้าง / ต้องส่งเอกสารเพิ่ม / ถูกจำกัด)

**R1 — จ่ายด้วยพร้อมเพย์อัตโนมัติ (P0)**
- R1.1 หน้าชำระเงินมีตัวเลือก "พร้อมเพย์ · ยืนยันอัตโนมัติ" แยกจาก "บัตร" เมื่อร้าน `stripe_payments_enabled` และ PromptPay ของบัญชีร้าน active
- R1.2 ตัวเลือกพร้อมเพย์เปิด Stripe Checkout ที่จำกัดให้เป็นพร้อมเพย์ (หรือแสดง QR ใน ZOKY — Architect เลือกวิธี) บนบัญชีร้านเดิม (direct charge)
- R1.3 ยืนยันการจ่ายผ่าน webhook ที่ตรวจลายเซ็นเท่านั้น ห้ามเชื่อ redirect `?stripe=success` จาก client
- R1.4 บันทึกวิธีจ่ายจริง (card / promptpay) จาก PaymentIntent/Charge แทน `payment_method_types[0]`
- R1.5 ร้านที่ Stripe พร้อมแต่ PromptPay ยังไม่ active → แสดงเฉพาะบัตร (ถ้า Founder เลือก D9 = ก) หรือร้านปิดรับออเดอร์ (D9 = ข); ไม่มีทางเลือก QR/สลิปอีกต่อไป

**R2 — คืนเงินอัตโนมัติเมื่อยกเลิก (P0)**
- R2.1 เมื่อออเดอร์ที่ `payment_provider='stripe'` และ `payment_status='paid'` ถูกยกเลิก (ไม่ว่าโดยร้าน หรือโดยลูกค้าถ้า Founder เปิดสิทธิ์ใน D3) ระบบ server สร้าง Stripe refund เต็มจำนวนเองโดยไม่ต้องให้ร้านกด
- R2.2 ใช้ idempotency key ต่อออเดอร์ (ต่อยอด `wynos-refund-<order>` เดิม) — ห้ามคืนซ้ำ
- R2.3 refund ถูกสร้างบนบัญชี Stripe ที่รับเงินจริง (`food_stripe_payments.stripe_account_id`) และ livemode ตรงกัน (pattern เดียวกับ `merchant-stripe-refund`)
- R2.4 ถ้ามี GP > 0 ให้คืน application fee ตามคำตัดสิน GP v1 (`refund_application_fee`)
- R2.5 สถานะ `refund_status`: pending → refunded (จาก webhook) หรือ failed (จาก `refund.failed` / error) — **`refund.failed` ต้องอัปเดตออเดอร์และแจ้งร้าน**
- R2.6 การยกเลิกต้องสำเร็จเสมอแม้ Stripe ล่มชั่วคราว — refund ต้องถูก retry อัตโนมัติ (มีงาน retry/reconcile) ไม่ใช่ทิ้งไว้
- R2.7 ปุ่ม "คืนเงินผ่าน Stripe" เดิมของร้านคงไว้เป็นทาง retry/สำรอง (ไม่ทำให้คืนซ้ำเพราะ idempotency)

**R3 — กันเงินค้างจากการจ่ายหลังยกเลิก (P0)**
- R3.1 เมื่อลูกค้าหรือร้านยกเลิกออเดอร์ที่ยังไม่จ่ายแต่มี Stripe session เปิดอยู่ ต้อง expire session ก่อน/พร้อมการยกเลิก (แบบเดียวกับ `food-unpaid-timeout`)
- R3.2 ถ้า webhook "paid" มาถึงออเดอร์ที่ `cancelled` แล้ว → บันทึกว่าจ่ายแล้ว + คืนเงินอัตโนมัติทันที ห้ามเปลี่ยนออเดอร์กลับเป็นใช้งาน และแจ้งลูกค้า/ร้าน

**R4 — การมองเห็นสถานะ (P0 สำหรับลูกค้า/ร้าน, P1 สำหรับ Admin)**
- R4.1 ลูกค้าเห็น "กำลังคืนเงิน" / "คืนเงินแล้ว" / "คืนเงินมีปัญหา — ติดต่อร้าน" ในหน้าออเดอร์ + แจ้งเตือน
- R4.2 ร้านเห็นผลคืนเงินในออเดอร์และหน้าการเงิน (มีอยู่แล้วบางส่วน `merchant-finance.tsx`)
- R4.3 (P1) Admin เห็นรายการคืนเงินค้าง > X ชั่วโมง และล้มเหลว (อ่านอย่างเดียว)

### Non-functional

- Security: refund/expire ทำฝั่ง server เท่านั้น ด้วย service role; ไม่มี endpoint ที่ลูกค้าเรียกให้คืนเงินตามยอดที่ client ส่ง; ตรวจสิทธิ์ร้าน/ลูกค้าฝั่ง server; ห้าม log ข้อมูลส่วนบุคคล/secret
- Auditability: ทุกการคืนเงินมี `food_order_events` + `stripe_refund_id`
- Mobile-first, ภาษาไทย, ข้อความสถานะเข้าใจง่าย
- ไม่กระทบ flow QR/สลิปเดิมจนกว่า Founder ตัดสิน D1

## Acceptance Criteria

**การจ่าย**
- AC1: ร้านที่ Stripe ready + PromptPay active: ลูกค้าเห็นตัวเลือกพร้อมเพย์ จ่ายสำเร็จ → ภายใน ≤ 1 นาทีหลัง Stripe ส่ง webhook ออเดอร์เป็น `paid` โดยไม่มีสลิปและไม่มีการกดของร้าน
- AC2: redirect success อย่างเดียว (ไม่มี webhook) ไม่ทำให้ออเดอร์เป็น `paid`
- AC3: ร้านที่ PromptPay ไม่ active ไม่แสดงตัวเลือกพร้อมเพย์อัตโนมัติ
- AC4: ออเดอร์ที่จ่ายด้วยพร้อมเพย์ถูกบันทึกวิธีจ่ายเป็น promptpay
- AC5: หมด 10 นาทีโดยไม่จ่าย → session หมดอายุที่ Stripe แล้วออเดอร์ถูกยกเลิก (พฤติกรรมเดิมไม่ถดถอย)

**การคืนเงิน**
- AC6: ร้านยกเลิกออเดอร์ Stripe ที่จ่ายแล้ว → มีการสร้าง refund อัตโนมัติ 1 ครั้ง โดยร้านไม่ต้องกดอะไรเพิ่ม; ลูกค้าเห็น "กำลังคืนเงิน" แล้ว "คืนเงินแล้ว" เมื่อ webhook ยืนยัน
- AC7: เรียกยกเลิก/คืนเงินซ้ำ (double click, retry, webhook ซ้ำ) → Stripe มี refund เดียว
- AC8: Stripe ตอบ error/timeout ตอนสร้าง refund → ออเดอร์ยังถูกยกเลิก, `refund_status` ไม่หายไป, ระบบ retry อัตโนมัติจนสำเร็จหรือถึงขีดจำกัดแล้วตั้ง `failed` + แจ้งร้าน (และ Admin ใน P1)
- AC9: `refund.failed` → `refund_status='failed'`, ลูกค้าเห็นข้อความ "คืนเงินมีปัญหา", ร้านได้แจ้งเตือน
- AC10: ลูกค้ายกเลิกออเดอร์ที่ยังไม่จ่ายขณะมี Stripe session เปิด → session ถูก expire; ถ้า Stripe รายงานว่าจ่ายแล้วระหว่างนั้น การยกเลิกต้องไม่ทิ้งเงินค้าง (คืนอัตโนมัติ หรือไม่ยกเลิก — ตาม design)
- AC11: webhook `paid` มาถึงออเดอร์ที่ `cancelled` → คืนเงินอัตโนมัติ + ออเดอร์ยังเป็น `cancelled`
- AC12: ผู้ใช้อื่น/ร้านอื่นสั่งคืนเงินออเดอร์ที่ไม่ใช่ของตนไม่ได้ (authorization server-side)
- AC13: ข้อมูลใน log ไม่มี secret, ชื่อ/เบอร์/ที่อยู่ลูกค้า

**Stripe เท่านั้น (Founder 2026-10-22)**
- AC14: หน้าชำระเงิน ZOKY ไม่มี QR ร้าน ข้อมูลบัญชีร้าน หรือปุ่มแนบสลิป สำหรับออเดอร์ใหม่
- AC15: เรียก `food_submit_payment` / `food-payment-qr` / `food-verify-slip` / `food_set_payment_status` ตรงผ่าน API กับออเดอร์ ZOKY ใหม่ → ถูกปฏิเสธฝั่ง server
- AC16: สร้างออเดอร์กับร้านที่ Stripe ไม่ ready (เรียก API ตรง) → ถูกปฏิเสธพร้อมข้อความภาษาไทยที่เข้าใจได้
- AC17: ร้านที่ Stripe ถูกจำกัดภายหลัง → รับออเดอร์ใหม่ไม่ได้ภายในรอบ sync ถัดไป
- AC18: ออเดอร์สลิปที่สร้างก่อนวันเปลี่ยน ยังถูกร้านยืนยัน/แจ้งปัญหา/บันทึกคืนเงินได้จนจบ และไม่มีออเดอร์เก่าถูกยกเลิกเพราะการเปลี่ยนนี้
- AC19: ร้านที่ไม่มี Stripe เห็นแบนเนอร์อธิบายและปุ่มเปิดรับชำระเงิน

## Edge Cases

| กรณี | พฤติกรรมที่ต้องการ |
|---|---|
| QR หมดอายุ | QR/Checkout ต้องหมดอายุไม่เกินเส้นตาย 10 นาทีของออเดอร์ (ระยะหมดอายุ QR ของ Stripe PromptPay **ต้องตรวจสอบกับ Stripe**) ลูกค้าเห็นปุ่มสร้างใหม่ถ้ายังไม่หมดเวลาออเดอร์ |
| จ่ายหลังหมดเวลา/หลังยกเลิก | คืนเงินอัตโนมัติเต็มจำนวน (R3.2) |
| จ่ายสำเร็จก่อนเส้นตายแต่ webhook มาช้า | worker เดิม defer ไม่ยกเลิก (คงไว้) |
| จ่ายซ้ำ (เปิด 2 แท็บ / 2 session) | session เดิมถูก reuse (`food-stripe-checkout` ~133–148) ถ้ายังเกิด charge ที่ 2 ต้องคืน charge ส่วนเกินอัตโนมัติ — กลไกให้ Architect ออกแบบ |
| จ่ายทั้ง Stripe และโอนตาม QR ร้าน+สลิป | มีกันบางส่วนแล้ว (`food_submit_payment` บังคับยกเลิก Stripe session ก่อน) แต่ QR ร้านจ่ายได้ตลอด → หมดไปเมื่อตัด QR/สลิป (R0) ยกเว้นลูกค้าที่บันทึก QR ร้านไว้เอง |

## Dependencies

- Stripe Connect accounts ของร้านต้อง ready และเปิด PromptPay ได้ (ฝั่ง Stripe)
- Stripe webhook endpoint ต้อง subscribe event ที่จำเป็นเพิ่ม เช่น `refund.failed`, `charge.refunded`, `checkout.session.async_payment_succeeded` (Founder ตั้งค่าใน Stripe Dashboard — **ต้องตรวจสอบรายการ event ที่ subscribe อยู่จริง**)
- Software Architect: กลไก auto-refund (trigger จาก DB → edge function หรือ worker แบบ `food-unpaid-timeout`), retry/reconcile, การ expire session ตอนยกเลิก
- Database Engineer: migration additive (ไม่ destructive) สำหรับสถานะ/คิวคืนเงิน และแก้ `food_apply_stripe_event` กรณี paid-after-cancel
- UI/UX: ตัวเลือกพร้อมเพย์บนหน้าชำระเงิน ZOKY และสถานะคืนเงิน (ลูกค้า/ร้าน)
- QA & Security: ทดสอบใน Stripe test mode เท่านั้น ด้วย synthetic data
- Production freeze / release gates เดิม — edge functions ที่กระทบ: `food-stripe-checkout`, `stripe-webhook`, `merchant-stripe-refund`, `food-unpaid-timeout`, (ใหม่) worker คืนเงิน

## Priority

**P0 (ต้องมีถึงจะถือว่าทำตามคำขอ + คำตัดสิน 2026-10-22)**
1. R5 + R7 บังคับ "ร้านต้องมี Stripe ready จึงรับออเดอร์ได้" (server-side) พร้อมหน้าจออธิบายสำหรับร้านที่ยังไม่มี — **ทำและสื่อสารร้านก่อน** จึงจะตัดสลิปได้
2. R0 ตัด QR ร้าน + สลิป + ยืนยันเงินด้วยมือ ทั้ง UI และ server สำหรับออเดอร์ใหม่
3. R6 จัดการออเดอร์สลิปที่ค้างอยู่ให้จบโดยไม่ยกเลิกย้อนหลัง
4. R2 คืนเงินอัตโนมัติเมื่อยกเลิกออเดอร์ที่จ่ายแล้ว + retry + idempotency + จัดการ `refund.failed`
5. R3 กันเงินค้าง: expire session ตอนยกเลิก และคืนอัตโนมัติเมื่อจ่ายหลังยกเลิก/หมดเวลา
6. R1.1–R1.3 ตัวเลือก "พร้อมเพย์ · ยืนยันอัตโนมัติ" ที่ชัดเจน
7. R4.1–R4.2 ลูกค้าและร้านเห็นสถานะคืนเงิน + แจ้งเตือน

ลำดับเปิดใช้ที่แนะนำ: (1) แจ้งร้าน + ช่วยร้านเปิด Stripe → (2) เปิดคืนเงินอัตโนมัติ + แก้ช่องโหว่ E1 (ไม่กระทบร้าน) → (3) วันบังคับ: ปิดรับออเดอร์ร้านที่ไม่พร้อม + ตัดสลิปพร้อมกัน → (4) เก็บกวาดออเดอร์สลิปค้าง

**P1**
- R1.4 บันทึกวิธีจ่ายจริง (card/promptpay) สำหรับรายงาน
- R4.3 หน้า Admin อ่านอย่างเดียว: คืนเงินค้าง/ล้มเหลว
- ช่วยร้านที่ PromptPay ยัง pending/inactive ให้เปิดได้ (ข้อความ/ลิงก์ใน merchant setup)
- คืน charge ซ้ำอัตโนมัติ (double payment)

**P2**
- Reconcile จาก Stripe แบบรายวัน (เทียบออเดอร์ cancelled+paid ที่ยังไม่ refund)
- คืนเงินบางส่วน (เฉพาะถ้า Founder อนุมัติใน D4)
- Admin สั่งคืนเงินได้เอง (เฉพาะถ้า Founder อนุมัติ — เป็นการเปลี่ยน payment authority)

## ผลกระทบต่อร้านที่ยังไม่อยู่บน Stripe (สำคัญ)

- เมื่อบังคับใช้ R5 **ร้านที่ Stripe ยังไม่ ready จะรับออเดอร์ ZOKY ไม่ได้ทันที** — รวมร้านที่สมัคร Stripe ค้างอยู่ (`onboarding`/`pending`) หรือถูกจำกัด (`restricted`)
- จำนวนร้านที่โดนผล: **ยังไม่ทราบ** (PM ห้ามเชื่อม DB จริง) — ทีมต้องรายงานจาก read-only check ก่อน Founder ตั้งวันบังคับ: จำนวนร้านเปิดอยู่ทั้งหมด / Stripe ready / PromptPay active / ยังไม่เริ่ม Stripe
- การ "ready" ใน WYNOS เข้มกว่าแค่ `charges_enabled`: ต้องมี payouts, บัญชีธนาคาร, ไม่มีเอกสารค้าง และรอบโอนอัตโนมัติ (`stripe-webhook/index.ts` ~238–240) → ร้านอาจใช้เวลาหลายวันกว่า Stripe ตรวจเอกสารเสร็จ (ระยะเวลา **ต้องตรวจสอบกับ Stripe**)
- ร้านต้องให้ข้อมูล KYC กับ Stripe (ตัวตน/ธุรกิจ/บัญชีธนาคาร) ซึ่งมากกว่า "ชื่อ + เลขบัญชี" — ร้านเล็กบางร้านอาจทำไม่ได้หรือไม่ยอมทำ
- ร้านจะเสียค่าธรรมเนียม Stripe ทุกออเดอร์ (เดิม QR พร้อมเพย์ร้านไม่เสีย) — อัตรา **ต้องตรวจสอบกับ Stripe**

## การโอนเงินให้ร้าน (Settlement) — เปรียบเทียบ 2 แบบ

> Founder input 2026-10-22 (ยังเป็นความต้องการ ไม่ใช่คำตัดสิน): "ตอนสมัคร Merchant ให้กรอกแค่ ชื่อ เลขบัญชี แล้วเงินจะโอนเข้าบัญชีร้านทุกวัน ตัดรอบเป็นวันๆ หลังหักค่า GP และค่าอื่นๆ"

### สิ่งที่มีอยู่แล้วใน repo

- **Onboarding ร้าน = Stripe Connect Accounts v2** (`supabase/functions/merchant-stripe-connect/index.ts` `createV2Account` ~372–400): ประเทศ TH, สกุล THB, ขอ capability `card_payments`, `fees_collector: "stripe"`, `losses_collector: "stripe"`, `dashboard: "none"`, กรอก KYC ผ่าน **embedded onboarding ภายใน WYNOS Merchant** (`createAccountSession` ~401–418, เปิด `external_account_collection` ให้กรอกบัญชีธนาคาร) — ตาราง `food_stripe_accounts` ยังบันทึก `account_type='standard'`
- **รับเงิน = direct charge บนบัญชีร้าน** (`food-stripe-checkout` ส่ง header `Stripe-Account`) ไม่ใช่ destination charge
- **โอนเข้าร้านรายวัน**: ระบบขอรอบโอน daily ให้แล้ว (`preferDailyPayouts` ~239–241, เรียกตอน onboard ~583, 597) และร้านจะ "ready" ได้ต้องมีรอบโอนอัตโนมัติ; บันทึก payout จาก webhook `payout.*` ลง `food_stripe_payouts` (`stripe-webhook/index.ts` ~368–393)
- **GP ต่อออเดอร์ = Stripe application fee** (`supabase/migrations/20261011140000_merchant_gp_v1.sql`; คำนวณใน `food_order_gp_quote`, ใช้ใน `food-stripe-checkout` ~111–171) — ตอนนี้ 0% ทุกร้าน (Founder 2026-10-11); คืนเงินเต็มจำนวนคืน GP ด้วย (`merchant-stripe-refund` ~97–99)
- **รายงานการเงิน**: `merchant_finance_summary` และ `admin_merchant_finance_overview` คำนวณ `income = sales_net - ad_spend + platform_funded - gp` และแสดง `gp_uncollected` สำหรับออเดอร์สลิป (`supabase/migrations/20261011140100_merchant_gp_finance_lines.sql` บรรทัด 1–18, `20261011120000_admin_merchant_finance_overview.sql`)
- **มีตัวอย่าง "WYNOS โอนให้ร้านเอง" อยู่แล้ว 1 จุด**: `food_platform_settlements` (`supabase/migrations_wynos_platform_campaigns_v1.sql` ~53–68) — Admin บันทึกการโอนส่วนลดที่ WYNOS ออกให้ร้าน (บันทึกด้วยมือ ไม่ได้โอนอัตโนมัติ)

**สรุป**: ความต้องการ "เงินเข้าร้านทุกวัน หลังหัก GP" **ทำได้แล้วเกือบทั้งหมดด้วยแบบ A ที่มีอยู่** ส่วนที่ไม่ตรงคือ "กรอกแค่ชื่อ + เลขบัญชี" เพราะ Stripe ต้องเก็บ KYC ของร้าน

| คืนเงินหลังโอนให้ร้านไปแล้ว | Stripe หักจาก balance ร้าน (ถ้าไม่พอ balance ติดลบ/หักรอบถัดไป — พฤติกรรมและผู้รับความเสียหายตาม `losses_collector` **ต้องตรวจสอบกับ Stripe**) | WYNOS จ่ายคืนลูกค้าเองก่อน แล้วต้องตามเงินคืนจากร้าน (หักรอบถัดไป หรือทวง) — WYNOS รับความเสี่ยง |
| ค่าธรรมเนียม | ค่าธรรมเนียม Stripe หักจากร้าน (direct charge); อาจมีค่า Connect ต่อบัญชี/ต่อ payout ขึ้นกับประเภทบัญชี — **ต้องตรวจสอบกับ Stripe** | ค่าธรรมเนียม Stripe ตกที่ WYNOS + ค่าโอนเงินให้ร้านทุกวัน + ต้นทุนคน/ระบบ |
| PromptPay | ต้องเปิดบนบัญชีร้านแต่ละร้าน (บางร้านอาจไม่ได้) — **ต้องตรวจสอบกับ Stripe** | เปิดครั้งเดียวบนบัญชี WYNOS — ทุกร้านได้พร้อมเพย์เท่ากัน |
| ภาษี / เอกสาร | GP เป็นรายได้ WYNOS ต้องออกใบกำกับ/หัก ณ ที่จ่ายตามกฎ — **ต้องปรึกษานักบัญชี/ทนาย** | ซับซ้อนกว่า: WYNOS รับยอดขายเต็มเข้าบัญชี อาจถูกมองว่ารายได้ทั้งหมดเป็นของ WYNOS, ต้องออกเอกสารการโอนให้ร้าน, VAT/หัก ณ ที่จ่ายของ GP — **ต้องปรึกษานักบัญชี/ทนาย** |
| กฎหมาย | Stripe เป็นผู้ให้บริการชำระเงิน WYNOS เป็น platform | การรับเงินแทนร้านแล้วโอนต่อ อาจเข้าข่ายธุรกิจบริการการชำระเงินที่ต้องขอใบอนุญาต (พ.ร.บ.ระบบการชำระเงิน / ธปท.) และเงื่อนไขการใช้ Stripe แบบรับเงินแทนผู้อื่น — **ต้องปรึกษานักบัญชี/ทนาย และต้องตรวจสอบกับ Stripe** |
| งานที่ต้องทำ | น้อย–กลาง: ส่วนใหญ่มีแล้ว เหลือปรับ onboarding ให้สั้นที่สุดเท่าที่ Stripe อนุญาต, หน้าสรุปรายวันสำหรับร้าน | มาก: ledger ต่อออเดอร์, ตัดรอบรายวัน, ระบบโอนเงิน, reconcile, รายงาน/เอกสารภาษี, คืนเงินหลังโอน, ย้ายโค้ด checkout/refund/webhook/finance ทั้งชุด — เป็น **major architecture + business model change** |
| ความเสี่ยงหลัก | ร้านบางส่วนสมัคร Stripe ไม่ผ่าน/ไม่ยอมกรอก KYC; PromptPay ไม่ได้ทุกร้าน | WYNOS รับผิดชอบเงินคนอื่น (โอนผิด/โอนซ้ำ/ทุจริต/บัญชีถูกอายัด), ความเสี่ยงกฎหมาย, Stripe อาจไม่อนุญาตรูปแบบนี้, ต้องมีคนดูแลทุกวัน |

### คำแนะนำ: **แบบ A** (ต่อยอดของเดิม)

1. ได้ "เงินเข้าร้านทุกวัน หลังหัก GP" แล้วเกือบทั้งหมดจากโค้ดที่ production มีอยู่ — งานน้อยและเสี่ยงน้อยที่สุด
2. WYNOS ไม่ต้องถือเงินลูกค้า ลดความเสี่ยงกฎหมาย/ใบอนุญาตและความรับผิดชอบเมื่อโอนผิด
3. คืนเงินอัตโนมัติ (คำขอหลักของ PRD นี้) ทำบนบัญชีร้านได้ทันที ไม่ต้องรอระบบ ledger ใหม่
4. ส่วนที่ยังไม่ตรงใจ ("กรอกแค่ชื่อ + เลขบัญชี") ให้ทีมตรวจกับ Stripe ว่าลดฟอร์มได้แค่ไหน แทนการเปลี่ยนโมเดลธุรกิจ
5. ถ้า Founder ยังต้องการแบบ B → ต้องปรึกษานักบัญชี/ทนายก่อน และเปิดเป็นโครงการแยกพร้อม APPROVAL_REQUIRED (core business model, security, infrastructure)

---

## Recommendation

1. ทำ P0 บนโครงสร้าง Stripe เดิม (direct charge เข้าร้าน, แบบ A) — ไม่เปลี่ยนผู้ให้บริการ ไม่ให้ WYNOS ถือเงิน
2. เปิดคืนเงินอัตโนมัติ + แก้ช่องโหว่ E1 ก่อน เพราะไม่กระทบร้านและแก้ความเสี่ยงที่มีอยู่แล้วบน production
3. ก่อนตั้งวันตัดสลิป: ทีมรายงานจำนวนร้านที่ Stripe ready / PromptPay active และตรวจกับ Stripe ตามรายการ "ต้องตรวจสอบกับ Stripe" แล้วแจ้งร้านล่วงหน้า
4. ตัดสลิปฝั่ง server และบังคับ Stripe ready ในวันเดียวกัน เพื่อไม่ให้มีช่วงที่ร้านรับออเดอร์แต่ลูกค้าจ่ายไม่ได้
