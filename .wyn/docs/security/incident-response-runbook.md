# Security Incident Response Runbook

อ้างอิง: `.wyn/tasks/backlog/WYN-048-consent-audit-security-incident.md` (Requirement 3), Master Spec section 28 ("Security Incident Workflow")

สถานะ: **เอกสาร ไม่ใช่โค้ด/ฟีเจอร์** — WYN ยังไม่มี production/ผู้ใช้จริง (Readiness Gate ยังไม่ผ่าน) และยังไม่มี Admin panel สำหรับตอบสนองแบบ real-time (Phase 7) ดังนั้นสิ่งที่ทำได้จริงตอนนี้คือกระบวนการที่พร้อมใช้ทันทีที่มีเหตุการณ์จริง — เอกสารนี้เขียนให้ **คนจริงเปิดอ่านระหว่างเกิดเหตุแล้วทำตามได้ทันที** ไม่ใช่หลักการกว้างๆ

---

## 1. Security Incident คืออะไร

**นับเป็น Security Incident** (ต้องทำตาม runbook นี้ทันที):
- ช่องโหว่ (vulnerability) ที่มีหลักฐานว่าถูกใช้โจมตีจริงแล้ว ไม่ใช่แค่พบในโค้ด (ถ้าพบแต่ยังไม่ถูกใช้ ให้แก้เป็นบั๊กปกติผ่าน AI Debug Engineer ตาม `WORKFLOW.md` ไม่ต้องเปิด incident)
- ข้อมูลผู้ใช้ (โปรไฟล์, ข้อความแชท, รูป/วิดีโอส่วนตัว) รั่วไหลออกนอกระบบ หรือถูกเข้าถึงโดยไม่ได้รับอนุญาต
- บัญชี `platform_role = 'admin'` หรือ `'moderator'` ถูกยึด (account takeover) หรือมีเหตุอันควรสงสัยว่าถูกยึด
- Credential ระดับระบบรั่วไหล: Supabase `service_role` key, database password, หรือ API key ของบริการภายนอกใดๆ ที่ WYN ใช้
- มีการเรียก RPC/endpoint ในลักษณะที่ผิดปกติชัดเจน (เช่น เรียกรัวเป็นพัน request เพื่อ scrape ข้อมูล, พยายาม bypass RLS) แม้จะยังไม่ยืนยันว่าสำเร็จ

**ไม่นับเป็น Security Incident** (จัดการผ่านช่องทางปกติ):
- บั๊กทั่วไปที่ไม่เกี่ยวข้อง privacy/security (ไปที่ AI Debug Engineer)
- Minor finding จาก QA ที่ยังไม่ถูกโจมตีจริง (บันทึกเป็น fast-follow ตาม pattern ที่ใช้อยู่แล้วในโปรเจกต์)
- ผู้ใช้รายงานเนื้อหาที่ไม่เหมาะสม (ไปที่ระบบ Report/Moderation ปกติ, WYN-026/029)

**ระดับความรุนแรง** (ใช้ประเมินว่าต้องเร่งแค่ไหนในขั้นตอน Contain/Notify):
- **S0 — วิกฤต**: ข้อมูลผู้ใช้จำนวนมากรั่วไหลจริง, `service_role` key รั่วไหล, หรือบัญชี admin ถูกยึดและถูกใช้ก่อความเสียหายแล้ว → ทำ Contain ทันทีโดยไม่รอการวิเคราะห์ให้ครบก่อน
- **S1 — รุนแรง**: ช่องโหว่ถูกใช้โจมตีแล้วแต่ผลกระทบจำกัด (เช่น บัญชีเดียว, ข้อมูลเฉพาะจุด) → Contain ภายในไม่กี่ชั่วโมง
- **S2 — ปานกลาง**: มีเหตุอันควรสงสัยแต่ยังไม่ยืนยันว่าเกิดผลกระทบจริง → Assess ก่อนตัดสินใจว่าต้อง Contain แบบเร่งด่วนหรือไม่

## 2. ขั้นตอนตอบสนอง

### 2.1 Detect (ตรวจพบ)

ช่องทางที่ incident อาจถูกตรวจพบในตอนนี้ (WYN ยังไม่มีระบบ monitoring/alerting อัตโนมัติ — นี่คือข้อจำกัดที่ต้องยอมรับตามสถานะปัจจุบันของโปรเจกต์):
- Founder หรือทีมสังเกตพฤติกรรมผิดปกติเอง (เช่น ข้อมูลหาย, บัญชีทำอะไรที่ตัวเองไม่ได้สั่ง)
- AI QA & Security พบระหว่างทดสอบว่าช่องโหว่ Major ถูกโจมตีได้จริง (ไม่ใช่แค่ทฤษฎี)
- รายงานจากผู้ใช้ภายนอก (bug bounty/รายงานตรง — ยังไม่มีช่องทางที่เป็นทางการตอนนี้ ใช้อีเมล/ช่องทางติดต่อของ Founder)
- Supabase Dashboard เอง (Database → Logs, Authentication → Logs) แสดงกิจกรรมผิดปกติ

**เมื่อมีเหตุอันควรสงสัย** — สิ่งแรกที่ต้องทำคือ **บันทึกเวลา + สิ่งที่สังเกตเห็นทันที** (ก่อนทำอะไรอื่น) เพื่อไม่ให้หลักฐานหายหรือความจำคลาดเคลื่อน:
```
วันเวลาที่ตรวจพบ:
ใครตรวจพบ / ช่องทางไหน:
สิ่งที่สังเกตเห็น (เจาะจงที่สุดเท่าที่ทำได้ — user id, table, RPC, เวลาโดยประมาณที่คาดว่าเริ่มเกิด):
ระดับความรุนแรงเบื้องต้น (S0/S1/S2):
```
เก็บบันทึกนี้ไว้เป็นจุดเริ่มต้นของ incident record ทั้งหมด (ดู Post-mortem หัวข้อ 2.6)

### 2.2 Contain (ควบคุมความเสียหาย)

เป้าหมาย: หยุดความเสียหายที่กำลังดำเนินอยู่ **ก่อน** วิเคราะห์ทุกอย่างให้ครบ — สำหรับ S0/S1 ห้ามรอ

ทำตามประเภทเหตุการณ์ (เลือกข้อที่ตรงกับสถานการณ์):
- **Credential รั่วไหล (`service_role` key, database password, API key ภายนอก)**: หมุนเวียน (rotate) key นั้นทันทีผ่าน Supabase Dashboard (Project Settings → API) หรือ dashboard ของบริการที่เกี่ยวข้อง — key เก่าจะใช้ไม่ได้ทันที ต้องอัปเดต environment variable ทุกที่ที่ใช้ key นั้นด้วย (deploy ใหม่ถ้าจำเป็น)
- **บัญชี admin/moderator ถูกยึด**: บังคับ sign out ทุก session ของบัญชีนั้นผ่าน Supabase Dashboard (Authentication → Users → เลือกบัญชี → Sign out user/revoke sessions) จากนั้นรีเซ็ตวิธียืนยันตัวตนของบัญชีนั้น (ผูกกับ Social Login/Phone OTP ตามที่ WYN-002 อนุมัติไว้ — ถ้าเป็น Social Login ให้เพิกถอนสิทธิ์แอปที่ provider นั้นและผูกใหม่)
- **ช่องโหว่เฉพาะจุดในโค้ด/RLS policy ที่กำลังถูกโจมตีอยู่**: ถ้าปิดการใช้งานฟีเจอร์นั้นชั่วคราวได้โดยไม่กระทบส่วนอื่นมาก (เช่น ปิด RPC หนึ่งตัวผ่าน `revoke execute on function ... from authenticated;` ตรงๆ ใน Supabase SQL editor) ให้ทำก่อน แล้วค่อยส่งต่อ AI Debug Engineer แก้ที่ต้นเหตุตาม flow ปกติ (`WORKFLOW.md`) — **ห้ามแก้ schema/production โดยไม่มีมนุษย์ตรวจสอบ** (ปิดชั่วคราวด้วยคำสั่งสั้นๆ ที่ย้อนกลับได้ทำได้ทันที แต่การแก้ไข schema ถาวรยังต้องผ่าน Coding → QA ตามปกติ ยกเว้น Founder อนุมัติให้ข้ามเป็นกรณีฉุกเฉินจริงๆ)
- **ข้อมูลผู้ใช้รั่วไหลผ่าน Storage bucket ที่เปิด public โดยไม่ตั้งใจ**: ปิด public access ของ bucket นั้นทันทีผ่าน Supabase Dashboard (Storage → เลือก bucket → Configuration)
- **ไม่แน่ใจว่าเกิดอะไรขึ้นแต่สงสัยหนัก**: เมื่อไม่แน่ใจ ให้เลือกทางที่ปลอดภัยไว้ก่อนเสมอ (fail-closed) — เช่น หมุนเวียน key ที่เกี่ยวข้องทั้งหมด แม้จะยังไม่ยืนยัน 100% ว่ารั่วจริง เพราะต้นทุนของการหมุนเวียน key เร็วเกินไปน้อยกว่าต้นทุนของการปล่อยให้ผู้บุกรุกใช้ต่อ

หลัง Contain แล้ว **บันทึกว่าทำอะไรไปบ้างและเมื่อไหร่** ต่อจากบันทึกในขั้นตอน Detect ทันที ก่อนไปขั้นตอนถัดไป

### 2.3 Assess (ประเมินผลกระทบ) — ใช้ `audit_log` เป็นเครื่องมือหลัก

หลังควบคุมความเสียหายเบื้องต้นแล้ว ขั้นตอนนี้คือตอบคำถาม: **เกิดอะไรขึ้นบ้าง ใครทำ ทำอะไร กับใคร เมื่อไหร่ กี่ครั้ง**

`public.audit_log` (WYN-048) คือตารางเดียวในระบบที่ถูกออกแบบมาให้เป็น audit trail รวมศูนย์ของ action สิทธิ์สูง — บันทึกทุกครั้งที่มีการ: ดำเนินการ moderation (`moderation_action_applied`), ตัดสินอุทธรณ์ (`appeal_decided`), แอดมินส่งประกาศระบบ (`system_notification_sent`), ลบบัญชี (`account_deleted`), หรือ export ข้อมูล (`data_exported`) แต่ละแถวมี `actor_id` (ใครทำ, เก็บ `actor_username_snapshot` ไว้ด้วยแม้บัญชีนั้นจะถูกลบไปแล้วภายหลัง), `target_id` (ทำกับใคร/อะไร, polymorphic ตาม `event_type`), `detail` (jsonb รายละเอียดเพิ่มเติม), `created_at`

**วิธีเข้าถึง**: `audit_log` ไม่มี RLS policy ให้ client role ใดๆ อ่านได้เลย แม้แต่ `admin`/`moderator` (ตั้งใจ — ดูเหตุผลใน `supabase/schema.sql` ส่วน WYN-048) วิธีเดียวที่เข้าถึงได้ตอนนี้คือ **Founder ผ่าน Supabase Dashboard → SQL Editor** (รันด้วยสิทธิ์ที่ bypass RLS โดยธรรมชาติ) หรือเชื่อมต่อ `psql` ตรงด้วย connection string ระดับ owner — นี่คือข้อจำกัดที่ต้องยอมรับจนกว่า WYN-054 (Admin's Audit Log UI, Phase 7) จะสร้างหน้าจอที่ใช้งานง่ายกว่านี้

Query ที่ใช้บ่อยระหว่างสืบสวน (แก้ `<...>` ตามสถานการณ์จริง):

```sql
-- ดูทุก action ที่เกี่ยวข้องกับผู้ใช้คนหนึ่ง ทั้งตอนเป็นคนทำ (actor) และตอนถูกกระทำ (target)
select * from public.audit_log
where actor_id = '<user-uuid>' or target_id = '<user-uuid>'
order by created_at desc;

-- ดูทุก action สิทธิ์สูงในช่วงเวลาที่คาดว่าเกิดเหตุ (ปรับช่วงเวลาตามที่บันทึกไว้ในขั้นตอน Detect)
select * from public.audit_log
where created_at between '<start-timestamp>' and '<end-timestamp>'
order by created_at asc;

-- สงสัยว่าบัญชี admin/moderator คนหนึ่งถูกยึด -- ดูว่าเขาทำอะไรไปบ้างตั้งแต่เมื่อไหร่
select * from public.audit_log
where actor_id = '<suspected-admin-uuid>'
order by created_at desc;

-- ตรวจว่ามีการลบบัญชี/export ข้อมูลผิดปกติจำนวนมากในเวลาสั้นๆ หรือไม่ (สัญญาณของการโจมตีอัตโนมัติ)
select event_type, date_trunc('minute', created_at) as minute, count(*)
from public.audit_log
where event_type in ('account_deleted', 'data_exported')
group by 1, 2
having count(*) > 5
order by 2 desc;
```

**ข้อจำกัดสำคัญที่ต้องรู้ก่อนสรุปผล**: `audit_log` บันทึกเฉพาะ **5 action ที่ผูกไว้ในรอบ WYN-048** เท่านั้น (moderation/appeal/system notification/account deletion/data export) — **ไม่ครอบคลุม** เหตุการณ์การยืนยันตัวตน (login/logout/failed login attempts), การเปลี่ยน `platform_role` โดยตรง (ทำผ่าน SQL ตรงเท่านั้นตาม guard ใน WYN-029, ไม่มี RPC ไม่มี log), หรือการอ่านข้อมูลทั่วไปที่ไม่ใช่ 5 action ข้างต้น ถ้าสงสัยเรื่อง login/session ให้ตรวจ **Supabase Dashboard → Authentication → Logs** เพิ่มเติมเสมอ อย่าสรุปว่า "ไม่มีร่องรอยใน `audit_log`" แปลว่า "ไม่มีอะไรเกิดขึ้น"

จากผลการ query ให้สรุปเป็นข้อมูล 4 อย่างก่อนไปขั้นตอนถัดไป: **ใครได้รับผลกระทบ (รายชื่อ/จำนวน user), ข้อมูลอะไรที่เกี่ยวข้อง, ผลกระทบรุนแรงแค่ไหน (อัปเดตระดับ S0/S1/S2 จากข้อ 1 ถ้าจำเป็น), และเหตุการณ์จบแล้วหรือยังดำเนินอยู่**

### 2.4 Notify (แจ้งผู้เกี่ยวข้อง)

**แจ้ง Founder ทันทีเสมอ** ไม่ว่าระดับความรุนแรงจะเป็นเท่าไหร่ — ใช้ช่องทางเดียวกับที่ `RULES.md` กำหนดไว้สำหรับคำถามสำคัญ (push notification + สรุปสั้นกระชับ) พร้อมข้อมูลอย่างน้อย: เกิดอะไรขึ้น (สรุป 1-2 ประโยค), ระดับความรุนแรง, Contain ไปถึงไหนแล้ว, ต้องการการตัดสินใจอะไรจาก Founder หรือไม่ (เช่น อนุมัติแก้ schema แบบเร่งด่วน)

**แจ้งผู้ใช้ที่ได้รับผลกระทบ — เมื่อจำเป็นตามกฎหมายเท่านั้น**: การตัดสินว่า "จำเป็นตามกฎหมาย" หรือไม่ (เช่น ภายใต้ พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล/PDPA ของไทย ซึ่งมีกรอบเวลาแจ้งเหตุที่ชัดเจนสำหรับกรณีข้อมูลรั่วไหลที่มีความเสี่ยงสูง) **ต้องผ่านการตรวจสอบโดยผู้เชี่ยวชาญกฎหมายก่อนเสมอ** — เอกสารนี้ไม่ใช่คำแนะนำทางกฎหมาย ห้ามตัดสินใจเรื่องนี้เองโดยไม่ปรึกษาก่อน (มิเรอร์แนวทางเดียวกับที่ `platform_documents` ของ WYN-046 ทำไว้แล้ว: เนื้อหากฎหมายจริงต้องรอผู้เชี่ยวชาญตรวจสอบ ไม่ใช่ AI เขียนเอง) ระหว่างรอคำแนะนำทางกฎหมาย ให้เตรียมข้อมูลไว้ล่วงหน้า (รายชื่อ/จำนวนผู้ใช้ที่ได้รับผลกระทบจากขั้นตอน Assess, ข้อมูลอะไรรั่วไหล, ทำอะไรไปแล้วเพื่อแก้ไข) เพื่อให้พร้อมแจ้งได้ทันทีที่มีคำแนะนำ

ตอนนี้ WYN ยังไม่มี production/ผู้ใช้จริง ดังนั้นหัวข้อนี้ยังไม่เคยถูกใช้จริง — เตรียมไว้ให้พร้อมสำหรับตอนที่ launch แล้ว

### 2.5 Remediate (แก้ไข)

หลัง Contain แล้ว (หยุดเลือดได้แล้ว) และ Assess แล้ว (รู้ผลกระทบครบแล้ว) ขั้นตอนนี้คือแก้ที่ต้นเหตุถาวร ผ่าน flow ปกติของทีม (`WORKFLOW.md`):
1. ถ้าเป็นช่องโหว่ในโค้ด/schema — ส่งต่อ **AI Debug Engineer** เพื่อ reproduce + หา root cause + fix เหมือนบั๊กทั่วไป แต่ **ระบุชัดว่าเป็น security incident** ในรายงาน (ไม่ใช่แค่ P0 ปกติ) เพื่อให้ QA รอบถัดไปตรวจ scope กว้างขึ้น (ไม่ใช่แค่เคสเดิม แต่ต้องหาว่ามีจุดอื่นที่มี pattern เดียวกันหรือไม่ — ดู `WORKFLOW.md`'s "Regression Test Memory")
2. Fix ต้องมี **regression test ถาวร** พิสูจน์ว่าช่องโหว่นี้ปิดจริง (red → green) ตาม pattern ที่โปรเจกต์นี้ทำอยู่แล้วทุกจุด (`supabase/tests/*.sh`)
3. ผ่าน **AI QA & Security** ยืนยันก่อน deploy เสมอ — **ห้ามข้าม QA แม้จะเป็นเหตุฉุกเฉิน** (ยกเว้น Contain แบบชั่วคราวที่ย้อนกลับได้ในข้อ 2.2 ซึ่งไม่ใช่การ deploy fix ถาวร)
4. ถ้า Contain ทำสิ่งที่ต้องคืนสภาพภายหลัง (เช่น ปิดฟีเจอร์ชั่วคราว, revoke execute ตรงๆ) ให้เปิดกลับเมื่อ fix ถาวรผ่าน QA และ deploy แล้วเท่านั้น

### 2.6 Post-mortem (สรุปบทเรียน)

บันทึกที่ **`.wyn/learning/`** เสมอ ตาม `WORKFLOW.md`'s "Continuous Self-Improvement" — ใช้ 5 ไฟล์เดิมที่มีอยู่แล้ว ไม่สร้างไฟล์ใหม่แยกสำหรับ incident โดยเฉพาะ:
- **`.wyn/learning/RETROSPECTIVE.md`**: บันทึก timeline เต็มของ incident นี้ (Detect → Contain → Assess → Notify → Remediate เกิดขึ้นเมื่อไหร่ ใช้เวลาเท่าไหร่แต่ละขั้น) + คำตอบ 8 ข้อของ Continuous Self-Improvement (อะไรทำได้ดี/อะไรผิดพลาด/สาเหตุ/ควรปรับปรุงอะไร ฯลฯ)
- **`.wyn/learning/LESSONS_LEARNED.md`**: บทเรียนที่สรุปเป็นหลักการทั่วไป (ไม่ใช่แค่รายละเอียดเคสนี้) ที่ทีมในอนาคตต้องรู้
- **`.wyn/learning/MISTAKES.md`**: ถ้า incident นี้เกิดจากความผิดพลาดของทีม (เช่น ลืม RLS policy, เผลอ commit secret) บันทึกไว้ชัดเจนเพื่อกันไม่ให้เกิดซ้ำ
- **`.wyn/learning/PATTERNS.md`**: ถ้าพบ pattern การป้องกันใหม่ที่ควรใช้ซ้ำ (เช่น RLS pattern ใหม่, guard function ใหม่) บันทึกไว้ให้ task ถัดไปอ้างอิงได้
- **`.wyn/learning/IMPROVEMENTS.md`**: ข้อเสนอปรับปรุง process/checklist/workflow จาก incident นี้ (เช่น "ควรมี automated alert เมื่อ X เกิดขึ้น" — แม้ตอนนี้ยังไม่มี infra รองรับ ก็บันทึกไว้เป็น roadmap item)

Post-mortem ต้อง **ไม่กล่าวโทษบุคคล** (blameless) — เป้าหมายคือหาว่า process/ระบบตรงไหนที่ปล่อยให้เกิดเหตุนี้ได้ ไม่ใช่หาว่าใครทำผิด

## 3. Checklist สรุปย่อ (ใช้ระหว่างเกิดเหตุจริง)

```
[ ] 1. Detect: บันทึกเวลา+สิ่งที่สังเกตเห็น+ระดับความรุนแรงเบื้องต้น (S0/S1/S2)
[ ] 2. Contain: หยุดความเสียหายที่กำลังดำเนินอยู่ (rotate key / revoke session / ปิด RPC ชั่วคราว / ปิด public bucket ตามประเภทเหตุการณ์)
[ ] 3. Assess: query audit_log (+ Supabase Auth Logs ถ้าเกี่ยวกับ login/session) สรุปผู้ได้รับผลกระทบ/ข้อมูลที่เกี่ยวข้อง/ความรุนแรงจริง
[ ] 4. Notify: แจ้ง Founder ทันที (ทุกกรณี) -- แจ้งผู้ใช้เฉพาะเมื่อผู้เชี่ยวชาญกฎหมายยืนยันว่าจำเป็น
[ ] 5. Remediate: ส่งต่อ AI Debug Engineer -> fix + regression test -> AI QA & Security ยืนยัน -> Deploy ตาม WORKFLOW.md ปกติ (ห้ามข้าม QA)
[ ] 6. Post-mortem: บันทึกที่ .wyn/learning/ (RETROSPECTIVE/LESSONS_LEARNED/MISTAKES/PATTERNS/IMPROVEMENTS ตามที่เกี่ยวข้อง) แบบ blameless
```

## 4. ข้อจำกัดปัจจุบันที่ต้องยอมรับ (จนกว่าจะมีคำสั่งเปลี่ยนแปลง)

- ไม่มีระบบ monitoring/alerting อัตโนมัติ — การตรวจพบ (Detect) ต้องพึ่งคนสังเกตเอง
- ไม่มี Admin UI สำหรับดู `audit_log` (รอ WYN-054, Phase 7) — เข้าถึงได้ผ่าน SQL โดยตรงเท่านั้น
- ไม่มี on-call rotation หรือทีมตอบสนองหลายคน — Founder คือจุดติดต่อหลักจุดเดียวตอนนี้
- `audit_log` ครอบคลุมเฉพาะ 5 action ที่ระบุไว้ในหัวข้อ 2.3 เท่านั้น ไม่ใช่ audit trail ครอบคลุมทุกกิจกรรมในระบบ
- ยังไม่มีนโยบาย data retention สำหรับ `audit_log` เอง (ตั้งใจให้โตขึ้นเรื่อยๆ ไม่มี auto-cleanup ตามที่ WYN-048's Product spec ระบุไว้ — ถ้าข้อมูลโตมากในอนาคต Founder อาจต้องตัดสินใจเรื่อง retention policy แยกต่างหาก)

เอกสารนี้ควรทบทวน/ปรับปรุงทุกครั้งที่มี incident จริงเกิดขึ้น (ผ่าน Post-mortem หัวข้อ 2.6) และทุกครั้งที่ระบบมี infra ใหม่ที่เปลี่ยนข้อจำกัดข้างต้น (เช่น เมื่อ WYN-054 เพิ่ม Admin UI ให้กลับมาแก้หัวข้อ 2.3/4 ให้ตรงกับความเป็นจริงใหม่)
