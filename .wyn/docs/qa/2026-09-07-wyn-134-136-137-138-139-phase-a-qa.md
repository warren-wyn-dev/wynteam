### Bug Finding #1 (non-blocking) — `preview_club_invite_link()` returns 0 rows instead of `status = 'not_found'` for a nonexistent code, once any invite link exists anywhere in the database

**Reproduction:** with `club_invite_links` completely empty, `select * from preview_club_invite_link('bogus')` correctly returns 1 row with `status = 'not_found'`. As soon as **any** row exists in `club_invite_links` — for any club, not just the one being queried — the same call for a genuinely non-matching code returns **0 rows** instead. Confirmed independently and reproducibly via direct SQL (see `CHECK11a`/`CHECK11b` in `supabase/tests/wyn_136_club_invite_link_test.sh`, and manually isolated in a scratch DB).

**Root cause:** the RPC's SQL uses a `right join (select p_code as code) req on true` trick intended to always produce a fallback row when no link matches. `on true` means every row in `club_invite_links` is considered "matched" to the single `req` row regardless of its `code`, so the "preserve the unmatched right-hand row" behavior of `RIGHT JOIN` only actually triggers when the *entire table* has zero rows (nothing to match against at all) — not when the table has rows but none of them share this specific `code`. The subsequent `where l.code = req.code or l.code is null` then filters out every row (since `l.code` is `NOT NULL`), leaving an empty result set instead of the intended `not_found` row.

**Why this is Low severity, not blocking:** `ClubRepository.previewInviteLink()` (`app/lib/features/club/data/club_repository.dart`) already defends against an empty RPC result:
```dart
final rows = await _client.rpc('preview_club_invite_link', ...) as List<dynamic>;
final row = rows.isEmpty ? null : rows.first as Map<String, dynamic>;
if (row == null) {
  return const ClubInvitePreview(status: ClubInviteLinkStatus.notFound);
}
```
and `ClubInvitePreviewScreen` renders a friendly Thai message ("ไม่พบลิงก์เชิญนี้") for `notFound` — so **real users opening a mistyped/dead invite link see exactly the correct graceful UI today**, and no Acceptance Criterion is violated (the AC list only explicitly requires graceful handling of expired/revoked/exhausted, all 3 of which work correctly at the RPC layer per CHECK9/CHECK10/CHECK8 above). This is a latent defect against the RPC's own documented return contract (its own comment lists `'not_found'` as one of the values it returns), not a user-facing bug — but it's fragile: any other future consumer of this RPC (an admin/insights tool building on `club_invite_link_uses`, a direct integration test, a future web client) that doesn't happen to replicate this exact defensive `isEmpty` check would break or crash on a bad code.

**Recommended fix** (left in place as a comment directly above `CHECK11` in the new test script for whoever picks this up): replace the `right join ... on true` trick with an explicit `union all` fallback, e.g. `select ... from club_invite_links where code = p_code union all select 'not_found', null, null, null, null where not exists (select 1 from club_invite_links where code = p_code) limit 1`, so a row is returned unconditionally.

**Recommendation:** fast-follow fix, not a deploy blocker. `supabase/tests/wyn_136_club_invite_link_test.sh` will keep failing CHECK11a/CHECK11b until this is patched — this is intentional (a real regression trigger for the fix), not a flaky test.

### Other findings

Minor (informational only, not a bug): `redeem_club_invite_link()`'s `use_count`/`club_invite_link_uses` attribution bookkeeping increments any time a given user redeems a given link for the first time — including a user who was already an `approved` member of the club through some other path before ever clicking this particular link. Worth a one-line comment correction whenever the future Owner Insights UI for this data gets built, not urgent.
