## 2. POST หลายรูป (ข้อ 3) — ปัญหาจริงข้อที่ 5

**คำสั่ง Founder (2026-09-03):** *"โพสต์ รูปต้องเรียงกันเป็นการ์ดนะ แล้วก็รูปที่ 2 ก็โผล่นิดเดียว"*

**สถานะก่อนหน้า: Feed ถูกแล้ว Detail ไม่ถูก**

| จอ | ก่อน |
|---|---|
| Home feed | `ListView` แนวนอน การ์ด 82% ของแถว 4:5 มุมโค้ง 16 ระยะห่าง 8 รูปถัดไปโผล่ที่ขอบ ✅ |
| **Post Detail** | **`PageView` เต็มความกว้าง ทีละรูป — ไม่ใช่การ์ด ไม่มีรูปถัดไปโผล่** ❌ |

โพสต์เดียวกันจึงเป็นการ์ดเรียงกันใน Feed แล้ว **กลายเป็นแผ่นเดียวทันทีที่กดเข้าไปดู**
เป็นความไม่สม่ำเสมอชนิดเดียวกับเรื่องสัดส่วนรูปใน §3 แค่คนละมิติ

**แก้:** ทั้งสองจอสร้างจาก widget ตัวเดียวกัน `PostImageCarousel` ใน `core/widgets/post_media.dart`

* `postCardWidthFraction = 0.82` · `postCardAspectRatio = 4/5` · มุมโค้ง `radiusLg` (16) · ระยะห่าง `space2` (8)
* บนจอกว้าง 390pt: การ์ดกว้าง **320pt** เว้น 8pt แล้วรูปที่ 2 โผล่ **ราว 62pt** — พอให้รู้ว่ามีรูปต่อ ไม่ถึงกับอ่านเป็นสองรูปคู่กัน คือ "โผล่นิดเดียว" ตามที่สั่ง
* **Feed ไม่เปลี่ยนรูปทรงเลยแม้แต่ค่าเดียว** — เปลี่ยนแค่ว่าไปเรียก widget ที่ใช้ร่วมกันแทนโค้ดของตัวเอง
* Detail ยังมีตัวนับ "1/3" และจุดบอกตำแหน่ง — ย้ายมาวางทับแถวแทนที่จะผูกกับ `PageView.onPageChanged`
  ตำแหน่งปัจจุบันคำนวณจาก scroll offset (`(offset / (การ์ด + ระยะห่าง)).round()`) จึงยังทำงานได้โดยไม่ต้องทำให้แถว snap
* **แถว snap ทีละการ์ด** ทั้ง Feed และ Detail (คำสั่ง Founder 2026-09-03: *"ให้ snap ทีละการ์ดเลย"*)
  เดิมเลื่อนอิสระ (WYN-092) จึงจอดโดยมีการ์ดค้างครึ่งขอบได้บ่อย ๆ — ตอนนี้รูปจะเป็น "รูปที่กำลังดู"
  หรือ "รูปที่โผล่" เสมอ ไม่มีสถานะที่สามค้างอยู่ตรงกลาง

**วิธี snap:** `_CardSnapPhysics` — snap ไปที่ผลคูณของ *stride* (การ์ด + ระยะห่าง)

* ใช้ `PageScrollPhysics` ไม่ได้ เพราะมัน snap ทีละ **viewport เต็ม** ไม่ใช่ทีละการ์ด 82%
* ใช้ `PageView` + `viewportFraction` ก็ได้ แต่ต้องยัดระยะห่าง 8 เข้าไปใน fraction ทำให้ความกว้างการ์ด
  ขึ้นกับระยะห่าง แล้วเพี้ยนจาก 82% ที่ design ระบุไว้ — snap ที่ stride ทำให้ทั้งสองค่าเป็นตัวเลขที่มันบอกจริง ๆ
* **ปัดเด็ดขาดเลื่อน 1 การ์ดพอดีเสมอ ไม่ว่าจะปัดแรงแค่ไหน** — โพสต์ 9 รูปจึงยังเป็นลำดับรูปที่ดูได้ ไม่ใช่ภาพเบลอที่ไปหยุดที่ไหนก็ไม่รู้
* ลากช้า ๆ → จอดที่การ์ดใกล้ที่สุดตอนปล่อยนิ้ว
* เลยปลายแถวทั้งสองข้าง → ปล่อยให้ parent physics จัดการ (clamp / bounce) ไม่ไป snap ทับ

**Test:** ลากสั้นกว่าครึ่งการ์ด → กลับที่เดิม · ลากเลยครึ่ง → จอดที่ stride พอดี ·
ปัดแรง 6000 → เลื่อน **1 การ์ด ไม่ใช่ 3** · การ์ดสุดท้ายไม่เลยปลายแถว ·
`onIndexChanged` รายงานถูกทั้งไปและกลับ — **ยืนยันแล้วว่า test พังถ้าเอา physics ออก**

**Test:** `drop_image_gallery_test.dart` ยืนยันว่า Detail ไม่มี `PageView` แล้ว มี `PostImageCarousel`
การ์ดแรกกว้าง 82% ของแถวจริง สัดส่วน 4:5 จริง และส่วนที่โผล่ **น้อยกว่า 1 ใน 3 ของการ์ด**

## 3. IMAGE LAYOUT (ข้อ 4) — ปัญหาจริงข้อที่ 1

**อาการที่ Founder รายงาน:** *"รูปในหน้า Post / Post Detail แสดงไม่เหมือนรูปใน Profile และไม่มีมาตรฐานเดียวกัน"*

**ต้นตอที่พบ:** สามจอมีคำตอบของตัวเองคนละคำตอบ

| จอ | ก่อน |
|---|---|
| `HomeDropCard` | สัดส่วนจริง clamp 4:5..1.91:1 (WYN-093) |
| `HomeFeedImagePeekCarousel` | **คัดลอกฟังก์ชัน clamp เดียวกันไปไว้เป็นสำเนาส่วนตัว** พร้อมคอมเมนต์ว่า "ไม่คุ้มที่จะ export มาใช้ร่วมกัน" |
| `DropImageGallery` (Detail) | **ไม่สนใจ dimension เลย — `AspectRatio(1)` + `BoxFit.cover` ตายตัว** |

ผลคือ: รูปตั้ง 4:5 (สัดส่วนกล้องมือถือที่เจอบ่อยที่สุด) ที่ Feed แสดงเต็ม **หายหัวหายท้ายทันทีที่กดเข้าไปดู**
รูปเดียวกัน ครึ่งเดียวหายไป บนหน้าจอเดียวที่มีหน้าที่แสดงมัน

**แก้:** ย้ายกติกาไปอยู่ที่เดียว `app/lib/core/widgets/post_media.dart`

```
postImageAspectRatio(w, h)  →  clamp(w/h, 0.8, 1.91)  หรือ 1.0 ถ้าไม่รู้ขนาด
PostImage                   →  Image.network + cacheWidth + placeholder/error
PostImageFrame              →  ratio + เพดานความสูง + PostImage
```

| จอ | หลัง |
|---|---|
| Home feed รูปเดียว | `PostImageFrame` เพดาน 75% ของจอ |
| Peek carousel | `PostImage` (รูปทรง 82%/4:5 ของ carousel เหมือนเดิม) + fallback ใช้ `PostImageFrame` |
| Post Detail รูปเดียว | `PostImageFrame` เพดาน **85%** ของจอ |
| Post Detail หลายรูป | `PageView` ในสัดส่วนเดียวกัน เพดาน 85% |
| Profile — โพสต์/รีโพสต์/ถูกใจ | ใช้ `HomeDropCard` ตัวเดียวกับ Feed อยู่แล้ว ได้ทุกอย่างที่ Feed ได้ |
| Search แท็บโพสต์ / Saved / Draft | Grid 3 คอลัมน์จัตุรัสเหมือนเดิม ไม่แตะ |
| Club post | 1:1 เหมือนเดิม (`club_posts` ไม่เก็บ dimension เลย ไม่มีอะไรให้คำนวณ) แก้เฉพาะการ decode |

**ทำไม Detail ได้ 85% แต่ Feed ได้ 75%:** Detail คือหน้าที่มีโพสต์เดียวอยู่บนจอ รูปตั้งจึงกินพื้นที่ได้มากกว่า
แต่ยังต้องมีเพดาน เพื่อให้ caption ด้านบนและแถบ action ด้านล่างไม่ถูกดันหายไปจากจอสูง ๆ

**เจตนาที่รักษาไว้ตามข้อ 4:** *"ไม่ต้องทำให้ทุกหน้าเหมือนกัน 100% ให้แต่ละบริบทเหมาะสมกับหน้าที่"*
Grid ที่ยังเป็น Grid คือ Search แท็บโพสต์, Saved และ Draft — เป็น Content Overview คนละหน้าที่กับ Content Flow

⚠️ **แก้ข้อผิดพลาดของเอกสารฉบับก่อน (2026-09-03):** เอกสารรุ่นแรกและ artifact ที่ส่งให้ Founder
เขียน/วาดว่า "Profile เป็น Grid" — **ผิด** แท็บหลักทั้งสามของ Profile (โพสต์ / รีโพสต์ / ถูกใจ)
เป็น `ListView` ของ `HomeDropCard` เหมือน Feed มาตั้งแต่ WYN-013 แล้ว ตัวที่เป็น Grid จริงคือ
Search แท็บโพสต์, Saved และ Draft ซึ่งเป็นคนละที่กัน

## 4. POST DETAIL SCROLL (ข้อ 5) — ปัญหาจริงข้อที่ 2

**อาการที่ Founder รายงาน:** *"เปิด Post แล้วเห็น Post แค่ประมาณครึ่งเดียว และส่วน Profile / Content ด้านบนเหมือนกินพื้นที่จนไม่สามารถเลื่อนขึ้นไปใช้พื้นที่ได้เต็มที่"*

พบว่ามี **สองสาเหตุแยกกัน** ที่รวมกันแล้วให้อาการเดียว:

**สาเหตุที่ 1 — รูปโดนตัดครึ่งจริง ๆ** คือ §3 ข้างบน "เห็นแค่ครึ่งเดียว" ในความหมายตรงตัว

**สาเหตุที่ 2 — แถบหัวข้อตรึงอยู่ตลอด**
ข้อกำหนดของ Founder เขียนว่า *"ทุกส่วนของ Post Detail อยู่ใน Scroll Container เดียวกัน"* — ตรวจแล้วพบว่า **เนื้อโพสต์กับคอมเมนต์อยู่ใน scroll เดียวกันอยู่แล้ว** (`ListView(children: [header, ...comments])` มีมาตั้งแต่ WYN-004) ไม่มี nested scroll ไม่มี scroll ซ้อน

สิ่งที่ยังตรึงคือ `Scaffold appBar:` — แถบ "โพสต์" สูงราว 57px ที่หน้านี้ไม่เคยได้คืน
ข้อ 5 ห้ามไว้ตรง ๆ ว่า *"ห้ามทำ Header/Content ด้านบน fixed โดยไม่จำเป็น"*

**แก้:** แถบหัวข้อกลายเป็น `SliverAppBar(floating: true, snap: true)` **ภายใน scroll view เดียวกับโพสต์**
เลื่อนลง → แถบหายไปพร้อมหัวโพสต์ · ปัดขึ้นนิดเดียว → กลับมาทันที
`ListView` เดิมทั้ง 3 สาขา (error / loading / โหลดเสร็จ) กลายเป็น `CustomScrollView` + `SliverList`
ใช้ `SliverChildListDelegate` เพราะ children ถูกสร้างล่วงหน้าอยู่แล้วเหมือนที่ `ListView(children:)` ทำมาตลอด — **เปลี่ยนโครงสร้าง scroll ไม่ได้เปลี่ยนว่าสร้างอะไร**

**สิ่งที่ยังตรึงโดยตั้งใจ:** ช่องพิมพ์คอมเมนต์ด้านล่าง — ช่องพิมพ์ที่ต้องเลื่อนหาคือปัญหาที่แย่กว่าพื้นที่ที่ได้คืน

## 5. BACK NAVIGATION (ข้อ 6, 15, 17) — ปัญหาจริงข้อที่ 3

ตรวจทุก call site ที่ push `DropDetailScreen` แล้วดูว่าเกิดอะไรตอน pop กลับมา:

| จอ | ก่อน | สถานะ |
|---|---|---|
| Home feed | `_refreshRow(item)` — แถวเดียว | ✅ ถูกต้องอยู่แล้ว (Beta2) |
| Notifications | ไม่ทำอะไร | ✅ ถูกต้องอยู่แล้ว |
| Search แท็บโพสต์ | ไม่ทำอะไร | ✅ ถูกต้องอยู่แล้ว |
| Bookmarks | ไม่ทำอะไร | ✅ ถูกต้องอยู่แล้ว |
| **Profile แท็บโพสต์** | `_loadInitial()` | ❌ **โหลดใหม่ทั้งลิสต์** |
| **Profile แท็บรีโพสต์** | `_loadInitial()` | ❌ **โหลดใหม่ทั้งลิสต์** |
| **Profile แท็บถูกใจ** | `_loadInitial()` | ❌ **โหลดใหม่ทั้งลิสต์** |
| **Hashtag feed** | `_load()` | ❌ **ค้นหาใหม่ทั้งชุด** (ทั้ง Drop และ Club post) |

`_loadInitial()` เซ็ต `_isLoadingInitial = true` → `build` คืน `CircularProgressIndicator` แทนลิสต์ทั้งอัน
→ `ListView` ถูก unmount → ตำแหน่ง scroll หายไปกับมัน → ทุกหน้าที่ page มาแล้วถูกทิ้ง → เริ่มจากหน้า 0 ใหม่

**คือ Scenario D ของ Founder ตรง ๆ:** เปิดโพสต์ที่ 30 ในโปรไฟล์ใครสักคน กด Back แล้วโพสต์นั้นอยู่ไกลลงไปข้างล่าง

**แก้:** ทั้ง 4 จอรีเฟรช **แถวเดียว** ตามแบบที่ Home ทำอยู่แล้ว (`fetchById` / `fetchItemById`)

* แถวที่หายไปจากเซิร์ฟเวอร์ (ถูกลบจากหน้า Detail) → ถูกเอาออกจากลิสต์
* แท็บ "ถูกใจ" มีกติกาเพิ่มหนึ่งข้อ: ถ้า unlike จากหน้า Detail แถวนั้นไม่ควรอยู่ในแท็บ "ถูกใจ" อีกต่อไป → เอาออก
* refresh ที่ล้มเหลว → ปล่อยแถวไว้เหมือนเดิม (ตัวเลขเก่ากว่าความจริงเป็นปัญหาที่เล็กกว่าลิสต์ที่ว่างเปล่าเพราะ request timeout)
* `ProfileRedropsTab` หาแถวด้วย key ประกอบ `id:redropId` ไม่ใช่ `id` เพราะ Drop เดียวอยู่ในลิสต์ได้ 2 ครั้ง

**ที่รักษาไว้ครบตามข้อ 6:** scroll position, feed state, loaded posts, pagination state, filter state
ไม่มี jump to top, ไม่มี reset scroll, ไม่มี skeleton แสดงใหม่, ไม่กระพริบ

## 6. INFINITE SCROLL (ข้อ 8) — ปัญหาจริงข้อที่ 4 (P1)

Pagination ทั้งระบบเป็นแบบ **offset** — `range(from, to)`
ถ้ามีแถวเพิ่มที่หัวลิสต์ระหว่างที่ผู้ใช้กำลังเลื่อน ทุกอย่างเลื่อนลง 1 → แถวสุดท้ายของหน้า N กลับมาเป็นแถวแรกของหน้า N+1

`HomeFeedScreen` กันไว้แล้วด้วย `_seenKeys` และเขียนเหตุผลไว้ในคอมเมนต์ของตัวเอง
**อีก 4 ลิสต์ไม่เคยได้รับการกันเลย ทั้งที่ทั้ง 4 ใส่ `ValueKey` ให้แถว**

| ลิสต์ | key ที่ใช้ |
|---|---|
| Profile แท็บโพสต์ | `ValueKey(drop.id)` |
| Profile แท็บถูกใจ | `ValueKey(drop.id)` |
| Profile แท็บรีโพสต์ | `ValueKey('${id}:${redropId}')` |
| Bookmarks | `ValueKey(item.id)` |

**ผลไม่ใช่แค่ "แสดงซ้ำ"** — `ValueKey` ซ้ำสองอันใน `ListView` เดียว Flutter ปฏิเสธตรง ๆ: **ลิสต์ throw**
เป็นบั๊กระดับ P1 ที่ซ่อนอยู่ ไม่ใช่ปัญหาความสวยงาม

**แก้:** ทั้ง 4 ลิสต์ใช้ `_seenKeys` แบบเดียวกับ Home
`_hasMore` ยังตัดสินจากสิ่งที่เซิร์ฟเวอร์ตอบกลับ ไม่ใช่จากสิ่งที่รอดจากการกรอง — หน้าที่เต็มแต่ซ้ำทั้งหน้าก็ยังแปลว่ามีอีก

**Test:** `profile_likes_tab_test.dart` ยิงหน้า 1 ที่ทับกับหน้า 0 จริง แล้วนับว่าแถวที่คาบเกี่ยวขึ้นกี่ครั้ง
**ยืนยันแล้วว่า test นี้ fail ถ้าเอา guard ออก** — ไม่ใช่ test ที่ผ่านอยู่แล้วโดยบังเอิญ

## 7. FEED EXPERIENCE (ข้อ 7) — ไม่แตะ

Vertical social feed แบบ card ต่อกันลงมา ถูกต้องอยู่แล้ว
`RefreshIndicator` + new-posts pill + infinite scroll + 3 โหมด (สำหรับคุณ / ติดตาม / จาก Club) ครบ

---

## 8. LIKE / COMMENT / SHARE (ข้อ 13) — ตรวจแล้ว ไม่พบปัญหา

`HomeFeedScreen` ทำ optimistic update ถูกต้องอยู่แล้ว และมีอย่างหนึ่งที่ดีกว่ามาตรฐาน: `_serializeWrite()`

จัดคิว write ต่อแถวต่อ action ไม่ให้ทับกัน — like/unlike/like รัว ๆ 3 ครั้งยังส่งครบ 3 คำสั่ง แต่ **ไม่ซ้อนกัน** จึงไม่มีกรณีที่ INSERT ที่สองชน primary key แล้วทำให้การ์ด rollback ทั้งที่ like บันทึกไปแล้ว

Profile 3 แท็บ / hashtag feed ใช้ optimistic + rollback แบบตรง ๆ (ไม่มี serialize) ซึ่งพอเพียงในบริบทที่ไม่ได้กดรัว

* ✅ กด Like แล้ว UI ตอบสนองทันที · ✅ Unlike ถูกต้อง · ✅ rollback เมื่อ fail · ✅ ไม่ยิงซ้ำ

---

## 9. FOLLOW SYSTEM (ข้อ 14) — ตรวจแล้ว ไม่พบปัญหา

Follow / Unfollow / Follow Request (approve, reject, cancel) / Remove follower / Block / Unblock / Mute / Unmute
ทุกจุดโหลด state จริงจากเซิร์ฟเวอร์ก่อน แล้วซ่อนปุ่มไว้จนกว่าจะรู้สถานะจริง (`_isFollowing` เป็น `bool?` ปุ่มถูกซ่อนตอน `null` — ตั้งใจแก้ไปแล้วตอน WYN-008) จึงไม่เคยแสดงสถานะผิดชั่วขณะ

## 10. PROFILE (ข้อ 15) — และ "โปรไฟล์ต้องคล้ายฟีด"

**คำสั่ง Founder (2026-09-03):** *"โปรไฟล์ ก็ต้องคล้ายฟีดดิ (โพสต์)"*

**ตรวจแล้ว: หน้าตาเหมือน Feed อยู่แล้ว — แต่พฤติกรรมยังไม่เหมือน**

แท็บหลักทั้งสาม (โพสต์ / รีโพสต์ / ถูกใจ) เป็น `ListView.separated` ของ `HomeDropCard`
**ตัวเดียวกับที่ Feed ใช้** มาตั้งแต่ WYN-013 — โครงสร้าง Profile → Text → Media → Actions
เหมือนกันทุกอย่าง รวมถึงแถวการ์ดรูปหลายรูปที่ snap และสัดส่วนรูปที่ Beta3 แก้ไป

**ช่องที่ยังไม่เหมือน และแก้แล้ว:** แท็บพวกนี้สร้างการ์ดจาก `Drop` ธรรมดา ซึ่งไม่เคยพกรายการรูปมาด้วย
โพสต์หลายรูปบนโปรไฟล์จึงยัง**ยิง request รูปของตัวเองทีละการ์ด** — N+1 ตัวเดียวกับที่ Beta3
เอาออกจาก Home ไปแล้ว ตอนนี้ `DropRepository._fetchViewerState` batch รูปทั้งหน้าใน query เดียว
เหมือนที่ `HomeRepository` ทำ จึงครอบคลุมพร้อมกัน: **Profile แท็บโพสต์ + แท็บถูกใจ · Search แท็บโพสต์ ·
hashtag feed · Draft · และ `fetchById` ที่อยู่เบื้องหลังทุกครั้งที่กลับจาก Detail**
(แท็บรีโพสต์ใช้ `HomeRepository` อยู่แล้วจึงได้มาตั้งแต่รอบก่อน)

**Test:** โพสต์ 3 รูปบนแท็บถูกใจ → `fetchDropImages` ถูกเรียก **0 ครั้ง** และแถวการ์ดขึ้นครบตั้งแต่เฟรมแรก

* avatar / username / display name / bio / posts / followers / following / relationship state ✅ ครบ
* **Back จาก Post → กลับตำแหน่งเดิม** ✅ แก้แล้ว (§5)
* Profile ไม่ทำให้ Feed state เสีย ✅ — คนละ tab ใน `IndexedStack` มี state แยกกัน

**หมายเหตุที่ยังไม่แก้:** header ของ Profile ไม่เลื่อนหายไปพร้อม tab content (เป็น `Column` + `Expanded(TabBarView)`)
ต่างจาก Post Detail ที่ Founder สั่งไว้ตรง ๆ — Profile ไม่ได้ถูกกล่าวถึงในข้อ 5 และการเปลี่ยนเป็น `NestedScrollView`
กระทบทั้ง 3 แท็บ + pull-to-refresh + `AutomaticKeepAlive` พร้อมกัน ถือเป็นความเสี่ยง regression ที่ไม่คุ้มถ้า Founder ไม่ได้สั่ง — **บันทึกไว้ใน future ideas รอคำสั่ง**

## 11. SEARCH (ข้อ 16) — ตรวจแล้ว ไม่แตะ

Search เป็น **submit-based** ไม่ใช่ type-ahead: พิมพ์อย่างเดียวไม่ยิง query เลย ต้องกดปุ่มค้นหาหรือปุ่ม search บนคีย์บอร์ด (WYN-080)
จึง **ไม่มี debounce ให้ปรับ และไม่มี duplicate request จากการพิมพ์ตั้งแต่แรก** — ระหว่างพิมพ์จะเห็น DiscoveryView (trending/suggested) ตามที่ Founder เคยสั่งไว้ว่าอยากได้ "ฟิว TikTok"
pagination / loading / empty / error / retry ครบอยู่แล้ว

---

## 12. NOTIFICATIONS (ข้อ 17) — ตรวจแล้ว ไม่แตะ

* pagination, read/unread, loading, navigation, deep link ครบ
* เปิด Notification → เปิด Post → Back: **ไม่ reload อะไรเลย** state ถูกต้องอยู่แล้ว
* remount ทุกครั้งที่กด tab เป็นพฤติกรรมที่ตั้งใจ (initState คือจุดที่ mark-as-read) ไม่ใช่บั๊ก
* โพสต์ที่ถูกลบไปแล้ว → ขึ้น snackbar "โพสต์นี้ถูกลบไปแล้ว" ไม่ใช่จอว่าง ✅

---

## 13. LOADING / ERROR / EMPTY STATE (ข้อ 18–20)

**Loading:** สิ่งที่แก้ใน §5 คือการแก้ loading state ที่แย่ที่สุดในแอปอยู่แล้ว — spinner ที่โผล่มาแทนลิสต์ทั้งอันทุกครั้งที่กด Back
รูปในโพสต์ใช้ placeholder สีเรียบ ไม่ใช่ spinner ทุกที่ตอนนี้ (spinner ที่โผล่แล้วหายทุกแถวขณะเลื่อนคือ noise มากกว่าข้อมูล)

**Error:** ทุก API หลักมีข้อความ + retry อยู่แล้ว — ปรับปรุงของเดิมตามข้อ 19 ไม่ได้สร้างระบบใหม่

**Empty:** ไม่มีโพสต์ / ไม่มีผลค้นหา / ไม่มี notification / ไม่มี follower / following / comment มีข้อความครบทุกกรณี
แท็บ "ถูกใจ" แยกแยะ "ยังไม่มีอะไรถูกใจ" กับ "ไม่ได้รับอนุญาตให้ดู" ต่างหาก (WYN-099) ✅

---

## 14. MOTION (ข้อ 21)

Beta3 **ไม่เพิ่ม animation ใหม่แม้แต่ตัวเดียว** ตามหลัก "Motion มีหน้าที่ช่วย UX ไม่ใช่โชว์เอฟเฟกต์"
สิ่งเดียวที่เกี่ยวกับ motion คือ `SliverAppBar(snap: true)` ซึ่งเป็น motion ของแพลตฟอร์มเอง ไม่ใช่ animation ที่เขียนขึ้น
DoubleTapLike (หัวใจเด้ง), scroll-to-top, RefreshIndicator ที่มีอยู่แล้ว — ไม่แตะ

---

## 15. MOBILE UX (ข้อ 22) และ ACCESSIBILITY (ข้อ 23)

**ตรวจจากโค้ด — ไม่ได้ทดสอบบนอุปกรณ์จริง**

* Safe area: `SafeArea(top: false)` ที่ช่องพิมพ์คอมเมนต์ ✅ · `SystemChrome` ตั้ง overlay style ที่ `main()` ✅
* Keyboard: `resizeToAvoidBottomInset` (ค่าเริ่มต้น true) + ช่องพิมพ์อยู่นอก scroll view ✅
* Touch target: `WynSpacing.touchTargetMin` ใช้ที่ปุ่ม Follow · `IconButton` มี 48dp ของตัวเอง ✅
* Semantics: รูปในโพสต์รับ `semanticLabel` ได้แล้วผ่าน `PostImage` · carousel มี "รูปที่ N จาก M" อยู่แล้ว ✅
* Text overflow: `TextOverflow.ellipsis` ที่ชื่อ/username ทุกจุด ✅

**เพดานความสูงรูปคือเรื่อง mobile UX โดยตรง:** ถ้าไม่มีเพดาน รูปตั้งเต็มจอทำให้ไม่มีสัญญาณว่ามี caption / action bar / โพสต์ถัดไปอยู่ข้างล่าง

## 16. CLUB COVER (ข้อ 12)

**Founder ตัดสินใจ (2026-09-03): ลบเฉพาะที่หน้า Club page**

หน้า Club แสดงพื้นหลัง ink + sapphire ที่ระบบสร้างเองเสมอ ไม่สลับไปเป็น `club.cover_url` อีก
ก่อนหน้านี้หัว Club เป็นคนละดีไซน์กันขึ้นกับว่าเจ้าของเผอิญอัปรูปไว้ไหม และในกรณีที่อัปไว้ **ชื่อ Club หายไปจากแถบนั้นด้วย**

## 17. CRITICAL UX SCENARIOS (ข้อ 29)

| | Scenario | ผล |
|---|---|---|
| A | Feed → เลื่อนลง → เปิด Post → Back | ✅ กลับตำแหน่งเดิม ไม่ refresh ทั้ง feed ไม่ jump top ไม่ duplicate (ถูกต้องตั้งแต่ Beta2 — ตรวจซ้ำแล้ว) |
| B | เปิด Post Detail → เลื่อน | ✅ Profile → Text → Media → Actions → Comments เลื่อนต่อเนื่องกัน + แถบหัวข้อเลื่อนหายได้แล้ว |
| C | โพสต์ 3 รูป | ✅ carousel ปัดซ้ายขวา + ครบทุกรูปตั้งแต่เฟรมแรก (ไม่ต้องรอ request ต่อการ์ด) |
| D | Profile → เปิด Post → Back | ✅ **แก้แล้ว** กลับตำแหน่งเดิม (เดิมโหลดใหม่ทั้งลิสต์) |
| E | Feed → infinite scroll → load more | ✅ ไม่ duplicate / ไม่หาย / ไม่ reorder — และตอนนี้ Profile 3 แท็บ + Bookmarks ก็กันซ้ำแล้วเหมือน Home |
