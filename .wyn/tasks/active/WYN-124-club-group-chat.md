# Feature Request — WYN-124

Status: active — Product spec + Design เสร็จแล้ว (Founder สั่งให้ทำต่อทันที, 2026-09-06: "124 ต่อเลย"), **Coding ยังห้ามเริ่มจนกว่า WYN-115–118 เสร็จครบ**
Owner: AI Product Manager → AI Design

Feature: Club Group Chat — ห้องแชทกลุ่มเรียลไทม์ 1 ห้องต่อ Club (เฟส 2 ของแผน "Club แบบ Discord", ต่อจาก WYN-123 Channels)

Goal: ให้สมาชิก Club คุยกันสดแบบเรียลไทม์ในห้องเดียวกัน — ต่างจากโพสต์+คอมเมนต์ที่มีอยู่แล้ว และต่างจาก Channel ของ WYN-123 (ที่ยังเป็นกลไก "โพสต์" จัดหมวดหมู่ ไม่ใช่พื้นที่คุยสด) — ตรงกับสิ่งที่ Founder ระบุว่าทำให้ Discord "รู้สึกมีชีวิต" ที่สุด

Target User: สมาชิก Club ที่ต้องการพื้นที่พูดคุยสดแบบไม่เป็นทางการ ทันที ไม่ต้องรอคนมาคอมเมนต์ใต้โพสต์

Problem: ระบบแชทปัจจุบัน (WYN-031) รองรับแค่ 1-ต่อ-1 เท่านั้น — ตาราง `public.conversations` เป็น pair table ตายตัว (`user_a_id`/`user_b_id` + `unique(user_a_id, user_b_id)` + `constraint conversations_canonical_order`) ผูกกับคู่ 2 คนโดยโครงสร้าง ใช้กับ group ไม่ได้เลย ต้องสร้างระบบใหม่คู่ขนานที่รองรับ N คนต่อห้อง

## จุดที่เคยตัดสินใจ "รอก่อน" แล้วตอนนี้ตัดสินใจได้แล้ว

Backlog เดิมของงานนี้ (เขียนไว้ก่อนหน้า) เลื่อนการเขียน spec เต็มออกไปเพราะกังวลว่าห้องแชทกลุ่มควรผูกกับ Club ทั้งก้อนหรือผูกกับ Channel ของ WYN-123 — คำถามนั้นตอบได้แล้วโดยไม่ต้องรอดูโค้ด WYN-123 จริง (ดู R1 ด้านล่าง) เพราะเป็นคำถามเชิงหลักการของฟีเจอร์ ไม่ใช่รายละเอียด implementation ของ WYN-123

## Requirements

### R1 — ห้องแชทผูกกับ Club ทั้งก้อน ไม่ผูกกับ Channel
Channel (WYN-123) ยังคงเป็นกลไก "โพสต์ + คอมเมนต์" แค่จัดหมวดหมู่ใหม่ ส่วน Group Chat เป็นพื้นที่คุยสดที่ต่างออกไปโดยสิ้นเชิง (เรียงตามเวลา ไม่มีแนวคิด "โพสต์"/"ปักหมุด") — ผูกห้องแชทกับ Channel จะทำให้ Club ที่มีหลาย Channel ต้องมีห้องแชทหลายห้องตามไปด้วย เพิ่ม complexity โดยไม่มีประโยชน์ชัดเจนตอนนี้ (Founder Brief ข้อ 19 เตือนเรื่องนี้ตรงๆ) — **1 Club = 1 ห้องแชทกลุ่ม เสมอ** สร้างอัตโนมัติตอน Club ถูกสร้าง (Club ที่มีอยู่แล้วก่อน WYN-124 ก็ต้องมีห้องแชทให้อัตโนมัติตอน migrate เหมือนกัน ไม่มี Club ไหนไม่มีห้องแชท) ถ้าอนาคตพบว่าจำเป็นต้องมีหลายห้องต่อ Channel จริง ค่อยขยายทีหลัง — โครงตาราง N-person ที่ออกแบบไว้รองรับได้โดยไม่ต้อง migrate ใหม่ทั้งระบบ

### R2 — สมาชิกที่ approved เข้าห้องแชทได้ทันที ไม่มี Message Request gate
ต่างจาก DM (WYN-031) ที่มี Message Request เพราะเป็นการติดต่อคนแปลกหน้าครั้งแรก — การเป็นสมาชิก approved ของ Club เองคือ gate อยู่แล้ว เข้าห้องแชทได้ทันทีที่เข้าร่วม Club สำเร็จ และเสียสิทธิ์เข้าห้องแชททันทีที่ออกจาก/ถูกเตะออกจาก Club (ไม่เห็นข้อความใหม่หลังจากนั้น)

### R3 — ประเภทข้อความเหมือน DM เดิมทุกอย่าง (reuse ไม่คิดใหม่)
ข้อความตัวอักษร, รูปภาพ, reply-to-message, แชร์เนื้อหา (Drop/Profile/Club) — มิเรอร์ shape ของ `public.messages` เดิมทุกฟิลด์ (`text`/`image_url`/`reply_to_message_id`/`shared_content_type`+`shared_content_id`/soft-delete ผ่าน `deleted_at`) ต่างแค่ปลายทางจาก `conversation_id` (คู่ 2 คน) เป็น room id (กลุ่ม N คน) — ไม่มีเหตุผลให้ประเภทเนื้อหาต่างจาก DM เดิมในรอบนี้

### R4 — Read state แยกต่อสมาชิก ไม่ใช่ 2 คอลัมน์คงที่
WYN-031 เดิมเก็บ `user_a_last_read_at`/`user_b_last_read_at` เป็น 2 คอลัมน์ตายตัวเพราะรู้อยู่แล้วว่ามีแค่ 2 ฝั่ง — ห้องแชทกลุ่มต้องมีตารางแยกต่างหาก 1 แถวต่อ (ห้อง, สมาชิก) เก็บ `last_read_at` ของแต่ละคนเอง เพื่อคำนวณ unread-count ต่อคนได้ถูกต้อง (คนละสถานะกันได้ในเวลาเดียวกัน)

### R5 — Realtime/Push ต้อง fan-out ทุกสมาชิกในห้อง ไม่ใช่แค่ 2 ฝั่ง
ข้อความใหม่ต้อง broadcast ผ่าน Supabase Realtime ถึงสมาชิก online ทุกคนในห้อง (ไม่ใช่ 2 คนแบบ DM) และ push notification (ตอน Firebase พร้อมจริง ตาม pattern ที่ WYN-116 วางไว้แล้ว) ต้อง fan-out เหมือนกัน — Club อาจมีสมาชิกหลักร้อย/พันคน ข้อความเดียวอาจ trigger fan-out หลักร้อย/พันแถว ต่างจาก DM ที่มีผู้รับแค่ 1 คนเสมอ ต้องคำนึงเรื่อง scale ตั้งแต่ตอนออกแบบ schema/trigger

### R6 — Mute ห้องแชทได้ต่อ Club แยกจาก mute อื่น
สมาชิกปิดแจ้งเตือนห้องแชทของ Club หนึ่งได้โดยไม่กระทบแจ้งเตือน DM หรือแจ้งเตือนโพสต์ใหม่/ปักหมุดของ Club เดียวกัน (ซึ่งมี mute ของตัวเองอยู่แล้วจาก WYN-116, `club_notification_mutes`, ครอบคลุมแค่ `club_post_new`/`club_post_pinned`) — ตัดสินใจ: ตารางใหม่แยกต่างหาก **ไม่ใช้ตารางเดียวกับ WYN-116** เพราะเป็นแจ้งเตือนคนละประเภท (ข้อความสดต่อเนื่อง vs โพสต์ใหม่เป็นครั้งคราว) ควรเปิด/ปิดอิสระจากกันได้

### R7 — ไม่มีระบบ @mention รายคนในข้อความแชทรอบนี้ (ตัดออกจาก scope)
คุม complexity ตามที่ Founder Brief เตือนไว้ — ข้อความกลุ่มไม่ต้องมีกลไก mention ที่ trigger แจ้งเตือนพิเศษแยกจาก "มีข้อความใหม่ในห้อง" ปกติ (ต่างจาก `mention_club_post` ที่มีอยู่แล้วสำหรับโพสต์) เพิ่มได้ภายหลังถ้าเห็นความจำเป็นจริงจากการใช้งาน

### R8 — ไม่แตะระบบ DM (1-on-1) เดิมแม้แต่นิดเดียว
งานนี้เป็นตารางใหม่ทั้งชุดคู่ขนานกับ `conversations`/`messages` เดิม (ไม่ใช่เพิ่มคอลัมน์ในตารางเดิม) — ตรงกับที่ WYN-031's design doc เองตัดสินใจแยก scope ไว้ตั้งแต่ต้นด้วยเหตุผลเดียวกัน

## Acceptance Criteria

1. สมาชิกที่ approved ของ Club เปิดห้องแชทกลุ่มได้ทันที ไม่ต้องขอสิทธิ์/รอการอนุมัติเพิ่มเติม
2. ข้อความที่ส่งแล้ว สมาชิก online คนอื่นในห้องเห็นแบบเรียลไทม์โดยไม่ต้อง refresh หน้า
3. ผู้ที่ออกจาก Club แล้ว (leave เอง/ถูกเตะ) เข้าห้องแชทไม่ได้อีกทันที ไม่เห็นข้อความที่ส่งหลังจากนั้น
4. Unread count ของห้องแชทนับถูกต้องต่อสมาชิกแต่ละคนอิสระจากกัน
5. ปิดแจ้งเตือนห้องแชทของ Club หนึ่งไม่กระทบแจ้งเตือน DM หรือแจ้งเตือนโพสต์ของ Club เดียวกันเลย
6. ส่งรูป/reply/แชร์เนื้อหาในห้องแชทกลุ่มได้เหมือน DM ทุกประการ
7. Club ที่มีสมาชิกหลักพันคน ส่งข้อความ 1 อันไม่ทำให้ระบบช้าลงจนสังเกตได้ (fan-out/realtime ต้องพิสูจน์ว่ารองรับ scale นี้จริงตอน QA ไม่ใช่แค่คาดเดา)

## Dependencies

- WYN-031 (DM 1-on-1) — ต้นแบบ message shape (`text`/`image_url`/`reply_to`/`shared_content`) reuse โครงสร้างเดียวกัน แต่เป็นตารางใหม่แยกขาด ไม่แก้ของเดิม
- WYN-116 (Club Re-engagement Notification) — ต้นแบบ pattern การ mute ต่อ Club (`club_notification_mutes`) สำหรับ R6 (คนละตารางแต่ pattern เดียวกัน)
- **ไม่ต้องรอดูผล WYN-123 อีกต่อไป** สำหรับงานนี้ — R1 ตัดปัญหา "ผูกกับ Club หรือ Channel" ที่ backlog เดิมกังวลไว้ออกไปแล้วด้วยเหตุผลเชิงหลักการ ไม่ต้องรอโค้ดจริง
- **ยังต้องรอ WYN-115–118 เสร็จครบ** ก่อน Coding เริ่มจริง ตามลำดับ roadmap ที่ Founder วางไว้เดิม (ตรวจแล้ว: WYN-117/118 ยังอยู่ `.wyn/tasks/backlog/` ยังไม่เริ่มทำตอนนี้) — งานนี้ขยับจาก "รอวางแผน" มาเป็น "วางแผนเสร็จแล้ว รอคิว build" เท่านั้น ไม่ได้ตัดคิวเข้าไปสร้างก่อนกำหนด

## Priority

**P3** — วางแผน/Product spec เสร็จแล้วตามที่ Founder สั่งให้ทำต่อวันนี้ ("124 ต่อเลย") แต่คิว **Coding** ยังอยู่หลัง WYN-115–118 → WYN-123 เหมือนเดิมตาม roadmap — Founder ยังไม่ได้สั่งเปลี่ยนลำดับ build ตรงๆ มีแต่ขอให้วางแผนต่อ

## Risks

- **Scale ของ fan-out/realtime**: ยังไม่เคยมี pattern fan-out ระดับหลักร้อย/พันแถวต่อ event เดียวในระบบ (DM/Club post notification เดิม fan-out หลักสิบ-ร้อยแถวเป็นอย่างมาก) — ต้อง load-test จริงตอน Coding/QA ไม่ใช่แค่ประเมินจากทฤษฎี
- **R1 (ผูกกับ Club ไม่ผูกกับ Channel) ตัดสินใจก่อน WYN-123 เข้า Coding จริง**: ถ้า Channel ของ WYN-123 กลายเป็นแนวคิดที่มีอัตลักษณ์ของตัวเองแข็งแรงกว่าที่ประเมินไว้ตอนนี้ (เช่น สมาชิกเริ่มมองแต่ละ Channel เป็น "ห้อง" แยกกันจริงจัง) อาจต้องทบทวน R1 อีกครั้งตอน WYN-124 เข้าคิว Coding จริง — ระบุไว้ตรงๆ ว่าเป็นความเสี่ยงที่ยอมรับได้ ไม่ใช่มองข้าม
- **Complexity เพิ่มขึ้นจริงอีกชั้น** (ย้ำเตือนจาก Founder Brief ข้อ 19) — R7/R8 ตัด scope ไว้ชัดแล้ว ต้องคุมไม่ให้ Coding ขยายเพิ่มเองตอนเริ่มทำจริง

## Recommendation

ส่งต่อ **AI Design** ออกแบบ UX/UI ของห้องแชทกลุ่มได้ทันที — ใช้ `ConversationScreen`/`ChatInboxScreen` ของ DM เดิม (WYN-031) เป็นฐานอ้างอิงหลัก ต่างที่: header เป็นชื่อ Club + จำนวนสมาชิกแทนชื่อคน 1 คน, ไม่มี state "รออนุมัติ"/Message Request เลย (R2), ทางเข้าห้องแชทควรอยู่ที่ไหนในหน้า Club (เช่น TabBar เดิม 3 tab เพิ่มเป็น 4 หรือปุ่มลอยแยก) เป็นคำถามที่ Design ต้องตัดสินใจเอง — **Coding ยังไม่เริ่มจนกว่า WYN-115–118 จะเสร็จครบ**

- **ข้อควรระวังที่ Design เจอ ต้องยืนยันกับ Founder ก่อน Coding เริ่มจริง**: (1) WYN-122's chat lockdown (จำกัดแชท 1-ต่อ-1 เหลือ @warren↔@wynos_online ที่ยัง enabled อยู่จริงตอนนี้) ควรกินขอบเขตถึง Group Chat ด้วยหรือไม่ — โครงสร้างเดิมผูกกับคู่ 2 คน ใช้กับห้องกลุ่มไม่ได้ตรงๆ (2) ยังไม่มีกลไก report/moderation ระดับข้อความในห้องแชทกลุ่มเลยในดีไซน์นี้ (ตัด block ออกเพราะไม่เข้ากับบริบทสมาชิก Club เดียวกัน)

**Handoff (Design → Coding)**: **ห้ามเริ่มจนกว่า WYN-115–118 จะเสร็จครบ** — เมื่อถึงคิวจริงต้องถามยืนยัน 2 จุดข้างต้นกับ Founder ก่อนเขียน schema/RLS จริง และห้ามแก้ `chat_repository.dart`/`conversation_screen.dart` เดิมแม้แต่บรรทัดเดียว (ตาราง/หน้าจอใหม่ทั้งชุดแยกขาด ตาม R8)
