# Product Task — WYN-041

Status: backlog
Owner: AI Product Manager

Feature: Trending Engine v2 — wire view count เข้าสูตรจัดอันดับ + Anti-Manipulation Scoring (ต่อยอดจาก WYN-018)

Goal: ปิดช่องว่าง 2 จุดที่ WYN-040 (Discovery Page) เจอแล้วยกให้เป็นสโคปของ task นี้ตามชื่อที่ระบุไว้ใน roadmap (`.wyn/docs/product/wyn-v1.0.0-roadmap.md`, Phase 4) ตั้งแต่ต้น: (1) ตัวเลข View count ที่ WYN-038 สร้างไว้ (`drop_view_count()`, unique-viewer/rate-limit/self-view-exclusion ครบแล้ว) **ยังไม่เคยถูกใช้ในสูตรจัดอันดับใดๆ ในระบบเลย** ทั้งที่มีอยู่จริงและ trustworthy พอจะใช้ (2) ระบบจัดอันดับ ("สำหรับคุณ" WYN-018 / "กำลังนิยม" WYN-017 / Discovery's Trending Now-Hashtags WYN-040) **ไม่มีกลไกป้องกันการปั่นอันดับ (anti-manipulation) ใดๆ เลย** — บัญชีที่โดน moderator สั่ง restrict/suspend/ban แล้วจริง (WYN-029/030) เนื้อหาเก่าของบัญชีนั้นยังมีสิทธิ์ถูกจัดอันดับขึ้น Trending/สำหรับคุณ ได้เหมือนบัญชีปกติทุกประการ ทั้งที่ควรถูกกันออกจาก "การจัดอันดับเชิงบวก" ระหว่างที่ยังโดน sanction อยู่

Target User: ผู้ใช้ WYN Social ทุกคนที่เห็นผลจาก "สำหรับคุณ"/"กำลังนิยม"/Discovery — ได้รับผลลัพธ์ที่สะท้อนความนิยมจริง (รวม View ด้วย ไม่ใช่แค่ Like/Comment) และไม่เห็นเนื้อหาจากบัญชีที่กำลังโดน sanction ถูกดันขึ้นมาให้เด่นกว่าที่ควร

Problem: ยืนยันแล้วจากการอ่านโค้ดจริง (`app/lib/features/home/data/home_ranking.dart`, `home_repository.dart`) —
1. `rankingScore()` (WYN-018, ใช้ใน `fetchRankedFeed()` สำหรับ "สำหรับคุณ") สูตรปัจจุบันคือ `recencyScore + engagementScore + followingBoost` โดย `engagementScore = likeCount * 2 + commentCount * 3` **ไม่มี viewCount อยู่ในสูตรเลยแม้แต่พจน์เดียว** ทั้งที่ `HomeFeedItem.viewCount` มีอยู่แล้ว (WYN-038 wire เข้า `home_feed`/`saved_feed` view เรียบร้อยสำหรับ Drop)
2. `fetchTrending()` (ใช้ใน Home's "กำลังนิยม" row และ Discovery's Trending Now — WYN-040 — รวมถึงเป็น candidate source ของ Discovery's Trending Hashtags ด้วย) เรียงจาก `likeCount + commentCount` ล้วนๆ เช่นกัน ไม่มี viewCount
3. **ไม่มีจุดไหนในทั้งสองสูตรตรวจสอบสถานะ moderation ของผู้เขียนเลย** — Drop/Pop จากบัญชีที่กำลังโดน restrict/suspend/ban (`moderation_actions`, ยัง active อยู่จริงตาม `internal.is_posting_blocked()`) มีสิทธิ์ขึ้น Trending/สำหรับคุณ ได้เหมือนบัญชีปกติทันทีที่ engagement ตัวเลขสูงพอ ทั้งที่ตรรกะที่ถูกต้องคือ: การถูก sanction ไม่ควรตัดสิทธิ์การเข้าถึงเนื้อหาเก่าของผู้ใช้ทั่วไป (Home/Search/Following feed ยังเห็นได้ปกติตาม RLS เดิม ไม่แตะ) **แต่ไม่ควรได้รับการจัดอันดับเชิงบวกเพิ่มเติมจากระบบระหว่างที่ยังโดน sanction อยู่**

Requirements:

**1. Wire `viewCount` เข้าสูตรจัดอันดับทั้งสองจุด — เฉพาะ Drop เท่านั้น (Pop ไม่รวมในรอบนี้ ดูเหตุผลข้อ 2)**
- แก้ `rankingScore()` (WYN-018) เพิ่มพจน์ `viewScore` ใหม่เข้าไปในสูตร (`recencyScore + engagementScore + viewScore + followingBoost`) — น้ำหนักต้อง **น้อยกว่า** like/comment มาก เพราะจำนวน View ตามธรรมชาติจะเยอะกว่า Like/Comment หลายเท่าตัวเสมอ (คนเปิดดูมากกว่าคนกด Like/Comment เป็นปกติของทุกแพลตฟอร์ม) ถ้าให้น้ำหนักเท่าๆ กัน View จะกลืนสูตรทั้งหมดทันทีจน Like/Comment แทบไม่มีผล — เสนอเริ่มที่ `viewCount * 0.1` (Design/Coding ปรับตัวเลขจริงได้ ต้องมี comment อธิบายเหตุผลไว้ชัดเจนแบบเดียวกับที่ WYN-038 ทำกับ rate-limit numbers ว่าเป็นค่าที่ Product กำหนดเองชั่วคราว ไม่มีข้อมูล traffic จริงมาอ้างอิง เพราะแอปยังไม่ deploy จริง)
- แก้ `fetchTrending()` เรียงจาก `likeCount * 2 + commentCount * 3 + viewCount * 0.1` แทนของเดิม (`likeCount + commentCount`) — ใช้น้ำหนัก Like/Comment เดิมของ `rankingScore()` ให้สอดคล้องกันทั้งสองสูตร (ตอนนี้ `fetchTrending()` ใช้ `likeCount + commentCount` แบบ 1:1 ซึ่งต่างจาก `rankingScore()`'s `2:3` อยู่แล้ว — ถือโอกาสนี้ปรับให้สอดคล้องกันเลยเพราะทั้งสองสูตรควรสื่อความหมาย "engagement" แบบเดียวกัน ไม่ใช่คนละนิยาม)
- **Pop's engagement score ไม่เปลี่ยน** (ยังคง `likeCount * 2 + commentCount * 3` ล้วนๆ ไม่มี viewCount) — เหตุผลอยู่ข้อ 2 ด้านล่าง
- ทั้งสองจุดที่แก้เป็น client-side sort ที่มีอยู่แล้ว (ไม่ใช่ SQL ใหม่) — แก้แค่สูตรคำนวณ ไม่แตะ query/candidate-fetch logic เดิม

**2. Pop's view count ไม่นำมาใช้ในสูตรจัดอันดับรอบนี้ — เพราะยังไม่ trustworthy พอสำหรับ "anti-manipulation" engine**
- ยืนยันจากโค้ดจริง (`increment_pop_view_count()`, WYN-006): Pop's view count เป็น **counter ธรรมดาที่ `+1` ทุกครั้งที่เรียก ไม่มี unique-viewer dedup/self-view exclusion/rate-limit ระดับ DB เลยแม้แต่อย่างเดียว** (มีแค่ client-side flag กันเรียกซ้ำ "ภายในเซสชันเดียว" เท่านั้น ตามที่ WYN-038's Product spec เคยบันทึกไว้แล้วว่าเป็น Minor gap ที่ยอมรับไว้ตอนนั้น) — ถ้านำตัวเลขนี้ไปใส่ในสูตรจัดอันดับของ task ที่ชื่อ "anti-manipulation scoring" ตรงๆ จะกลายเป็นการเปิดช่องโหว่ใหม่ทันที: เจ้าของ Pop เปิดคลิปตัวเองซ้ำๆ (หรือใช้หลายบัญชีเปิด) ดันตัวเลข View แล้วได้อันดับ Trending สูงขึ้นได้ง่ายๆ โดยไม่ต้องมี engagement จริงเลย — ขัดกับวัตถุประสงค์หลักของ task นี้เอง
- **การแก้ Pop's view counting ให้ trustworthy เท่า Drop (สร้างตาราง `pop_views` + `record_pop_view()` RPC มิเรอร์ `drop_views`/`record_drop_view()` ของ WYN-038 เป๊ะ) ไม่อยู่ในสโคปของ task นี้** — เป็นงานแยกที่ควรเป็น task ใหม่ต่างหาก (เสนอชื่อใน Recommendation ด้านล่าง) เพราะมีขนาดงานเทียบเท่า WYN-038 เต็มรูปแบบ (schema ใหม่ + RPC ใหม่ + regression test ใหม่) ไม่ใช่แค่ "wire ตัวเลขที่มีอยู่แล้วเข้าสูตร" แบบ Drop

**3. Anti-manipulation: กันเนื้อหาจากบัญชีที่กำลังโดน moderation sanction ไม่ให้ได้รับการจัดอันดับเชิงบวก**
- นิยาม "กำลังโดน sanction" ใช้ตรรกะเดียวกับ `internal.is_posting_blocked(p_user_id)` ที่มีอยู่แล้ว (WYN-029/030): restrict/suspend ที่ยัง `expires_at > now()` หรือ ban ถาวร และไม่ถูก `overturned_at` จากการอุทธรณ์สำเร็จ (WYN-030) — reuse ฟังก์ชันเดิมตรงๆ ไม่ต้องเขียน logic ใหม่ซ้ำ
- **ไม่ใช่การซ่อนเนื้อหา** — เนื้อหาเก่าของบัญชีที่โดน sanction ยังเห็นได้ปกติทุกจุดเหมือนเดิม (Home chronological feed, Following feed, Search, Hashtag feed, โปรไฟล์เจ้าของเอง) เพราะ RLS ของ `drops`/`pops` ไม่เคยบล็อกการอ่าน (restrict/suspend/ban บล็อกแค่การ "สร้างเนื้อหาใหม่" ที่ INSERT policy ตาม WYN-029/030 ไม่เคยบล็อกการมองเห็น) — task นี้เปลี่ยนแค่ **"ไม่ได้รับการจัดอันดับเชิงบวกเพิ่มเติมจากอัลกอริทึม"** เท่านั้น สองเรื่องนี้แยกกันชัดเจน ห้ามปนกัน
- ขอบเขต: ตัดออกจาก **"กำลังนิยม" (Home Trending row + Discovery Trending Now)** และ **"สำหรับคุณ" (WYN-018 ranked feed)** เท่านั้น — Discovery's Trending Hashtags ใช้ candidate window เดียวกับ "กำลังนิยม" อยู่แล้ว (`fetchTrending()`) ตาม WYN-040 design จึงได้ผลลัพธ์เดียวกันโดยอัตโนมัติถ้าแก้ที่จุดเดียว (`fetchTrending()`) ไม่ต้องแก้ซ้ำที่ `DiscoveryRepository`
- **เทคนิคที่ต้องระวัง (มิเรอร์ Risk เดียวกับที่ WYN-040 เคยเจอ)**: `moderation_actions` ไม่มี SELECT policy เปิดให้บุคคลทั่วไปเห็น ("ordinary users have no SELECT policy on..." ตามคอมเมนต์ในสคีมาเอง) และ `internal.is_posting_blocked()` อยู่ใน schema `internal` (ไม่ถูก expose เป็น REST endpoint ตรงๆ อยู่แล้ว) — การกรอง candidate list ของ Trending/สำหรับคุณ (ซึ่งทำแบบ fetch-candidate-แล้ว-sort-ฝั่ง-client เหมือนเดิม) ต้องมี **SECURITY DEFINER RPC ใหม่** รับ list ของ author id ที่เป็น candidate แล้วคืนกลับมาว่า "ตัวไหนบ้างที่ active sanction อยู่" — **คืนแค่ id ที่ควรถูกกันออก ไม่คืนรายละเอียด action_type/reason/reviewer/expiry ใดๆ เลย** (มิเรอร์ anti-gaming return-shape เดียวกับ `rising_profiles()`/`suggested_users()` ของ WYN-040 — ป้องกันไม่ให้ third-party ใช้ RPC นี้เป็นเครื่องมือสอดส่อง "ใครโดน sanction บ้าง" ซึ่งเป็นข้อมูลอ่อนไหวที่ WYN-029/030 ตั้งใจปิดไว้แล้ว) — pattern การเรียกใช้ให้เดินตามแนวเดียวกับ `HomeRepository._fetchFollowedAuthorIds()` ที่มีอยู่แล้ว (fetch candidate ก่อน แล้วยิง RPC/query แยกเพื่อกรอง ก่อน sort สุดท้าย)

Acceptance Criteria:
- [ ] "กำลังนิยม" (Home Trending row) และ Discovery's Trending Now: Drop ที่มี View (deduped) มากกว่าอย่างมีนัยสำคัญแต่ Like/Comment เท่ากัน ได้อันดับสูงกว่า Drop ที่มี View น้อยกว่า — ยืนยันด้วย unit test ของสูตรโดยตรง (ไม่ต้องพึ่ง Supabase จริง เหมือน `rankTrendingHashtags`/`rankingScore` เดิม)
- [ ] "สำหรับคุณ" (WYN-018): สูตรใหม่มี viewCount term จริง น้ำหนักน้อยกว่า like/comment ตามที่ระบุ ไม่ทำให้ลำดับเดิมของ item ที่ viewCount เท่ากันเปลี่ยนไป (regression: ผลลัพธ์เดิมของ WYN-018's test suite ที่ไม่เกี่ยวกับ view ต้องยังผ่านหมด)
- [ ] Pop content: engagement score/ranking ไม่เปลี่ยนแปลงจากเดิมแม้แต่กรณีเดียว (regression เต็ม)
- [ ] จำลองบัญชีที่โดน `restrict`/`suspend` (ยัง `expires_at > now()`) หรือ `ban` จริงผ่าน `moderation_actions` → Drop/Pop ของบัญชีนั้นหายไปจาก candidate ranking ของ "กำลังนิยม"/"สำหรับคุณ"/Discovery Trending Now ทันที แม้จะมี engagement สูงกว่าเนื้อหาอื่นทั้งหมดก็ตาม
- [ ] เนื้อหาเดียวกันนั้นยัง**เห็นได้ปกติ**ผ่าน Home chronological feed/Following feed/Search/Hashtag feed/โปรไฟล์เจ้าของเอง — ยืนยันว่าไม่ใช่การซ่อนเนื้อหา แค่ตัดสิทธิ์การจัดอันดับ
- [ ] บัญชีที่เคยโดน sanction แต่หมดอายุแล้ว (`expires_at` ผ่านไปแล้ว) หรือถูก `overturned_at` จากการอุทธรณ์สำเร็จ (WYN-030) กลับมาได้รับการจัดอันดับปกติทันที ไม่มี penalty ค้าง
- [ ] RPC ใหม่สำหรับตรวจ sanction status ของกลุ่ม author คืนแค่ id ที่ถูกกันออกเท่านั้น ไม่รั่ว action_type/reason/reviewer/expiry ออกไปทางไหนเลย — ยืนยันด้วย SQL test ตรง (เทียบ return type และเนื้อหา response)
- [ ] Regression เต็มชุด: WYN-017 (Home Trending)/WYN-018 (สำหรับคุณ)/WYN-040 (Discovery ทั้ง 5 section) ทำงานเหมือนเดิมทุกจุดที่ไม่เกี่ยวกับการเปลี่ยนแปลงนี้ ไม่มี regression

Dependencies: WYN-017 (`fetchTrending()`), WYN-018 (`rankingScore()`/`fetchRankedFeed()`), WYN-038 (`drop_view_count()`, ตัวเลข View ที่ trustworthy พอจะใช้), WYN-029/030 (`moderation_actions`/`internal.is_posting_blocked()`, active-sanction semantics รวม overturned-by-appeal), WYN-040 (Discovery's Trending Now/Trending Hashtags reuse `fetchTrending()` ตรงๆ — ได้ผลจาก task นี้อัตโนมัติถ้าแก้ที่จุดเดียว)

Priority: P1 — task ที่สองของ Phase 4 (Discovery & Trending Engine) ตาม roadmap ต่อจาก WYN-040 ทันที

Risks:
- **น้ำหนักตัวเลขของ viewCount ในสูตร (`* 0.1`) เป็นค่าที่ Product กำหนดเองชั่วคราว** ไม่มีข้อมูล traffic จริงมาอ้างอิง (แอปยังไม่ deploy ขึ้น production จริง) เหมือนที่ WYN-038 เคยยอมรับกับตัวเลข rate-limit — ต้องเก็บเป็นค่าคงที่ปรับได้ง่าย มี comment อธิบายเหตุผลชัดเจน ปรับได้ภายหลังเมื่อมีข้อมูลจริง
- **Pop's view count ยังไม่ trustworthy พอสำหรับ ranking** (ดูข้อ 2) — เป็น known gap ที่ยังไม่ปิดในรอบนี้ ถ้า Founder ต้องการให้ Pop ได้รับ treatment เดียวกัน ต้องเป็น task ใหม่แยก (ดู Recommendation)
- **ไม่ใช่ full anti-manipulation/bot-detection** — ยังไม่มี CAPTCHA/device fingerprint/IP tracking ในระบบเหมือนที่ WYN-038 เคยยอมรับสโคปไว้แล้ว (ไม่มี backend service แยก เป็น Flutter+Supabase ล้วนๆ) — task นี้ปิดแค่ 2 ช่องที่ระบุไว้ชัดเจน (view count ไม่ trustworthy สำหรับ Pop, ไม่มีการกันบัญชีที่โดน sanction ไม่ให้ถูกดันขึ้น) ไม่ใช่การแก้ปัญหา sybil/fake-engagement แบบเต็มรูปแบบ — ถ้า Founder ต้องการมากกว่านี้ต้องคุยเรื่อง infra เพิ่มเติม (เหมือนที่ WYN-038 เคยระบุไว้)
- **RPC ใหม่ต้องคืนแค่ id ที่ถูกกันออก ไม่คืนรายละเอียดใดๆ** — ถ้า Design/Coding มองข้ามจุดนี้แล้วคืน action_type/reason ออกมาด้วย จะกลายเป็นการรั่วข้อมูล moderation ที่ WYN-029/030 ตั้งใจปิดไว้เป็นการเฉพาะ (เหมือน Risk ที่ WYN-040 เจอกับ Rising's follower-growth number)
- **การกรองต้องเกิดที่ "การจัดอันดับ" เท่านั้น ห้ามลามไปเป็นการซ่อนเนื้อหาใน RLS/view เดิม** — ถ้าเขียนผิดจุด (เช่น ไปแก้ WHERE clause ของ `home_feed` view ตรงๆ) จะกลายเป็นเปลี่ยนพฤติกรรมการมองเห็นเนื้อหาที่ WYN-029/030 ไม่เคยตั้งใจให้เปลี่ยน (restrict/suspend/ban บล็อกแค่การสร้างเนื้อหาใหม่ ไม่เคยบล็อกการมองเห็นเนื้อหาเก่า) — เน้นให้ QA ตรวจจุดนี้เป็นพิเศษ

Recommendation: เริ่มจาก Requirement 1 (wire viewCount เข้าสูตร — reuse ข้อมูลที่มีอยู่แล้วเต็มที่ ไม่มีความเสี่ยงใหม่) ก่อน แล้วตามด้วย Requirement 3 (moderation-exclusion RPC — งานใหม่แต่ reuse `internal.is_posting_blocked()` เต็มที่ ไม่ต้องเขียน sanction logic ใหม่) — เสนอ **WYN-04X ใหม่แยกต่างหาก** (นอกสโคป task นี้) สำหรับ "Pop View Counting Hardening" (`pop_views` table + `record_pop_view()` RPC มิเรอร์ WYN-038 เป๊ะ ให้ Pop ได้ตัวเลข View ที่ trustworthy เท่า Drop) เป็นตัวเลือกให้ Founder พิจารณาทำต่อหลัง Phase 4 หรือแทรกก่อน WYN-042 (WYN Top 100) ก็ได้ถ้าต้องการให้ Top 100 นับ Pop's view อย่างเป็นธรรม

Handoff: AI Design — ออกแบบ schema/RPC ของ moderation-exclusion filter (Requirement 3, ต้องเป็น SECURITY DEFINER คืนแค่ id ที่ถูกกันออก) และตัดสินใจ integration point สุดท้ายของทั้งสอง Requirement ใน `home_repository.dart` (แก้ตรงจุดไหนใน `fetchTrending()`/`fetchRankedFeed()`/`rankingScore()` ให้ diff เล็กที่สุดและ Discovery (WYN-040) ได้ผลอัตโนมัติโดยไม่ต้องแก้ `DiscoveryRepository` เพิ่ม) — ดู Requirements ข้างต้นสำหรับน้ำหนัก/ขอบเขตที่ Product กำหนดไว้แล้ว
