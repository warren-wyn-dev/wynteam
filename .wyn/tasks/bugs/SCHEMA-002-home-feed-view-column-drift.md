# Bug Report — SCHEMA-002

Status: bugs
Owner: AI Debug Engineer
Bug: `supabase/schema.sql` cannot be applied fresh (top-to-bottom, e.g. a brand-new Supabase project or this repo's own local-Postgres regression test harness) — it aborts partway through with `ERROR: cannot change name of view column "comment_count" to "liked_by"`. Found while working on WYN-077 (unrelated task); confirmed with `git stash` that it reproduces identically on `main`'s current `schema.sql` with zero WYN-077 changes applied, so it predates this task and isn't something WYN-077 introduced or needs to fix.
Reproduction:
```
createdb schema_fresh_test
psql -d schema_fresh_test -f supabase/tests/<any existing test>'s 00_stub.sql equivalent (auth/storage schema stub -- see any file in supabase/tests/ for the exact stub)
psql -d schema_fresh_test -v ON_ERROR_STOP=1 -f supabase/schema.sql
-- fails partway through with:
-- ERROR:  cannot change name of view column "comment_count" to "liked_by"
-- HINT:  Use ALTER VIEW ... RENAME COLUMN ... to change name of view column instead.
```
This also silently blocks every `supabase/tests/*.sh` regression test that applies the real `schema.sql` (they all load it the same way) — none of them can currently run end-to-end in a from-scratch environment. `supabase/check_schema_ordering.py` does NOT catch this class of bug (it only checks forward references, not `CREATE OR REPLACE VIEW` column-shape compatibility across a table/view's multiple historical redefinitions in the file).
Root Cause: `public.home_feed` is redefined via a full `create or replace view` 7 separate times through the file's history (as different WYN tasks added columns) at (line numbers as of this report, before any future edits shift them): 456, 3982, 5965, 6381, 7033, 7156, 10674. Postgres's `CREATE OR REPLACE VIEW` only allows *appending* new columns at the end of an existing view's column list — renaming, removing, or reordering any existing column is rejected outright. The redefinition at line 7156 (added by a later WYN task, judging by the `liked_by` column) inserts a new `liked_by` column *in the middle* of the column list (right after `like_count`, before `comment_count`) instead of appending it at the end — this pushes `comment_count` from position 16 to 17 relative to the immediately preceding redefinition at line 7033, which `CREATE OR REPLACE VIEW` reads as "rename column 16 from comment_count to liked_by" and rejects.

This is the exact same bug *class* already documented and fixed once before in production only (not in this file) — see `.wyn/company/DECISIONS.md`, 2026-09-01 ("WYN-072 deploy จริงขึ้น production"): that incident hit `42P16` applying a schema delta straight to production, root-caused to "column order jumping the middle instead of appending", and was fixed *in production* by moving the new columns to the end. That production fix was never back-ported into `schema.sql` at this specific spot (or this bug wouldn't reproduce from a clean file).
Fix: Not attempted here (out of scope for WYN-077, and the safest fix requires checking whether any other redefinition of `home_feed`/`saved_feed`/`moderation_queue`/`chat_inbox`/`message_requests` (this repo's other multiply-redefined views, per the `grant select on public.<view> to authenticated` occurrences scattered through the file) has the same "inserted new column in the middle" mistake before declaring this fully fixed. Suggested direction, mirroring the production fix DECISIONS.md already describes: edit the line-7156 `create or replace view public.home_feed` definition to move `liked_by` to the *end* of its column list (after `poll_expires_at`) instead of between `like_count` and `comment_count`, then re-verify every later redefinition (7156→10674, and any I haven't audited) is still a pure append relative to its predecessor. A `drop view if exists ... cascade;` immediately before each `create` would also work and is more robust against future column reorders, at the cost of needing to re-grant `select` after each one (mirrors what this session did in a throwaway local copy purely to unblock testing WYN-077 — never applied to the real file).
Files Changed: none (bug report only)
Tests: `supabase/tests/wyn_050_admin_dashboard_test.sh` and `supabase/tests/wyn_077_basic_product_analytics_test.sh` both indirectly prove this bug exists (both currently cannot be run against the unmodified `schema.sql` in this sandbox — verified only against a throwaway local copy with the view-drift statements patched to `drop view ... cascade; create view ...` purely for that verification, never applied to the committed file). Once this bug is fixed, both should be re-run against the real `schema.sql` to confirm they pass end-to-end (see WYN-077's own Coding notes in `.wyn/company/CONTEXT.md`).
Regression Risk: Low to fix (view-only, no data-shape change to the underlying tables), but wide blast radius if done carelessly — `home_feed` is read by most of the app's main screens, so whoever fixes this should re-run every existing `wyn_*_test.sh` that touches `home_feed`/`saved_feed` afterward, not just add a new one.
