# Bug Report — WYN-143 (App signs the user out mid-session on any hard background-refresh failure, not just account switching)

Status: mitigated (defensive recovery added), root cause of the *underlying* refresh failure not directly observed -- pending QA re-verification with a real Flutter toolchain and, ideally, Supabase Auth Logs from a real occurrence (see Regression Risk / Handoff to QA)
Owner: AI Debug Engineer
Founder report (2026-09-13): "เช็คทั้งระบบ หาบั๊คให้หน่อย เหมือนระบบ มันชอบเด้งออก" (whole-system bug hunt). Follow-up clarification (same session, via structured questions): the unexpected-logout symptom happens **during ordinary use** (scrolling the feed / liking / commenting, not idle/backgrounded) and **after posting a photo/video or anything that takes a while to load** — explicitly **not** while using the multi-account switcher (ruling out WYN-142, a separate, already-fixed bug found and fixed earlier in this same investigation).

Bug: Any time real `gotrue`'s own background/automatic token refresh (fires roughly every ~55 minutes for the active session, and whenever an in-flight request's access token has gone stale) is rejected by the server for any reason other than gotrue's own narrow `refresh_token_already_used` recovery case, the **entire session is torn down immediately** and `AuthGate` bounces the user straight to `WelcomeScreen` — indistinguishable, from the user's perspective, from an intentional sign-out. There is no retry, no grace period, and (before this fix) no way for the app to tell "the refresh token is genuinely dead" apart from "that one refresh attempt hit a transient failure" (a network blip on mobile data, a momentary 5xx, etc.). A slow Drop/Pop upload over a flaky mobile connection is exactly the kind of window where a transient refresh failure is more likely to coincide with active use — matching the Founder's own description of when this happens.

Reproduction: Traced against the same pinned `gotrue` source already downloaded for WYN-142 (version `2.27.2`, `app/pubspec.lock`) — `GoTrueClient._doRefresh` (`gotrue_client.dart`):
```dart
} on AuthException catch (error, stack) {
  final existingSession = _currentSession;
  if (error is AuthApiException &&
      error.code == 'refresh_token_already_used' &&
      existingSession != null &&
      !existingSession.isExpired) {
    return AuthResponse(session: existingSession);
  }
  if (error is! AuthRetryableFetchException) {
    if (!_isDisposed && _sessionVersion == versionBeforeRefresh) {
      _removeSession();
      notifyAllSubscribers(AuthChangeEvent.signedOut, signOutReason: SignOutReason.sessionExpired);
    }
  } ...
  rethrow;
}
```
Any `AuthApiException` that isn't specifically `refresh_token_already_used` (e.g. `refresh_token_not_found`, a revoked token, a transient-but-not-`AuthRetryableFetchException`-classified server error) takes the `_removeSession()` + `signedOut` branch unconditionally, on **every** background refresh, not just ones triggered by user action. `AuthGate`'s own listener (`auth_gate.dart`, before this fix) treated every `signedOut` event as equally "relevant" and popped straight to `WelcomeScreen` regardless of `AuthState.signOutReason` — even though `gotrue`'s own `AuthState`/`SignOutReason` types are explicitly documented (`sign_out_reason.dart`) as existing specifically "to distinguish an explicit sign out from an involuntary one, such as an expired session" — a mechanism the app never consumed anywhere (confirmed via `grep -rn "SignOutReason" app/lib` before this fix: zero matches).

Not run against a real Flutter toolchain in this session (none available in this sandbox, same limitation as every other task noted here) and **not observed directly via a live occurrence's network/console logs or Supabase Auth Logs** — this session has no network egress to production and no Supabase Management API credentials, so the *specific* transient condition that rejects a given real-world background refresh (mobile network drop, a momentary Supabase Auth outage, clock skew, something else) could not be confirmed empirically. What **is** confirmed directly from source, not guessed: (1) `gotrue`'s all-or-nothing teardown behavior on any non-`refresh_token_already_used` rejection, unconditionally, for every kind of refresh including its own silent background one; (2) the app never previously distinguished `SignOutReason.userInitiated` from an involuntary one; (3) the fix's own regression tests (below) prove the new code paths behave as designed against a controlled fake.

Root Cause: `AuthGate`'s auth-state listener treated `AuthChangeEvent.signedOut` as always meaning "the user is genuinely no longer signed in," collapsing gotrue's own three distinct `SignOutReason`s (`userInitiated`, `sessionExpired`, `sessionMissing`) into one code path. Combined with gotrue's fail-fast background-refresh behavior (confirmed above), any transient rejection of an automatic refresh — not just a truly dead/revoked token — permanently and immediately signs the user out with no recovery path, mid-session, with no relation to anything the user did wrong.

Fix: `AuthGate` now gives an involuntary `signedOut` (`signOutReason != SignOutReason.userInitiated`) exactly one recovery attempt before treating it as a real sign-out: it keeps the most recent refresh token known to have been valid (`_lastKnownRefreshToken`, updated on every `signedIn`/`tokenRefreshed` event) and, on an involuntary `signedOut`, calls a new `AuthRepository.recoverSession(refreshToken)` (thin wrapper around `client.auth.setSession(refreshToken)`) before popping navigation. If that recovery succeeds, its own `tokenRefreshed` event flows back through the same listener and nothing is visible to the user at all — exactly as if the original refresh had simply succeeded. If recovery also fails, this really is a dead session, and the existing pop-to-`WelcomeScreen` behavior runs unchanged. An explicit `signOut()` call (Settings, Delete Account, leaving a blocked-account screen, ...) is untouched — those already pass/imply `SignOutReason.userInitiated` and skip the recovery path entirely, so a real logout still always works. A `_recoveringSession` guard prevents a second, redundant recovery attempt if gotrue's own recovery-attempt failure fires a second `signedOut` on the same stream while the first attempt is still in flight (traced through the same `_doRefresh` code path — a real, not hypothetical, risk without the guard).

Files Changed:
- `app/lib/features/auth/presentation/auth_gate.dart` (`_lastKnownRefreshToken`, `_recoveringSession`, listener restructured into `_handleAuthEvent` + `_attemptSessionRecovery`)
- `app/lib/features/auth/data/auth_repository.dart` (new `recoverSession(String refreshToken)`)
- `app/test/support/recording_auth_repository.dart` (`signOut()` now tags `SignOutReason.userInitiated` correctly; new `emitInvoluntarySignedOut()`, `recoverSession` override with controllable outcome)
- `app/test/auth_gate_test.dart` (`_fakeSession` now carries a `refreshToken`; new `'Involuntary sign-out recovery'` test group, 3 tests)

Tests: 3 new widget tests in `auth_gate_test.dart`'s `'Involuntary sign-out recovery'` group: (1) a recoverable involuntary `signedOut` never pops navigation or shows `WelcomeScreen`; (2) an involuntary `signedOut` that also fails to recover falls through to `WelcomeScreen` exactly as before; (3) an explicit `signOut()` (`userInitiated`) is never treated as recoverable, proving a real logout still always works. **Not run against a real Flutter toolchain in this session** (no `flutter`/`dart` binary available, confirmed via `which`) — needs a real `flutter analyze`/`flutter test` run to confirm both compile and pass, same caveat as WYN-142 and every other task hitting this sandbox limitation.

Regression Risk: Low-to-moderate. The recovery path only ever activates on an involuntary `signedOut` (never on `signIn`, ordinary same-account `tokenRefreshed`, or an explicit `signOut()`), and on failure falls through to byte-for-byte the same existing behavior as before this fix. The one real risk surface: interaction with WYN-142's own recovery inside `AccountSwitcherRepository.switchTo()` — a failed account switch's `signedOut(sessionExpired)` event now also reaches *this* new recovery path concurrently with WYN-142's own restore attempt, both racing to `setSession()` the same cached refresh token. Traced through `_doRefresh`'s own `refresh_token_already_used` special-case (which explicitly exists to absorb concurrent-refresh races like this): whichever of the two attempts loses the race hits that graceful path and returns the session the winner just established, rather than tearing anything down further — no new failure mode, just a harmless duplicate network call in an already-rare edge case (switching to an account whose stored token is *also* simultaneously stale). Not exercised by a dedicated test (out of scope for this round; flagged here for whoever next touches account-switcher/session-recovery code together).
