# Bug Report — DS-001c (BUG-1)

Status: bugs
Owner: AI Debug Engineer
Found by: AI QA & Security (DS-001 full QA — DS-001a/b/c, 2026-08-16)
Severity: **Major (blocking)** — breaks the entire point of the ZOKY sub-theme (commerce identity separation) on the customer-facing marketplace; directly contradicts an explicit Founder decision and DS-001's own Section 4 rule #1.

Bug: ZOKY product prices shown inside `app/` (the customer-facing WYN Social app's ZOKY marketplace tab) render as **Cyan `#00C8FF`**, not **Orange**, in both light and dark mode. DS-001c's commit message ("feat(design): tokenize scrim overlays, price accents, seller Cyan leaks (DS-001c)", PR #122, "Part B") claims:

> Product price digits across app/'s ZOKY module now read `colorScheme.tertiary` instead of `colorScheme.primary`, matching DS-001 Section 3.4/4 ("ราคาสินค้าทุกที่").

This claim is **false in effect**. In `app/`, the only theme in existence is `WynTheme` (`app/lib/core/design/wyn_theme.dart`), built from `WynColors.socialLightScheme`/`socialDarkScheme` (`app/lib/core/design/wyn_colors.dart`). In both of those `ColorScheme`s, `tertiary` is set to `cyan500` (`#00C8FF`) — **identical to `primary`**. So swapping `colorScheme.primary` → `colorScheme.tertiary` in these 5 files changed nothing about the rendered color: it was Cyan before, and it is still Cyan after, in both light and dark mode. The DS-001 spec's own design doc predicts this exact outcome and never resolves it — `.wyn/docs/design/ds-001-color-system.md`, Section 3.4, last paragraph, states in plain words: **"ส่วนแอป Social เรียกช่องเดียวกันแล้วได้ Cyan ดิบ (ไม่มีทางหลุดข้ามฝั่ง)"** ("...and the Social app calling the same slot gets raw Cyan — there's no way to cross over"). `app/`'s ZOKY marketplace tab is embedded *inside* the Social app's single `MaterialApp`/`WynTheme` — there is no `Theme()` override anywhere in `app/lib` that locally re-maps `tertiary` to Orange for the ZOKY-tab subtree (confirmed by exhaustive `grep` — zero matches for `Theme(` wraps or a `ZokyTheme`-equivalent anywhere in `app/lib`). The only place a ZOKY sub-theme (`ZokyTheme`, `tertiary` = Orange) actually exists is `seller_app/lib/core/design/wyn_zoky_theme.dart`, which is a **different Flutter app/binary** — `app/`'s ZOKY tab cannot use it.

This directly contradicts:
- `.wyn/company/DECISIONS.md` (2026-08-15, "เปลี่ยน Color Direction ของ WYN: Blue → Cyan"): "ZOKY Primary (commerce layer แยก identity): Orange `#FF6B35` ใช้เฉพาะ price/CTA/seller badge/commerce state"
- `.wyn/docs/design/ds-001-color-system.md`, Section 4, Rule #1 ("ราคา — ตัวเลขราคาสินค้าทุกที่ (grid tile, product detail, cart, checkout summary, order detail) — light `#CC4A16`, dark `#FF6B35`"), which explicitly lists `product_grid_tile.dart`, `product_detail_screen`, `cart`, `order` — all of which live in `app/lib/features/zoky/`, not `seller_app/`
- DS-001 backlog task's Acceptance Criteria: "ZOKY แสดง Orange เฉพาะจุดที่ระบุใน R3 เท่านั้น" — it fails to show Orange at all in `app/`.

Reproduction (proved independently with a throwaway widget test, run and then deleted — not just theorized from reading the code):

1. `flutter test` a widget test that pumps `MaterialApp(theme: WynTheme.light, home: Builder(builder: (context) => ...))` and reads `Theme.of(context).colorScheme.tertiary`.
2. Assert it against `WynColors.cyan500` (`#00C8FF`) — **passes** (i.e. `tertiary == cyan500`, not `orange700`/`orange500`).
3. Repeat with `WynTheme.dark` — same result, `tertiary == cyan500`.
4. Actual QA run output:
   ```
   QA PROBE light colorScheme.tertiary = Color(alpha: 1.0000, red: 0.0000, green: 0.7843, blue: 1.0000, ...) (cyan500=Color(... red: 0.0000, green: 0.7843, blue: 1.0000, ...), orange700=Color(... red: 0.8000, green: 0.2902, blue: 0.0863, ...))
   QA PROBE dark  colorScheme.tertiary = Color(alpha: 1.0000, red: 0.0000, green: 0.7843, blue: 1.0000, ...) (cyan500=Color(... same as above ...), orange500=Color(... red: 1.0000, green: 0.4196, blue: 0.2078, ...))
   ```
   `colorScheme.tertiary`'s RGB (`0.0, 0.7843, 1.0`) matches `cyan500` exactly in both light and dark, and does not match either orange shade.
5. Also confirmed at the source level: `git show 5ea364b:app/lib/features/zoky/presentation/widgets/product_mini_card.dart` (the commit right before DS-001c) shows the price used `colorScheme.primary` before this change — and `socialLightScheme`/`socialDarkScheme` set `primary: cyan500` too, so this was *already* Cyan before DS-001c. DS-001c's diff only swapped which Cyan-valued slot is read, not the actual color.

Expected: ZOKY product prices inside `app/`'s ZOKY marketplace tab render in Orange (`#CC4A16` light / `#FF6B35` dark), matching every other ZOKY-branded price display in the platform (`seller_app/`'s equivalents, which correctly resolve to Orange via `ZokyTheme`).

Actual: ZOKY product prices inside `app/`'s ZOKY marketplace tab render in Cyan (`#00C8FF`), identical to WYN Social's brand accent color, in both light and dark mode — no visual distinction from the Social app's own accent color anywhere in the customer marketplace flow.

Affected files (all in `app/lib/features/zoky/`, all changed by DS-001c commit `6df622f`, "Part B"):
1. `app/lib/features/zoky/presentation/widgets/product_mini_card.dart:50` — product price on ZOKY Home's mini card
2. `app/lib/features/zoky/presentation/widgets/zoky_cart_item_tile.dart:78` — line price in the cart
3. `app/lib/features/zoky/presentation/product_detail_screen.dart:223` — main price on Product Detail
4. `app/lib/features/zoky/presentation/zoky_checkout_summary_screen.dart:155` — per-item line total at checkout
5. `app/lib/features/zoky/presentation/zoky_order_detail_screen.dart:255,263` — per-item unit price and line total on Order Detail

All 6 call sites read `Theme.of(context).colorScheme.tertiary` and get Cyan instead of Orange.

Secondary, lower-priority related gap (same root cause family, **not** touched by DS-001c, pre-existing since ZOKY-001 — flagging for completeness since Section 4's own file table names it): `app/lib/features/zoky/presentation/widgets/product_grid_tile.dart`'s price badge (line 42-48) uses a hardcoded `Colors.white` on `WynColors.imageScrim`, not any Orange token at all — the grid tile price never got an Orange treatment even before this bug. Not blocking on its own (badge/scrim pattern is defensible per spec Section 3.0), but worth folding into the same fix pass since Section 4's rule #1 table names this exact file.

Root Cause (analysis by QA — Debug Engineer should confirm independently before fixing): DS-001a/b built exactly one `ColorScheme` pair for `app/` (`socialLightScheme`/`socialDarkScheme`, `tertiary = cyan500`) and exactly one *additional* `ColorScheme` pair for `seller_app/` only (`ZokyTheme`, `tertiary` swapped to Orange) — because `seller_app/` is a **separate whole app** where "the ZOKY sub-theme is the only theme" (DS-001 spec, Section 4's `seller_app/` subsection) is a coherent, implementable rule. But `app/`'s ZOKY marketplace is a **tab embedded inside the Social app**, sharing one `MaterialApp`/`Theme` with Home/Drop/Pop/Club/Profile — DS-001 never designed (and DS-001a/b/c never implemented) a mechanism for that one tab's subtree to locally re-map `tertiary` to Orange the way `seller_app/`'s whole-app `ZokyTheme` does. DS-001c's Part B change assumed `colorScheme.tertiary` would resolve to Orange the same way it does in `seller_app/`, without checking what `tertiary` actually equals under `app/`'s own `WynTheme` — an assumption the design doc's own Section 3.4 text explicitly warns against ("ส่วนแอป Social เรียกช่องเดียวกันแล้วได้ Cyan ดิบ").

Fix (options — Debug Engineer / AI Design should pick one, this is a design-scope decision as much as a code fix):
- **Option A (recommended, smallest blast radius)**: Wrap the ZOKY tab's subtree in `app/lib/features/root/presentation/root_shell.dart` (or wherever the ZOKY tab's root screen is built) with a local `Theme(data: Theme.of(context).copyWith(colorScheme: Theme.of(context).colorScheme.copyWith(tertiary: WynColors.orange700 /* light */ or WynColors.orange500 /* dark */, onTertiary: WynColors.ink, tertiaryContainer: ..., onTertiaryContainer: WynColors.ink)), child: ...)` — mirrors what `ZokyTheme.copyWith(...)` does for `seller_app/`, but scoped to just the ZOKY tab's widget subtree instead of the whole app. Needs to pick the correct shade per light/dark (`orange700` for light per Section 2.2's own contrast table — raw `orange500` fails AA on white bare text, same problem Section 3.0 solved for Cyan; `orange500` for dark, matching `ZokyTheme`'s own dark `tertiary`). This needs an explicit design decision on whether `app/`'s local ZOKY-tab override should use the *raw* `orange500` (Option B parity, contrast-failing on light like the rest of B) or the AA-safe `orange700` shade Section 2.2 already names for exactly this purpose — recommend asking AI Design/Founder to confirm rather than picking silently, since it's the same B-vs-contrast tension DS-001's own Section 3.0 already resolved once for Cyan and never explicitly re-resolved for this specific case.
- **Option B**: Skip `colorScheme.tertiary` entirely for these 6 call sites and reference `WynColors.orange700`/`WynColors.orange500` (theme-brightness-conditional) directly, same pattern already used correctly in `seller_app/`'s files via `ZokyTheme`. Simpler, but loses the "single call site auto-adapts" property DS-001 Section 3.4 was designed around, and re-introduces a small amount of brightness-conditional branching at each of the 6 call sites (`Theme.of(context).brightness == Brightness.dark ? WynColors.orange500 : WynColors.orange700`).
- Either way, fold in the secondary `product_grid_tile.dart` gap (see above) into the same fix pass since it's the same underlying "app/'s ZOKY tab has no way to get Orange" root cause and Section 4's own file table names it directly.

Files Changed (expected): the 5 files under "Affected files" above, `product_grid_tile.dart`, and whichever theme-wrap location Option A picks (likely `app/lib/features/root/presentation/root_shell.dart` or a new small helper in `app/lib/features/zoky/`). Do **not** touch `seller_app/` — its ZOKY prices already resolve to Orange correctly via `ZokyTheme`, confirmed by QA's `grep` sweep (zero remaining `colorScheme.primary`/`colorScheme.secondary` references in `seller_app/lib/features`).

Tests to add (regression memory): a widget test analogous to QA's throwaway probe, but permanent — pump each of the 6 fixed widgets (or at minimum `ProductDetailScreen`, `ProductMiniCard`, one checkout/order-detail line item) under the real `app/` widget tree (via `RootShell` or whatever wraps the ZOKY tab) and assert the resolved `TextStyle.color` used for the price digits equals `WynColors.orange700` (light) / the dark equivalent chosen — not `WynColors.cyan500`. A test that only checks "some color is applied" would not have caught this bug (the previous `colorScheme.primary` also "applied a color").

Regression Risk: Low — this is additive (a new local theme wrap, or a direct token reference) scoped to the ZOKY tab / 6 specific `Text` widgets. It should not affect any other screen's color, and should not affect any non-color behavior (no logic/route/DB change needed). Full `app/` (280 tests) and `seller_app/` (91 tests) suites must still pass, plus the new tests above.

Handoff to QA: After the fix, QA round 2 must (1) re-run the same "what does `colorScheme.tertiary` (or whichever token is used) actually resolve to" runtime probe for all 6 call sites and confirm Orange, not Cyan, in both light and dark; (2) re-run the full `grep` sweep for `colorScheme.tertiary`/`colorScheme.primary` in `app/lib/features/zoky` to confirm no other price-adjacent spot was missed; (3) re-run `flutter analyze`/`flutter test` independently on both `app/` and `seller_app/`; (4) re-verify the `seller_app` drift/red-green proof and the rest of DS-001's checklist are still intact (this bug's fix should not touch any of the 4 mirrored token files).

## Secondary finding (non-blocking, NOT part of this bug, discovered incidentally during the same QA pass — logged for a future fast-follow, not included in "Files Changed" above)

`seller_app/lib/features/dashboard/presentation/seller_dashboard_screen.dart:223` (`_summaryRow`, used by the "ยอดขาย" card's วันนี้/เดือนนี้/รวมทั้งหมด rows) overflows `RenderFlex` by ~9.4px at `textScaler 1.3` even with realistic, short data (`store.name = 'ร้านทดสอบ'`, no unusually long strings) and even under the real, production `ZokyTheme.light`. Verified this is **not** a DS-001 regression: (a) `git log` shows this file was created in SELLER-001 (`d96bc22`) and has never been touched by any DS-001 commit; (b) the same overflow (14px, larger because of Flutter's stock default type scale being slightly different) reproduces even with Flutter's out-of-the-box default `ThemeData()` with no WYN/ZOKY theme applied at all — the `Row(mainAxisAlignment: MainAxisAlignment.spaceBetween, children: [Text(label), Text(value, ...)])` pattern in `_summaryRow` has never had an `Expanded`/`Flexible` wrap on either child, so it was always going to overflow at large text scale regardless of which typography values are plugged in. Root cause and fix (wrap the value `Text` in `Flexible` with `TextOverflow.ellipsis`, or switch to a `Wrap`) is unrelated to DS-001's color/typography *values* — recommend a separate small ticket (e.g. `SELLER-001` fast-follow or fold into a future SELLER-app accessibility pass) rather than blocking DS-001 on it. QA did not write a permanent regression test for this since it is out of DS-001's own scope; the AI Debug Engineer picking this up later should re-derive the repro (`tests/_qa_scratch` pattern above, `FlutterError.onError` capture, `textScaler 1.3`, real `ZokyTheme.light`) rather than assume the numbers above without re-verifying.
