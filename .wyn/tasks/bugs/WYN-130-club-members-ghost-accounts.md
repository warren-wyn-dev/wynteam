# Bug Report — WYN-130

Status: fixed, awaiting QA + Founder to apply SQL to production
Owner: AI Debug Engineer

Bug: A Club's About > สมาชิก (Members) tab renders some rows as a bare "@" with no username and a "?" fallback avatar instead of a real member — Founder's own screenshot of "พื้นที่ของเรา" showed 4 such rows out of 8 members. Same "ghost account" symptom already fixed once for Discovery's `suggested_users()` RPC (schema.sql, 2026-09-05 entry) but never fixed for Clubs.

Reproduction: traced via code inspection (no direct production DB access from this session).

1. `AuthRepository.setDateOfBirth` — the *first* onboarding step — upserts a bare `public.profiles` row (id only, no `username`/`display_name`/`avatar_url`) before the Username step ever runs. A signup abandoned right there (app closed, never finished) leaves that row behind forever.
2. The `club_members` insert RLS policy ("Users can request or join clubs as themselves", `supabase/schema.sql`) checks only `auth.uid() = user_id`, `role = 'member'`, and the club's own `privacy` — nothing requires `profile_private.onboarding_completed`. Any authenticated session, onboarded or not, can insert an approved `club_members` row for a public Club (or a pending one for a Private Club).
3. `ClubRepository.fetchApprovedMembers`/`fetchPendingMembers` (`app/lib/features/club/data/club_repository.dart`) select `club_members` joined straight to `profiles(username, display_name, avatar_url)` with no filter for this.
4. `ClubMember.fromMap` (`app/lib/features/club/data/club_member.dart`) coalesces the null `username` to `''`. `ClubMembersTab`'s row builders render `Text('@${member.username}')` (→ bare `@`) and `AvatarCircle(fallbackText: member.username)` (→ `?` fallback) — exactly the screenshot.

Confirmed a local Postgres regression harness reproduces this precisely: a `club_members` row for a `profiles` row with no `profile_private.onboarding_completed = true` was returned by the pre-fix query shape with `username`/`display_name`/`avatar_url` all null (see `supabase/tests/wyn_130_club_members_ghost_accounts_test.sh`, run against the fix reverted — CHECK2/CHECK3/CHECK5 fail without it).

Root Cause: `club_members` never gates insertion (or its list queries) on onboarding completion, so a ghost `profiles` row (ambient consequence of the onboarding flow's own step ordering — same root cause `suggested_users()` already documents) can appear as a legitimate-looking, blank-profile row anywhere `club_members` is joined to `profiles` for display. The suggested_users() fix only patched Discovery's own RPC; Clubs' Members tab was a second, independent call site of the same underlying data shape and was never touched.

Fix: added a new `SECURITY DEFINER` RPC, `public.club_member_profiles(p_club_id, p_status, p_limit, p_offset)` (`supabase/schema.sql`, appended at end of file per the file's own "additive, end of file" convention for fixes like this — see its comment for the full reasoning). It re-implements the two `club_members` SELECT policies it stands in for ("Approved members can view other approved members" / "Club owners and admins can view pending requests") so no caller sees any row they couldn't already see today, and additionally excludes any row whose `profile_private.onboarding_completed` is not `true` — mirroring `suggested_users()`'s own filter.

A plain client-side `exists (...)` filter (like `suggested_users()` uses) was not possible here: `profile_private`'s own SELECT policy only lets a user read their OWN `onboarding_completed`, never a fellow Club member's, so a client-side embed filtered against it would silently return nothing for every row but the caller's own. The RPC is `SECURITY DEFINER` for exactly this reason — same mechanism `club_role()`/`club_insights()` already use to see across that same RLS boundary.

`ClubRepository.fetchApprovedMembers`/`fetchPendingMembers` (`app/lib/features/club/data/club_repository.dart`) now call this RPC instead of a plain `club_members` select+embed, via a shared private `_fetchMemberProfiles` helper. `ClubMember.fromMap`'s nested-map shape is unchanged (the RPC's flat row is reshaped into that same `{'profile': {...}}` map before calling it), so `ClubMember`/`ClubMembersTab`/`fetchMyMembership` (still a plain select — reads only the caller's own row, not affected by this bug) are all untouched.

Note: this does NOT stop a not-yet-onboarded account from joining a Club (that would be an RLS/insert-policy change to `club_members`, a bigger surface touching how far into onboarding a session is allowed to act — flagged here, not done, since the existing fix pattern (`suggested_users()`) was query-level exclusion, not blocking the underlying join). If Founder wants joining itself blocked pre-onboarding, that's a follow-up decision, not folded into this fix.

**Second call site, found proactively**: per `.wyn/learning/MISTAKES.md`'s own 2026-09-05 lesson ("a ghost-account fix at one call site doesn't mean the class of bug is gone elsewhere"), grepped the rest of the app for the same `profiles(username, display_name, avatar_url)` embed shape right after fixing the Members tab, before closing this bug out. Found one more: `ClubEventRepository.fetchAttendees()` (`app/lib/features/club/data/club_event_repository.dart`) backs the Event RSVP attendee bottom sheet the exact same way — a plain `club_event_rsvps` select embedding `profiles` directly. `validate_club_event_rsvp()` (schema.sql) already requires an *approved* club membership to RSVP at all, which is exactly the same gap `club_member_profiles()` exists to work around — so a ghost account that joined a public Club can RSVP to its Events too, and would show up here as the same bare "@" / "?" avatar row. Fixed the same way: a second RPC, `public.club_event_attendee_profiles(p_event_id, p_status)`, mirroring the "Approved club members can view event RSVPs" SELECT policy plus the same `onboarding_completed` exclusion; `ClubEventRepository.fetchAttendees` now calls it instead of the plain select+embed.

Files Changed:
- `supabase/schema.sql` — two new functions + grants, appended at end of file (not yet applied to production — see below): `public.club_member_profiles()` (Club Members tab) and `public.club_event_attendee_profiles()` (Event attendee sheet)
- `app/lib/features/club/data/club_repository.dart` — `fetchApprovedMembers`/`fetchPendingMembers` now call `club_member_profiles()` via a new shared `_fetchMemberProfiles` helper
- `app/lib/features/club/data/club_event_repository.dart` — `fetchAttendees` now calls `club_event_attendee_profiles()`

Regression Risk: low. Both RPCs are strictly additive (new functions, new grants) — no existing table, policy, or function is altered. The only behavior change for the four affected repository methods is that ghost rows (blank username/avatar, already useless in the UI) stop appearing; every real member/attendee's data and every existing permission boundary (who can see approved vs. pending members, who can see an Event's RSVPs) is unchanged, proven by CHECK1/CHECK4/CHECK6/CHECK7/CHECK10/CHECK12 above. **Not yet applied to production** — per this file's own "HOW TO APPLY: Supabase Dashboard → SQL Editor.
