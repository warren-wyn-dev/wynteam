# Bug Report — WYN-106

Status: fixed, pending QA re-verification
Owner: AI QA & Security found it; fixed directly in the same session (2026-09-04)

Fix applied: Option 1 from this report's own suggestion. `admin/app/globals.css` line 3 changed from `@custom-variant dark (&:is(.dark *));` to `@custom-variant dark (@media (prefers-color-scheme: dark));` -- no `.dark` class mechanism existed anywhere to react to, so switching the variant's activation strategy to match the token layer's own OS-preference mechanism fixes every `dark:`-prefixed class at once (today, still just the one call site this report identified). Verified via the same reproduction method this report used: rebuilt (`cd admin && npm run build`) and re-grepped the compiled CSS -- the rule now reads `@media (prefers-color-scheme:dark){.dark\:bg-white\/10{background-color:#ffffff1a}...}`, gated on the media query instead of the dead `:is(.dark *)` selector. Re-grepped the whole `admin/` tree for other `dark:`-prefixed classes per this report's own handoff note -- still only the one site, now fixed by the same change.
Not yet done: an actual browser/Playwright check with `prefers-color-scheme: dark` emulation (this report's own "do not re-approve on code-reading alone" note) -- deployed to production, but needs QA's own re-verification pass to close.

Bug: `Badge`'s `gray-tonal` variant (used for the "moderator" role pill on both `/users` search results and `/users/[id]`) uses `dark:bg-white/10` (added in commit `30b0a42`, "make Badge's gray-tonal variant dark-mode-safe") to avoid low-contrast text in dark mode. That `dark:` utility is **dead code in production** — it can never activate, so the exact contrast bug the commit claims to have fixed is still live.

Root Cause: two independent, non-interoperating dark-mode mechanisms exist in the same file (`admin/app/globals.css`) after today's re-skin (`ddf7987`):
1. `@custom-variant dark (&:is(.dark *));` (line 3, pre-existing shadcn scaffold) — makes every Tailwind `dark:` utility class compile to a selector that only matches when an ancestor element carries the literal class `dark` (confirmed in the compiled build output: `.dark\:bg-white\/10:is(.dark *){...}`).
2. `@media (prefers-color-scheme: dark) { :root { ... } }` (added today in `ddf7987`, design doc section 8's "OS preference is the primary activation mechanism since no manual toggle exists yet") — flips the CSS custom properties (`--background`, `--foreground`, `--primary`, etc.) directly on `:root`, with **no JS anywhere adding a `.dark` class** to `<html>`/`<body>` (checked `admin/app/layout.tsx`, `admin/lib/supabase/middleware.ts`, and grepped the whole `admin/` tree for `classList`/`matchMedia`/`next-themes`/`ThemeProvider` — none exist).

Net effect: in a user's OS/browser dark mode, semantic-token classes (`bg-background`, `text-foreground`, `bg-primary`, `bg-muted`, etc.) correctly flip to dark values because they resolve through the CSS variables mechanism (2). But any class using Tailwind's `dark:` variant prefix — which today is only `gray-tonal`'s `dark:bg-white/10` — resolves through mechanism (1) and never fires, because nothing ever adds `.dark` to the DOM.

So under OS/browser dark mode, the `gray-tonal` Badge renders as: `bg-zinc-200` (`#E4E4E7`, a literal light-gray Tailwind color, unaffected by either dark-mode mechanism since it isn't a semantic token) + `text-foreground` (which *does* flip, becoming `oklch(0.985 0 0)`, near-white). Near-white text on light gray background — a severe WCAG AA contrast failure, the same failure `30b0a42`'s commit message describes finding and fixing, except the fix itself is inert.

Reproduction (static analysis, confirmed reproducible without a browser):
1. `cd admin && npm run build`
2. `grep -o "\.dark\\:bg-white\\\\/10[^{]*{[^}]*}" .next/static/chunks/*.css` → shows `.dark\:bg-white\/10:is(.dark *){background-color:...}` — the selector's activation condition (`:is(.dark *)`) is visible directly in the compiled CSS.
3. `grep -rn "classList\|matchMedia\|documentElement\|next-themes\|ThemeProvider" admin --include="*.ts" --include="*.tsx"` (excluding `node_modules`) → no matches. Nothing in the app ever adds `.dark` to any element.
4. Therefore any real browser with OS/browser color scheme set to dark will apply `@media (prefers-color-scheme: dark)`'s `--foreground` (near-white) to the `gray-tonal` badge's text, while its `bg-zinc-200` background and the (never-firing) `dark:bg-white/10` stay exactly as in light mode.

Affected surface: `admin/app/(admin)/users/results.tsx` and `admin/app/(admin)/users/[id]/page.tsx` — the "moderator" role badge specifically (`admin`'s `ink-solid` and `user`'s `outline` variants are unaffected, since both use semantic tokens only, no literal `dark:`-prefixed utility).

Severity: Major — real, reproducible WCAG AA contrast failure live in production for any admin/moderator whose OS or browser is set to dark mode (a common default, not a rare edge case), on a badge that communicates role/permission level (a value staff rely on for judgement calls, e.g. before a Ban). Not Critical: does not block login, does not affect any destructive action's own confirmation UI (Ban/Remove dialogs use semantic-token `destructive` styling, not `dark:`, and are unaffected), does not expose secrets or break authorization, and the underlying data/text is still present in the DOM (a screen reader / text-selection workaround still works) — so this does not need to block current production usage, per QA scope note ("ไม่ต้อง block การใช้งานถ้าไม่ใช่ security-critical").

Suggested Fix (for AI Debug Engineer to evaluate, not yet applied): the architecture, not just this one class, needs reconciling — two options:
1. **Preferred, matches design doc section 8's own stated intent** ("OS preference via `prefers-color-scheme` is the primary activation mechanism for now"): change line 3 of `admin/app/globals.css` from `@custom-variant dark (&:is(.dark *));` to a media-query-based custom variant (e.g. `@custom-variant dark (@media (prefers-color-scheme: dark));`), so every existing/future `dark:` utility class in the codebase (not just this one) activates consistently with the CSS-variable mechanism already in place. Re-verify the `.dark` class block still works as a **future** override path per the doc's own note, or explicitly drop it if a manual toggle is never planned.
2. **Narrower, single-component patch**: stop using a literal Tailwind color (`bg-zinc-200`) + `dark:` override for `gray-tonal`, and instead add a proper semantic CSS custom property (e.g. `--badge-muted-bg`) to all three of `:root` / `.dark` / `@media (prefers-color-scheme: dark)` blocks in `globals.css`, matching every other token in the file — then reference it via `bg-[var(--badge-muted-bg)]` (or wire it through `@theme inline` as a new Tailwind color token) so it flips automatically like `bg-muted`/`bg-background` already do.

Option 1 is lower-risk and fixes the whole class of bug at once (any other `dark:`-prefixed class added in the future would have silently had the same problem); Option 2 is more surgical if there's a reason to keep the class-based `.dark` mechanism reserved for a future manual toggle.

Files Likely Affected by the Fix: `admin/app/globals.css`, `admin/components/ui/badge.tsx`

Regression Risk: low if Option 1 is chosen — currently exactly one class in the whole `admin/` tree uses the `dark:` variant (`gray-tonal`'s `dark:bg-white/10`), so switching the variant's activation strategy has a single, already-identified call site to re-verify; if Option 2, risk is contained to `Badge`/`globals.css` only.
