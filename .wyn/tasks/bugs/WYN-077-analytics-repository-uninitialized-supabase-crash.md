# Bug Report — WYN-077 (Analytics Repository crashes when Supabase isn't initialized)

Status: fixed (2026-09-02) — see Fix section below
Owner: AI Debug Engineer
Bug: `AnalyticsRepository`'s 4 call sites (`EmailAuthScreen`, `UsernameSetupScreen`, `CreateDropScreen`, `RootShell`) all construct it inline as `AnalyticsRepository(Supabase.instance.client)`. `Supabase.instance` is a singleton getter that throws synchronously if `Supabase.initialize()` was never called in the current process. Two of this app's *existing, currently-passing* widget tests never call `Supabase.initialize()` at all (by design — they only use `RecordingDropRepository`/`RecordingProfileRepository` fakes, deliberately keeping `CreateDropScreen` fully testable without touching Supabase), so `Supabase.instance` throws the moment `CreateDropScreen._share()` reaches the new `unawaited(AnalyticsRepository(Supabase.instance.client).logFirstCoreAction());` line added by this task. That throw happens while evaluating the argument to `unawaited()` — i.e. *before* `unawaited()`'s own error-silencing takes effect, and *inside* `_share()`'s existing `try { ... } catch (_) { setState(() => _errorMessage = '...'); }` block — so it gets caught by the same handler as a real publish failure, `Navigator.of(context).pop(true)` never runs (it's after the analytics line), and the screen never closes.
Reproduction: Run `app/test/create_drop_screen_test.dart`'s `'sharing a valid poll calls createPollDrop with the question, options, and selected duration'` test (line 221) or `'publishing from an opened draft creates the Drop and deletes the draft'` test (line 457). Both tap the post/submit button, expect the repository call to have recorded the right args (still true — the repository call happens *before* the new analytics line, so it still runs), and then `expect(find.byType(CreateDropScreen), findsNothing)` (asserting the screen popped). With this task's change, that last assertion fails: `Supabase.instance` throws synchronously (this test file has zero Supabase setup — confirmed via `grep -n "Supabase" app/test/create_drop_screen_test.dart`, no match), the outer `catch (_)` swallows it and sets `_errorMessage` instead, and the screen is still on-screen when the test checks. **Not run against a real Flutter toolchain in this session (none available in this sandbox, same limitation every prior WYN task has hit) — this is a static trace of deterministic Dart language behavior (synchronous exceptions during argument evaluation propagate before `unawaited()` can silence them, `Supabase.instance`'s uninitialized-throw is well-documented `supabase_flutter` behavior), not an empirically-run failure. Flag this trace to whoever fixes it and have them confirm with a real `flutter test` run before closing.**
Root Cause: This breaks the codebase's own established convention (`.wyn/learning/PATTERNS.md`: "optional repository param, real default") that every *other* dependency in these same 4 screens already follows specifically so tests can swap in a fake without ever touching `Supabase.instance` — see `CreateDropScreen`'s own `ProfileRepository? profileRepository` / `HashtagRepository? hashtagRepository` params, `RootShell`'s dozen `late final X ... = widget._x ?? X(client)` fields, etc. `AnalyticsRepository` was deliberately given the *simpler* "bare fire-and-forget, no DI, matches `PushNotificationService(PushTokenRepository(client)).initialize()` in `RootShell.initState`" shape instead (see this task's own commit message/`AnalyticsRepository`'s doc comment) — but that simpler shape is only safe in `RootShell` because `root_shell_test.dart`/`root_shell_guest_gate_test.dart` happen to call `initFakeSupabaseSession()` already (for unrelated reasons — reading `session.user`). `CreateDropScreen`'s tests have no equivalent safety net, and neither does `EmailAuthScreen`'s (that one's tests just happen not to tap Submit at all, per its own doc comment, so the same crash is latent there too — not currently visible as a test failure, but the same bug), nor does `UsernameSetupScreen` (no test file for it exists yet at all).
Fix (applied 2026-09-02): Exactly the direction QA suggested. `AnalyticsRepository` no longer takes a `SupabaseClient` constructor parameter at all (`const AnalyticsRepository()` now) — each `logX()` call funnels through the same private `_log()` helper, which resolves `Supabase.instance.client` **inside its own `try` block**, alongside the network `.insert()` call, so an uninitialized-Supabase throw is now just another "best-effort, swallow it" case, identical in kind to a failed network insert. All 4 call sites (`EmailAuthScreen`, `UsernameSetupScreen`, `CreateDropScreen`, `RootShell`) updated from `AnalyticsRepository(Supabase.instance.client).logX(...)` to `const AnalyticsRepository().logX(...)`. `EmailAuthScreen`/`UsernameSetupScreen` no longer need `package:supabase_flutter/supabase_flutter.dart` imported at all (removed — it was only there for this one call, and was otherwise unused, which `flutter analyze`'s `unused_import` lint would have flagged); `CreateDropScreen`/`RootShell` keep that import since they use `Supabase.instance.client` elsewhere for unrelated reasons.
Files Changed: `app/lib/features/analytics/data/analytics_repository.dart`, `app/lib/features/auth/presentation/email_auth_screen.dart`, `app/lib/features/auth/presentation/username_setup_screen.dart`, `app/lib/features/drop/presentation/create_drop_screen.dart`, `app/lib/features/root/presentation/root_shell.dart`
Tests: `app/test/create_drop_screen_test.dart`'s 2 identified tests are the regression coverage for this fix — **still not run against a real Flutter toolchain (none available in this sandbox, unchanged from Coding/QA's own notes)**, re-verified only by re-tracing the same code path by hand: `Supabase.instance` is no longer evaluated anywhere outside `_log()`'s own `try`, so the earlier failure mode (a synchronous throw landing in `_share()`'s outer catch before `Navigator.pop`) can no longer occur — the analytics call can now fail internally without ever throwing past `_log()` at all. `EmailAuthScreen`'s equivalent gap (no test taps Submit on the sign-up branch, per that test file's own pre-existing doc comment about `AuthRepository` not being fakeable/injectable) is **not closed by this fix** — out of scope here, would need `AuthRepository` itself to become injectable first, which is a separate, larger change nobody has asked for. Left as a known gap, not a regression this task introduced.
Regression Risk: Low — the fix is contained entirely inside `analytics_repository.dart`'s internals plus 4 one-line call-site updates; none of the surrounding business logic in any of the 4 screens changed. Still needs a real `flutter test`/`flutter analyze` run (by QA/CI, once a toolchain is available) to confirm empirically, since nothing in this task has been able to do that at any point.
