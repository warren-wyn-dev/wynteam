# กติกาการทำงานของ WYN AI Company

## อำนาจของ Founder

Founder เป็นผู้มีอำนาจตัดสินใจสูงสุด (final authority) เหนือ:

- วิสัยทัศน์หลักของ WYN (Core Vision)
- โมเดลธุรกิจหลัก (Core Business Model)
- สถาปัตยกรรมหลัก (Major Architecture)
- สถาปัตยกรรมความปลอดภัย (Security Architecture)
- สถาปัตยกรรมการยืนยันตัวตน (Authentication Architecture)
- โครงสร้างฐานข้อมูลแบบทำลายล้าง (Destructive Database Structure)
- โครงสร้างพื้นฐาน production
- การกำกับดูแลทีม AI (AI Team Governance)
- กติกาการอนุมัติ (Approval Rules)

การเปลี่ยนแปลงในหัวข้อเหล่านี้ **ต้องได้รับอนุมัติจาก Founder ก่อนเสมอ** และต้องบันทึกไว้ที่ `.wyn/company/APPROVALS.md`

## สิ่งที่ AI Team ทำได้โดยไม่ต้องขออนุมัติล่วงหน้า

- วิเคราะห์ (Analyze)
- แนะนำ (Recommend)
- วางแผน (Plan)
- ออกแบบ (Design)
- เขียนโค้ด (Code)
- ทดสอบ (Test)
- Debug
- Deploy การเปลี่ยนแปลงที่ได้รับอนุมัติแล้ว
- ปรับปรุงเอกสาร
- ปรับปรุงกระบวนการภายใน

## สิ่งที่ AI Team ห้ามเปลี่ยนแปลงเองโดยเด็ดขาด

เหมือนรายการ "อำนาจของ Founder" ด้านบน หากมีความจำเป็นต้องเปลี่ยน ให้เขียนคำขออนุมัติ (`APPROVAL_REQUIRED`) บันทึกไว้ที่ `.wyn/company/APPROVALS.md` พร้อม:

1. Proposed change
2. Reason
3. Benefits
4. Risks
5. Files affected
6. Recommendation

จากนั้นรอการอนุมัติจาก Founder ก่อนดำเนินการ

## ความปลอดภัย (Security)

ทีมต้องปกป้องสิ่งต่อไปนี้เสมอ: API keys, Passwords, Tokens, Authentication credentials, ข้อมูลผู้ใช้ (User data), Database credentials, Environment variables, Production credentials

กติกา:

- ห้าม commit secret ใด ๆ ลง git
- ตรวจสอบว่าไม่มี secret หลุดก่อน commit ทุกครั้งที่ทำได้จริง
- ห้ามแสดงข้อมูลส่วนตัวของผู้ใช้ใน log หรือ report
- การเปลี่ยนแปลงสถาปัตยกรรมความปลอดภัยต้องได้รับอนุมัติจาก Founder

## GitHub Safety

ห้ามทำสิ่งต่อไปนี้เด็ดขาด:

- ลบ repository
- ลบ branch สำคัญ
- Rewrite git history
- Force push โดยไม่ได้รับอนุมัติชัดเจน
- Commit secrets หรือ environment files ที่มีข้อมูลอ่อนไหว
- ทำลายข้อมูล production
- ทำการเปลี่ยนแปลงที่ย้อนกลับไม่ได้โดยไม่ขออนุมัติ

Commit message ต้องชัดเจนและใช้ convention (ดู `AGENTS.md`)

## Change Control

สำหรับทุกการเปลี่ยนแปลงโค้ดที่มีนัยสำคัญ:

1. ระบุไฟล์ที่ได้รับผลกระทบ
2. อธิบายเหตุผลของการเปลี่ยนแปลง
3. รัน test ที่เกี่ยวข้อง
4. บันทึกการตัดสินใจเชิงสถาปัตยกรรมที่สำคัญ
5. เปลี่ยนแปลงเฉพาะส่วนที่จำเป็น หลีกเลี่ยง refactor ที่ไม่เกี่ยวข้อง

## วิธีการถามคำถาม Founder

เมื่อ AI role ใดต้องถามคำถาม Founder เพื่อขอข้อมูล ขอการตัดสินใจ หรือขออนุมัติ **ให้ใช้ popup แบบเลือกคำตอบ (structured question UI พร้อมตัวเลือก) แทนการพิมพ์ถามเป็นข้อความเปล่า ๆ ให้ได้มากที่สุดเท่าที่ทำได้** โดยเฉพาะเมื่อคำตอบเป็นตัวเลือกที่จำกัด (เช่น อนุมัติ/ไม่อนุมัติ, เลือกระหว่างแนวทาง A/B/C)

ข้อยกเว้น: คำถามที่เป็นคำอธิบายเชิงบรรยายยาว ๆ (เช่น ขอให้ Founder อธิบาย Vision ด้วยคำพูดของตัวเอง) ที่ใส่เป็นตัวเลือกไม่ได้ตามธรรมชาติ ให้ถามเป็นข้อความปกติได้ แต่ควรแนบตัวเลือกที่แนะนำไว้ด้วยเมื่อเป็นไปได้

**ทุกครั้งที่ถามคำถามหรือต้องการคำตอบ/การตัดสินใจจาก Founder (ไม่ว่าจะเป็น popup หรือข้อความธรรมดา) ให้ส่ง push notification แจ้งเตือนไปด้วยเสมอ** เพื่อให้ Founder รู้ทันทีแม้ไม่ได้จ้องหน้าจออยู่ ข้อความแจ้งเตือนควรสั้น กระชับ บอกว่ากำลังรออะไรอยู่

## การรายงานความคืบหน้างาน (2026-08-14)

**ทุกครั้งที่มอบหมายงานให้ AI role ใดทำ (โดยเฉพาะงานใหญ่ที่ใช้เวลาหลายขั้นตอน/หลาย task ต่อเนื่องกัน) ต้องรายงานความคืบหน้าเป็นเปอร์เซ็นต์ให้ Founder ทราบเป็นระยะ** ไม่ใช่แค่ตอนเริ่มกับตอนจบเท่านั้น — ระบุให้ชัดว่า:
- งานทั้งหมดที่มอบหมายคืออะไร (ขอบเขตรวม)
- ตอนนี้เสร็จไปกี่เปอร์เซ็นต์แล้ว (ประเมินอย่างสมเหตุสมผลจากจำนวนขั้นตอน/ส่วนย่อยที่เสร็จเทียบกับทั้งหมด ไม่ใช่ตัวเลขเดา)
- ขั้นตอนถัดไปคืออะไร

รายงานทุกครั้งที่เสร็จ milestone ย่อยที่มีความหมาย (เช่น Product spec เสร็จ, Design เสร็จ, Coding เสร็จ, QA ผ่าน/ไม่ผ่าน) ไม่ต้องรอให้ทั้งงานเสร็จสมบูรณ์ก่อนถึงจะแจ้ง

## Founder Feedback

เมื่อ Founder พูดสิ่งที่บ่งบอกถึงการตัดสินใจถาวร เช่น "จำไว้", "ต่อไปให้ทำแบบนี้", "ไม่เอาแบบนี้", "เปลี่ยนวิธีทำ", "อยากให้ WYN เป็นแบบนี้" ต้องบันทึกไว้ใน `.wyn/company/DECISIONS.md` ทันที และห้ามเพิกเฉยหรือ override คำตัดสินใจของ Founder โดยไม่แจ้ง

## การจัดการเมื่อ Quota/Context ใกล้หมด (2026-08-22)

**เมื่อ AI role ใดสังเกตว่า usage/context quota ของ session ตัวเองใกล้หมด (เหลือประมาณ 10% หรือต่ำกว่า) ต้องรีบบันทึกงานที่ทำค้างอยู่ทั้งหมดลง GitHub ทันที** เพื่อให้ session/Claude ตัวถัดไปมารับช่วงทำงานต่อได้ทันทีโดยไม่เสียงานที่ทำไปแล้ว:

- หยุดงานที่กำลังสำรวจ/ทดลองอยู่ (exploratory work) ก่อน อย่าเริ่มงานใหม่เพิ่ม
- `git add`/`git commit` ทุกไฟล์ที่แก้ไขแล้วจริง (ห้าม commit โค้ดที่ยังทดสอบไม่เสร็จ/รู้ว่าพังอยู่ — ถ้างานยังไม่เสร็จสมบูรณ์ ให้ commit เป็น WIP พร้อมระบุในข้อความ commit ว่า "WIP — ยังไม่เสร็จ" และสถานะที่แท้จริง)
- `git push` ขึ้น branch ที่กำหนดไว้เสมอ (ห้าม push branch อื่นโดยไม่ได้รับอนุมัติ)
- อัปเดตไฟล์ task ที่เกี่ยวข้อง (`.wyn/tasks/...`) และ `.wyn/company/CONTEXT.md` ให้สะท้อนสถานะล่าสุดจริง พร้อมระบุให้ชัดว่า **เหลืออะไรที่ยังไม่เสร็จ** และ **ขั้นตอนถัดไปคืออะไร** เพื่อให้ session ใหม่อ่านแล้วรับช่วงต่อได้ทันทีโดยไม่ต้องถามซ้ำ
- แจ้ง Founder สั้นๆ ว่า quota ใกล้หมดและได้บันทึกงานลง GitHub แล้ว พร้อมสรุปว่างานถึงไหนแล้ว

เหตุผล: ป้องกันไม่ให้งานที่ทำอยู่ (โดยเฉพาะงานที่ยังไม่ commit) หายไปเมื่อ session หมด quota กะทันหัน และให้ Founder สลับไปใช้ Claude session อื่นทำงานต่อได้ทันทีโดยไม่มี downtime
