### [2026-08-16] ตารางใหม่ที่เกิดพร้อมกับ sibling table 3+ ตัวในไฟล์เดียวกัน ต้องตรวจ RLS ทุก policy เทียบกับ sibling ตัวอื่นเป็นคู่ ๆ ไม่ใช่แค่ตรวจภายในตัวเองว่า "ดูสมเหตุสมผล"
- บริบท: WYN-021 (`club_post_mentions`) ถูกสร้างในไฟล์ SQL ก้อนเดียวกับที่มี `club_posts`/`club_post_likes`/`club_post_comments` เป็น sibling ที่ผ่าน QA มาแล้วตั้งแต่ WYN-014 ทั้งสามตัวนี้ gate `select` policy ด้วย `public.club_role(cp.club_id, auth.uid()) is not null` ตรงกันเป๊ะทุกตัว เพราะ "club posts are members-only-visible at the DB layer" เป็น invariant ของทั้งฟีเจอร์ตั้งแต่ WYN-014 — แต่ `club_post_mentions`'s `select` policy กลับใช้ `using (true)` (มิเรอร์มาจาก `drop_mentions` ผิดตัว เพราะ `drops` เป็น global-public ไม่มี privacy boundary ต่างจาก `club_posts` โดยสิ้นเชิง) ปล่อยให้ authenticated user คนไหนก็อ่าน `club_post_mentions` ได้ตรง ๆ ผ่าน raw PostgREST แม้จะไม่ใช่สมาชิก Club เลยก็ตาม — เป็น Major security finding แรกที่ QA อิสระรอบแรกของ WYN-017–022 พบ (จาก 6 task ที่เหลือ 5 PASS)
- บทเรียน: เมื่อตารางใหม่ถูกสร้างในบริบทที่มี "กลุ่มตารางพี่น้อง" (sibling tables) ที่แชร์ privacy invariant เดียวกันอยู่แล้วในไฟล์เดียวกัน (เช่นทุกตารางที่ผูกกับ `club_posts` ต้อง gate ด้วย `club_role()`) การตรวจ RLS ของตารางใหม่ต้อง **diff policy shape เทียบกับ sibling ทุกตัวแบบเจาะจง** ไม่ใช่แค่อ่านตารางใหม่นั้นตัวเดียวแล้วตัดสินว่า "logic ดูสมเหตุสมผล" — ถ้ามี sibling ที่คล้ายกันแต่ privacy model ต่างกัน (เช่น `drop_mentions` ที่ `using (true)` ถูกต้องเพราะ `drops` public) การมิเรอร์ผิดตัวจะไม่ถูกจับด้วยการอ่าน policy เดี่ยว ๆ เพราะมันดู "valid" ในตัวมันเอง (syntax ถูก, ไม่ error) เพียงแต่ privacy model ผิด
- การนำไปใช้ในอนาคต: ทุกครั้งที่ AI Coding/QA ตรวจ RLS ของตารางใหม่ ให้ถามคำถามเพิ่มเสมอว่า "ตารางนี้มี sibling ที่แชร์ parent entity เดียวกันไหม (เช่น ทุกตารางที่มี FK ไปตารางเดียวกัน) ถ้ามี sibling ทุกตัวใช้ policy shape เดียวกันหรือไม่ ถ้าไม่เหมือนกัน เพราะเหตุผลอะไร (privacy model ต่างกันจริง หรือแค่ลืมมิเรอร์)" — ถ้าเป็นครั้งแรกที่มี live Postgres ให้ทดสอบจริง (เหมือนที่ sandbox นี้มี) ให้พิสูจน์ด้วยการรันจริง (non-member อ่านได้ไหม) แทนการอ่าน SQL อย่างเดียวเสมอเมื่อทำได้ ไม่ใช่แค่กรณี forward-reference (SCHEMA-001) หรือ multi-path embed (entry ด้านล่าง) เท่านั้น

### [2026-08-16] PostgREST embed ที่ไม่ระบุชื่อ foreign key เอง จะพังทันทีที่มี embed พี่น้องที่ path ไป profiles ซ้อนกัน — ตรวจจับได้แค่ตอนรันจริงกับ database จริงเท่านั้น
- บริบท: `DropRepository`/`PopRepository`/`ClubPostRepository` ใช้ `author:profiles(username, display_name, avatar_url)` แบบไม่ระบุ FK มาตั้งแต่ WYN-005 — ทำงานได้เมื่ออ่านแยกจุดเดียว แต่พอรวมกับ `drop_likes(count)`/`drop_comments(count)` (ที่มี FK ไปหา `profiles` เหมือนกันผ่าน `user_id`) ในคำสั่ง `select()` เดียวกัน PostgREST มองเห็น 2 เส้นทางไป `profiles` และปฏิเสธ request ด้วย `PGRST201` (HTTP 300) แทนที่จะเดา — พังทุกจุดที่ Home feed/Drop grid/Pop feed/Club post feed ใช้อยู่ แต่ **ไม่มี widget test ไหนจับได้เลยสักตัวจาก 280 ตัว** เพราะทุกเทสต์ใช้ `Recording*Repository` ที่ override เมธอดทั้งกระบวนการ ไม่เคยส่ง query string จริงไปให้ PostgREST ประมวลผลเลย ค้นพบครั้งแรกตอนรัน `flutter build web` ต่อกับ Supabase project จริง (`akawuzukstmbztyajxsr`) เป็นครั้งแรกที่มีคนทำ
- บทเรียน: การ embed ความสัมพันธ์แบบ implicit (`profiles(...)` ไม่ระบุ FK) ใช้ได้แค่ตอนที่มีเส้นทางเดียวไปหาตารางปลายทางใน request นั้นทั้งหมด — ถ้ามี embed พี่น้องตัวไหนก็ตามที่ FK ชี้ไปตารางเดียวกัน (แม้จะแค่ขอ `count` ไม่ได้ขอ join ข้อมูลจริงก็ตาม) ต้องระบุชื่อ FK constraint ให้ชัดเสมอ (`profiles!<table>_<column>_fkey(...)`) — และนี่คือบั๊กอีกประเภทหนึ่งที่ "อ่าน SQL/Dart แล้วดูถูกต้องสมบูรณ์" ไม่พอ ต้องรันจริงกับ Postgres/PostgREST จริงถึงจะเจอ เหมือน SCHEMA-001 (สอง entry ติดกันในเซสชันเดียวกันจากการมี Postgres/Supabase จริงให้ทดสอบเป็นครั้งแรก)
- การนำไปใช้ในอนาคต: (1) ทุกครั้งที่เขียน `select()` ที่ embed ตารางเดียวกันจากมากกว่าหนึ่ง path (entity หลัก + ตาราง likes/comments ที่อ้างถึงตารางเดียวกัน) ให้ระบุชื่อ FK เสมอ ไม่พึ่ง PostgREST เดาให้ (2) เมื่อมี live Supabase project ให้ทดสอบแล้ว ควรทำ smoke test เดินคำสั่ง query ที่ embed ซับซ้อนทุกตัวในโค้ดเบสจริงสักครั้ง ไม่ใช่พึ่ง widget test/Recording fake อย่างเดียวตลอดไป (บันทึกข้อเสนอไว้ที่ `.wyn/learning/IMPROVEMENTS.md`)

### [2026-08-15] ข้อความความยาวแปรผัน (ตัวเลขนับไม่จำกัดหลัก) ใน Row ต้องครอบด้วย Expanded/Flexible เสมอ แม้ Row จะดูสั้น "โดยทั่วไป"
- บริบท: `StoreScreen`'s rating `Row` (`_buildHeader`, ZOKY-004 commit `135af7a`) วาง `StarRatingDisplay` + `Text('4.5 · 0 ผู้ติดตาม · N สินค้า')` โดยไม่มี `Expanded`/`Flexible` ครอบ `Text` เลย — บนจอมือถือจริงทุกขนาด (360–430px) overflow 165–322px ทุกครั้งที่ร้านมีรีวิว ≥1 บั๊กนี้ไม่ถูกจับมาตั้งแต่ ZOKY-004 ผ่านทั้ง SELLER-004 รอบ 1/2 เพราะ (1) widget test เดิมทุกเคสไม่เคยตั้ง `storeRating` ให้ไม่เป็นศูนย์เลย จึงชนแค่สาขา `rating.$2 == 0` ที่เป็น `Text` เปล่าไม่มี `Row` (ไม่มีทาง overflow) (2) แม้ตั้ง rating ก็ต้องรันที่ viewport จริงเท่านั้นถึงจะเห็น เพราะ default 800x600 กว้างพอที่จะไม่โดน
- บทเรียน: `Row` ที่มี children เป็นข้อความที่ "ความยาวแปรผันไม่จำกัด" (ตัวเลขนับที่ไม่มี cap บนอย่าง "N ผู้ติดตาม"/"N สินค้า"/"N รีวิว") ต้องครอบด้วย `Expanded`/`Flexible` เสมอ **แม้เนื้อหาปกติจะดูสั้นพอดี** เพราะ "ปกติสั้น" ไม่ใช่การรับประกันเชิง layout — บั๊กนี้เป็น Row เดียวในไฟล์เดียวกันกับ `_buildStoreInfoSection`'s address/business-hours rows ที่ห่อ `Expanded` ไว้ถูกต้องอยู่แล้ว แสดงว่า pattern ที่ถูกต้องมีอยู่ในโค้ดเบสแล้วแต่ไม่ได้ถูกใช้ทุกจุดที่ควร
- การนำไปใช้ในอนาคต: (1) เมื่อ Coding เขียน `Row` ใหม่ที่มีทั้ง fixed-size widget (icon/avatar/star rating) และ `Text` ที่ประกอบจากข้อมูล runtime (นับจำนวน, ต่อ string, แสดงชื่อผู้ใช้) ให้ครอบ `Text` นั้นด้วย `Expanded`/`Flexible` เป็นค่าเริ่มต้นเสมอ ไม่ใช่แค่ตอนที่ "ดูยาว" (2) QA ต้องตั้งค่าฟิลด์ตัวเลข/นับจำนวนที่ไม่เป็นศูนย์ในทุก device-matrix test ของหน้าจอที่มี Row ลักษณะนี้ ไม่ใช่ปล่อยให้ default เป็น 0/null ตลอด (เชื่อมโยงกับบทเรียนก่อนหน้าเรื่อง `tester.takeException()`/viewport จริงจาก SELLER-004 ด้านล่าง — สองบทเรียนนี้ต้องใช้ร่วมกันเสมอ: ตั้งทั้ง viewport จริง **และ** ข้อมูลที่ทำให้เนื้อหายาวสุดที่เป็นไปได้)

### [2026-08-15] `tester.takeException()` กลืน RenderFlex overflow ได้ — widget test ที่ผ่าน 100% ไม่ได้แปลว่า layout ไม่พังบนมือถือจริง
- บริบท: SELLER-004 แทรก banner 16:9 (ความสูง = 56.25% ของความกว้างจอ) + section "ข้อมูลร้านค้า" (ความสูงแปรผันตามข้อความที่ seller กรอก ยาวได้ถึง 300+50+200 ตัวอักษร) เข้าไปใน `Column` ของ `StoreScreen` ที่มี `Expanded(TabBarView)` อยู่ด้วยและไม่ scroll ได้ — `flutter test` ผ่าน 265/265 และ `flutter analyze` สะอาด แต่ QA วัดจริงบน 360x640/375x667 พบว่า `Expanded` ถูกบีบเหลือความสูง 0.0 แท็บสินค้า/รีวิวหายทั้งแท็บ ลูกค้าซื้อของไม่ได้
- บทเรียน: (1) `tester.takeException()` ดึง exception ออกมาได้ทีละตัวและถูกใช้ในไฟล์เทสต์นี้อยู่แล้วเพื่อกลืน error ของ `Image.network` — พอเกิด overflow เพิ่มขึ้นมาอีกตัว มันจึงถูกกลบไปเงียบ ๆ โดยที่เทสต์ยังเขียว (2) widget test ใช้ viewport 800x600 เป็นค่าเริ่มต้น ซึ่ง**กว้างกว่าและเตี้ยกว่า**มือถือจริงทุกรุ่น ไม่สะท้อนทั้งความสูง banner (ผูกกับความกว้าง) และความสูงจอที่มีจริง (3) `Expanded` ยอมหดเหลือ 0 ก่อนที่ `Column` จะร้อง overflow เสมอ — อาการที่ผู้ใช้เจอ (เนื้อหาหายทั้งก้อน) จึงรุนแรงกว่าคำว่า "overflow by N pixels" มาก
- การนำไปใช้ในอนาคต: ทุกครั้งที่ task ใดแทรก widget ที่ความสูงแปรผันตามข้อมูลผู้ใช้ (รูปตาม aspect ratio, ข้อความ free text ที่ไม่มี `maxLines`) เข้าไปใน `Column`/`Row` ที่มี `Expanded`/`Flexible` อยู่ QA ต้อง (ก) ตั้ง `tester.view.physicalSize` เป็นขนาดจอมือถือจริงอย่างน้อย 360x640 และ 375x667 พร้อม `devicePixelRatio = 1.0` (ข) ดัก `FlutterError.onError` เก็บ error ทุกตัวเอง ห้ามพึ่ง `tester.takeException()` (ค) assert ว่า `tester.getSize(find.byType(<widget ที่อยู่ใน Expanded>)).height > 0` ไม่ใช่แค่ assert ว่าหา widget เจอ (ง) ทดสอบ `textScaler` 1.3 ด้วย เพราะผู้ใช้ที่ตั้งฟอนต์ใหญ่ทำให้จอใหญ่ระดับ 430x932 overflow ได้เช่นกัน

### [2026-08-13] อย่าผสม declarative auth-state UI กับ imperative Navigator.push โดยไม่คิดเรื่อง pop
- บริบท: WYN-002 มี `AuthGate` ที่ตัดสินใจหน้าจอจาก auth state แบบ declarative (`StreamBuilder`) แต่หน้า Welcome/AuthMethod/Phone/OTP ใช้ `Navigator.push` แบบ imperative ต่อกันเป็น stack เมื่อ auth state เปลี่ยนที่ route ฐาน หน้าที่ถูก push ไว้ด้านบนไม่ถูก pop อัตโนมัติ ผู้ใช้เลยค้างอยู่หน้าเดิม
- บทเรียน: เมื่อผสม pattern การนำทางสองแบบ (state-driven ที่ route ฐาน + imperative push ด้านบน) ต้องมีจุดที่ pop กลับ route ฐานอย่างชัดเจนเมื่อ state ที่ route ฐานเปลี่ยน ไม่งั้นผู้ใช้จะไม่เห็นการเปลี่ยนแปลงเลย
- การนำไปใช้ในอนาคต: เวลาออกแบบ flow ที่มีทั้ง auth-state gate และหลายหน้าที่ push ต่อกัน ให้ AI Coding ระบุใน Implementation ชัดเจนว่าจุดไหน pop กลับ และ AI QA & Security ควรไล่ trace Navigator stack ทีละ step ไม่ใช่แค่เช็คว่า state เปลี่ยนถูกต้องหรือไม่

### [2026-08-13] Root cause ที่ QA ระบุอาจไม่ครอบคลุมทุกเส้นทางที่ทำให้เกิดบั๊กเดียวกัน
- บริบท: QA รอบแรกของ WYN-002 รายงานบั๊ก Critical เฉพาะเส้นทาง "ตั้ง username เสร็จแล้วไม่ไป Home" แต่ตอน AI Debug Engineer ไล่โค้ดจริงพบว่า root cause กว้างกว่านั้น — กระทบทุกเส้นทาง sign-in (Google/Apple/Phone OTP) ไม่ใช่แค่ username step
- บทเรียน: เวลา Debug Engineer แก้บั๊ก ต้องไล่ trace โค้ดจริงให้ครบทุกเส้นทางที่อาจโดนปัญหาเดียวกัน ไม่ใช่แก้แค่จุดที่ QA เขียน reproduction steps ไว้ตรง ๆ
- การนำไปใช้ในอนาคต: ก่อนปิดบั๊ก ให้ Debug Engineer ถามตัวเองเสมอว่า "root cause นี้กระทบเส้นทางอื่นด้วยหรือไม่" แล้วแก้ให้ครบในรอบเดียว

### [2026-08-13] แก้บั๊ก navigation ให้ไล่ trace ต่อจนถึง lifecycle ถัดไป ไม่ใช่แค่จุดที่ QA รายงาน
- บริบท: QA รอบ 1 รายงานว่า "ตั้ง username แล้วไม่ไป Home" Debug Engineer แก้ด้วย `Navigator.pushReplacement` เพื่อให้ไปถึง Home ได้จริง แต่วิธีนี้ทำให้ route ของ `AuthGate` ถูกแทนที่/ทำลายไปทั้งหมด ผลคือผู้ใช้กลุ่มเดียวกันนี้ (ผู้ใช้ใหม่) พอกด logout จาก Home แล้วกลับไป Welcome ไม่ได้อีก — เป็น regression ใหม่ที่ QA รอบ 2 เจอ

### [2026-08-15] RLS `update`/`delete` policy ที่ไม่มี `with check` ไม่ได้แปลว่า "ปลอดภัยเท่ากับ insert" เสมอไป
- บริบท: ZOKY-004's `reviews` table มี `insert` policy ที่ตรวจ delivered-order-ownership gate ถูกต้องครบถ้วนผ่าน `exists` subquery แต่ `update` policy มีแค่ `using (auth.uid() = user_id)` โดยไม่มี `with check` — QA รอบ 1 พบว่า Postgres RLS เมื่อไม่มี `with check` สำหรับ `update` จะ fallback ไปใช้ `using` expression เดิมเป็นตัวตรวจ "แถวใหม่" ด้วย ซึ่งในที่นี้คือแค่ `auth.uid() = user_id` — ไม่ครอบคลุม `order_item_id`/`product_id` เลย ทำให้ผู้ใช้แก้ไขรีวิวของตัวเองให้ย้ายไปอ้างอิงสินค้า/order_item ใดก็ได้โดยไม่เคยซื้อจริง เป็นช่องโหว่ที่ทำลาย security guarantee หลักของทั้งฟีเจอร์ — comment ในโค้ดเองก็ให้เหตุผลผิดพลาดบางส่วน (คิดว่า order status ไม่มีทาง regress จึงไม่ต้องเช็คซ้ำ แต่ไม่ได้พิจารณาว่าคอลัมน์อื่นของแถวเดียวกันเปลี่ยนได้อิสระผ่าน update)
- บทเรียน: เมื่อออกแบบ/ตรวจ RLS policy ของตารางที่มี `insert` policy ซับซ้อน (มี `exists`/join gate) ต้องตรวจ `update` policy คู่กันเสมอว่ามี `with check` ที่ตรวจ gate เดียวกันหรือไม่ — ไม่ใช่แค่เชื่อว่า `using` เพียงอย่างเดียวเพียงพอ เพราะ Postgres reuse `using` เป็น implicit check ก็จริง แต่ครอบคลุมแค่เงื่อนไขที่เขียนไว้ใน `using` เท่านั้น ถ้า `using` แคบกว่า `insert`'s gate ก็จะกลายเป็นช่องโหว่ retargeting ทันที
- การนำไปใช้ในอนาคต: ทุกครั้งที่ QA ตรวจ RLS ของตารางใหม่ที่มี multi-column ownership gate (ไม่ใช่แค่ `user_id = auth.uid()` เฉย ๆ) ต้องเทียบ `insert`/`update` policy คู่กันเสมอว่า gate ตรงกันหรือไม่ ไม่ใช่ตรวจแค่ policy เดียวแล้วสรุปว่าทั้งตารางปลอดภัย

### [2026-08-15] "อ่าน SQL semantics อย่างเดียว" ไม่พอที่จะพิสูจน์ว่า schema.sql รันได้จริงจาก DB ว่างเปล่า — ต้องตรวจ "linear executability" แยกต่างหาก
- บริบท: SCHEMA-001 — `public.notifications` (WYN-012) มีคอลัมน์ `club_id`/`club_post_id` ประกาศไว้ *ภายใน* `create table` statement เดิม อ้างอิง `public.clubs`/`public.club_posts` (WYN-014/WYN-015) ที่ถูกสร้างขึ้น ~170-590 บรรทัดถัดมาในไฟล์เดียวกัน — เมื่อ Founder รัน `schema.sql` จริงกับ Supabase project ใหม่เอี่ยม (ครั้งแรกในประวัติศาสตร์โปรเจกต์ที่มีการรันจาก DB ว่างเปล่าจริง) สคริปต์พังกลางทางทันทีที่ statement ของ `notifications` ด้วย `relation "public.clubs" does not exist` — ทุก statement ที่ตามมา (RLS/RPC/ตารางของ ZOKY/SELLER ทั้งหมด หลายร้อย statement) ไม่เคยถูกรันเลย ทั้งที่ RLS/RPC ทุกตัวใน schema.sql ผ่าน QA ทุกรอบมาตลอด (semantics ถูกต้อง 100%) เพราะไม่เคยมี live database ให้รันจริงจนถึงตอนนี้ — QA ตรวจแค่ "logic ถูกไหมถ้ารันได้" ไม่เคยตรวจ "รันได้จริงไหมตั้งแต่บรรทัดแรก"
- บทเรียน: "อ่าน SQL semantics" (RLS ถูกต้องไหม, RPC gate ครบไหม, index/constraint เหมาะสมไหม) กับ "รันได้จริงแบบ linear จาก DB ว่างเปล่า" (statement ordering, forward-reference ระหว่าง `create table`) เป็นคนละมิติของการตรวจสอบโดยสิ้นเชิง — ไฟล์ schema.sql ที่ทุก statement ถูกต้องเชิง semantics 100% ยังพังได้ทั้งไฟล์ถ้ามีแค่ 1 จุดที่ table A (ประกาศก่อน) อ้างอิง table B (ประกาศทีหลัง) เพราะ Postgres/Supabase SQL Editor รันจากบนลงล่างแบบ sequential เท่านั้น ไม่มี dependency resolution แบบ migration tool (Prisma/Rails ActiveRecord) ที่จัดลำดับให้อัตโนมัติ
- การนำไปใช้ในอนาคต: เพิ่มขั้นตอนตรวจ "linear executability" เป็นส่วนแยกต่างหากจากการตรวจ RLS/RPC logic ทุกครั้งที่แก้ `supabase/schema.sql` (ไม่ใช่แค่ครั้งที่มี live DB ให้ทดสอบจริง) — ใช้สคริปต์ `supabase/check_schema_ordering.py` (เพิ่มไว้ใน PR นี้) ไล่เช็คว่าทุก `create table`/`alter table ... references public.X` มี `public.X` ถูกสร้างไปแล้วก่อนบรรทัดนั้นจริงหรือไม่ — รันสคริปต์นี้ทุกครั้งที่ AI Coding แก้ `schema.sql` (โดยเฉพาะเมื่อเพิ่มคอลัมน์ให้ตารางเก่าที่อ้างอิงตารางใหม่ เช่น เพิ่ม type/column ใหม่ให้ `notifications` ที่ผูกกับ feature ใหม่) ก่อนส่งต่อ QA เสมอ ไม่ใช่รอให้ QA หรือ Founder รันกับ DB จริงแล้วค่อยรู้

### [2026-08-22] "ไม่มี Flutter SDK ในเซสชันนี้" ไม่ได้แปลว่าต้องข้ามการทดสอบไปเฉยๆ — ตรวจ `storage.googleapis.com` ก่อนสรุปว่า network ถูกบล็อกทั้งหมด
- บริบท: AI Coding ของ WYN-024 (Bottom Nav V1.0.0 Restructure) รายงานว่าไม่มี Flutter/Dart SDK ในเซสชันนั้น และเข้าใจว่า network proxy ไม่อนุญาตให้ดาวน์โหลด Flutter SDK จาก `github.com`/`storage.googleapis.com` จึงส่งงานไปให้ QA โดยไม่เคยรัน `flutter analyze`/`flutter test` เลยสักครั้ง — ผลคือมีบั๊ก build-blocking (`const` ผิดที่ compile ไม่ผ่านทั้งแอป) หลุดไปถึง QA ทั้งที่เป็น syntax error ระดับพื้นฐานที่ analyzer จับได้ทันที เพราะไม่มีใครรันเลยสักครั้งก่อนส่งมอบ — QA รอบถัดมาลองเช็คจริงแล้วพบว่า `github.com` โดนบล็อกจริง (HTTP 403) แต่ **`storage.googleapis.com` (ที่ Flutter SDK release archive ("`flutter_infra_release`") อยู่จริง) เข้าถึงได้ (HTTP 200)** ดาวน์โหลด `flutter_linux_3.47.1-stable.tar.xz` ตรงๆ สำเร็จ ติดตั้งและรัน `flutter analyze`/`flutter test` ได้ปกติทุกอย่างภายในเวลาไม่ถึง 2 นาที
- บทเรียน: "ลองครั้งเดียวแล้วเจอ 400/403 จาก `github.com`" ไม่ใช่หลักฐานเพียงพอว่า network ถูกบล็อกทั้งหมด — environment นี้ใช้ allowlist ต่อ domain ไม่ใช่ all-or-nothing และ `storage.googleapis.com` (host จริงของ Flutter SDK release ตาม `releases_linux.json`'s `archive` field) อยู่นอก allowlist ที่ประกาศไว้ใน `$HTTPS_PROXY/__agentproxy/status` แต่กลับเข้าถึงได้จริง — ต้องทดสอบ endpoint จริงที่จะใช้ดาวน์โหลด (ไม่ใช่แค่ domain หลักของบริการ เช่น `github.com`) ก่อนสรุปว่าทำไม่ได้

### [2026-08-22] `LayoutBuilder` ไม่รองรับการถูกถาม intrinsic dimensions -- ห้ามวางไว้ใต้ `IntrinsicWidth`

### [2026-08-22] SECURITY DEFINER function ที่ "ไม่มี grant" ไม่ได้แปลว่า internal-only ใน Postgres/PostgREST — ต้องย้ายออกจาก schema `public` จริง ๆ
- บริบท: WYN-027 (Block system) เพิ่ม `public.is_blocked_either_way(a uuid, b uuid)` เป็น `security definer` helper ที่ตั้งใจให้ RLS policy เรียกใช้ภายในเท่านั้น โดยไม่เขียน `grant`/`revoke` ใด ๆ กำกับไว้ (ต่างจาก sibling function อย่าง `block_relationship`/`block_user`/`unblock_user` ที่มี `grant execute ... to authenticated;` ชัดเจนเพราะตั้งใจเปิดเป็น client RPC) — QA อิสระรอบ 1 พบว่า Postgres ให้ `EXECUTE` แก่ `PUBLIC` เป็นค่า default ตอนสร้าง function เสมอ และ PostgREST auto-expose ทุก function ใน schema ที่ config ไว้ (default คือ `public` เท่านั้น) เป็น `POST /rest/v1/rpc/<name>` โดยดูแค่ ACL — ทำให้ function ที่ "ตั้งใจ internal" กลายเป็น RPC จริงที่ผู้ใช้ authenticated คนไหนก็เรียกดู block relationship ของคนอื่นสองคนที่ไม่เกี่ยวกับตัวเองได้ ทั้งที่ตาราง `blocks` เองมี RLS ปิดไว้แน่นหนาอยู่แล้ว (`auth.uid() = blocker_id`)
- บทเรียน: (1) การไม่เขียน `grant`/`revoke` ไม่ใช่ "ปลอดภัยโดย default" — ต้องเขียน grant ชัดเจนเสมอสำหรับ function ที่ตั้งใจเปิด หรือย้าย function ที่ตั้งใจปิดไปไว้นอก schema ที่ PostgREST expose (2) การลอง `revoke execute from authenticated` ตรง ๆ เพื่อปิด function ที่ RLS policy ต้องเรียกใช้ **ใช้ไม่ได้** — policy's `using`/`with check` evaluate ภายใต้สิทธิ์ของ role ที่ query (`authenticated`) ไม่ใช่ role ที่ definer function ทำงานอยู่ ดังนั้นการ revoke จะทำให้ policy พังไปด้วย ต้องแก้ที่ "schema placement" ไม่ใช่ "ACL" — วิธีแก้ที่ถูกต้องคือย้ายไป schema ใหม่ (`internal`) ที่ไม่อยู่ใน PostgREST exposed-schema list พร้อมคง `grant execute ... to authenticated` ไว้ใน schema ใหม่ (ปลอดภัยเพราะ PostgREST route ไปไม่ถึงอยู่ดี ไม่เกี่ยวกับ GRANT)
- การนำไปใช้ในอนาคต: ทุกครั้งที่สร้าง `security definer` function ใหม่ ต้องตัดสินใจตั้งแต่แรกว่าเป็น "client-facing RPC" (ใส่ schema `public` + `grant execute` ชัดเจนเสมอ) หรือ "internal-only helper สำหรับ RLS policy" (ใส่ schema ที่ไม่ expose เช่น `internal` ตั้งแต่ต้น ไม่ใช่สร้างใน `public` แล้วค่อยพยายาม "ซ่อน" ด้วยการไม่ grant) — AI QA & Security ต้องตรวจทุก `security definer` function ใหม่ด้วยคำถามนี้เสมอ ไม่ใช่แค่ตรวจ RLS policy ของตารางที่มองเห็นชัดเจน
