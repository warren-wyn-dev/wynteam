- Common mistakes เพิ่มเติม (2): **QA เองก็เทียบ spec ไม่ครบทุกช่องทาง (WYN-005 รอบ 1 → รอบ 2)** — QA รอบ 1 เทียบ Requirements + Design Components ทีละบรรทัดแล้วจับบั๊ก Like Comment ได้ แต่ไม่ได้ไล่ "Acceptance Criteria" checklist (ซึ่งเป็นเอกสารคนละหัวข้อในไฟล์เดียวกัน) แบบเดียวกันแบบครบทุกข้อ ทำให้พลาดจับได้ว่า "ลบ Comment ของตัวเองได้" หายไปทั้งระบบเหมือนกัน (มี RLS delete policy ฝั่ง DB รองรับไว้แล้วตั้งแต่รอบ Coding แรก แต่ไม่มี repository method และไม่มี UI เลย — เหมือนบั๊ก Like Comment เป๊ะ) พบตอน QA รอบ 2 ตอนไล่ Acceptance Criteria ทุกบรรทัดใหม่ทั้งหมดแทนที่จะเทียบแค่จุดที่เพิ่งแก้ บทเรียน: QA ต้องไล่ **ทั้ง** Requirements, Design Components, **และ** Acceptance Criteria ทีละบรรทัดแยกกันทุกครั้ง ไม่ใช่แค่หัวข้อใดหัวข้อหนึ่ง เพราะแต่ละหัวข้อในเอกสารเดียวกันอาจระบุรายละเอียดที่อีกหัวข้อไม่ได้พูดถึง — และ QA รอบถัดไปของ task ใดก็ตามที่เคย FAIL ต้องไล่ checklist แบบครบทุกหัวข้อใหม่ทั้งหมดเสมอ ไม่ใช่แค่ตรวจจุดที่ Debug เพิ่งแก้

- Successful patterns เพิ่มเติม (2): **การลงทุนสร้าง pattern ที่ถูกต้อง+เอกสารบทเรียนไว้ตั้งแต่ feature แรก จ่ายผลตอบแทนจริงใน feature ถัดไป (WYN-006)** — WYN-006 (Pop) มี Comment ครบทั้ง 3 ความสามารถ (เพิ่ม/ลบ/Like) ตั้งแต่การส่งมอบครั้งแรก และผ่าน QA รอบเดียวโดยไม่มี FAIL เลย ต่างจาก WYN-005 ที่พลาดจุดเดียวกันนี้ไป 2 รอบติดกัน — ความแตกต่างเดียวคือ WYN-006 มีโค้ดที่ถูกต้องของ WYN-005 (หลัง Debug รอบ 2) ให้ reuse ตรง ๆ ระหว่างที่ WYN-005 ไม่มี pattern อะไรให้อ้างอิงเลยตอนเริ่ม (WYN-004 ไม่เคยมี Like/Delete Comment) — บทเรียน: เวลาที่ใช้แก้บั๊ก+เขียน regression test+บันทึก pattern ใน `.wyn/learning/` ไม่ใช่ overhead แต่เป็นการลงทุนที่ลด rework ของงานถัดไปได้จริงและวัดผลได้ (WYN-005: 3 รอบ QA, WYN-006: 1 รอบ QA)
- Successful patterns เพิ่มเติม (3): **สร้าง fake platform implementation ใหม่เมื่อ behavior สำคัญผูกกับ plugin ที่ไม่มี platform channel ในสภาพแวดล้อมทดสอบ (WYN-006)** — `video_player` ปกติจะ throw `MissingPluginException` ใน `flutter test` เพราะไม่มี platform implementation จริง ถ้าปล่อยแบบนั้น view-count recording และ mute/volume propagation จะกลายเป็นจุดที่ทดสอบไม่ได้เลย (เหมือนที่ยอมรับไว้สำหรับ `Image.network` ใน Drop) — แต่ต่างจาก Drop ตรงที่ Pop มี behavior จริงผูกกับความสำเร็จของการเล่นวิดีโอ จึงคุ้มที่จะสร้าง `FakeVideoPlayerPlatform` (implement `VideoPlayerPlatform` แบบง่าย emit `VideoEvent.initialized` ทันที) แทนที่จะยอมรับว่าทดสอบไม่ได้ — บทเรียน: การยอมรับข้อจำกัดของ sandbox (accepted known limitation) ควรใช้เฉพาะเมื่อสร้าง test double ไม่คุ้มค่าจริง ๆ ไม่ใช่ default แรกที่เลือกเสมอ
