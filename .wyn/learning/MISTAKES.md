- ผลกระทบ: กระทบ Acceptance Criteria หลักของ WYN-004 โดยตรง ("กดไลก์แล้วเห็นจำนวนเพิ่มทันที กดซ้ำเพื่อเลิกไลก์ได้") — เป็นบั๊กที่เกิดได้จริงบนมือถือ (ผู้ใช้ใจร้อน/เครื่อง lag) ไม่ใช่แค่ทฤษฎี
- วิธีป้องกันในอนาคต: เมื่อ widget เดียวกันมี async button handler มากกว่า 1 จุดที่ทำงานคล้ายกัน (เช่น toggle like ทั้งใน Feed และ Post Detail) ให้ AI Coding ใช้ pattern เดียวกันทุกจุดตั้งแต่แรก (อ่าน mutable state สดใหม่ในตัว method เสมอ ไม่รับเป็น parameter/closure ที่ capture ไว้ตอน build) และทุกปุ่มที่เรียก async operation ที่ไม่ควรถูกเรียกซ้อนกัน ต้องมี explicit guard (`if (_isXxx) return;`) เป็นบรรทัดแรกของ handler เสมอ ไม่ใช่พึ่งแค่ disabled state ของปุ่มซึ่ง lag ไปหนึ่ง frame เสมอ
- Regression test ที่เพิ่ม: `app/test/feed_screen_test.dart`, `app/test/create_post_screen_test.dart` — พิสูจน์ทั้งสองจุดได้จริงแบบ dynamic โดยเรียก widget's `onPressed` callback สองครั้งติดกันแบบ synchronous (แม่นยำกว่า `tester.tap()` สองครั้งซึ่งเป็น async และปล่อยให้ call แรกทำงานจบก่อนได้) ใช้เทคนิคใหม่ 2 อย่างที่ทำให้ testable: (1) `RecordingPostRepository` — subclass ของ `PostRepository` ที่ override method แทนการเพิ่ม interface ใหม่ (2) `fake_supabase_session.dart` — ปลอม signed-in session แบบ local-only (ไม่ยิง network จริง) ให้ widget ที่พึ่ง `Supabase.instance.client.auth.currentUser` ตรง ๆ (เช่น `FeedScreen`) pump ได้ในการทดสอบ — บันทึกเป็น pattern ใหม่ใน `.wyn/learning/PATTERNS.md`

### [2026-08-15] Task ZOKY-004 (QA รอบ 1) — ครั้งแรกที่พบช่องโหว่ security ระดับ Critical ในโปรเจกต์นี้
- ข้อผิดพลาด: `reviews` table's `insert` RLS policy ตรวจ delivered-order-ownership gate ถูกต้องครบถ้วนผ่าน `exists` subquery (join `order_items`→`orders` ตรวจ `buyer_id`/`status = 'delivered'`/`product_id` ตรงกัน) แต่ `update` policy เขียนแค่ `using (auth.uid() = user_id)` โดยไม่มี `with check` — Coding/Design เข้าใจผิดว่า "order status ไม่มีทาง regress กลับจาก delivered ได้ จึงไม่ต้องตรวจซ้ำตอนแก้ไข" แต่ลืมพิจารณาว่า `order_item_id`/`product_id` **ของแถว reviews เอง** เปลี่ยนแปลงได้อิสระผ่าน update โดยไม่มี gate ป้องกันเลย เป็นคนละเรื่องกับ order status regression — Postgres RLS เมื่อไม่มี `with check` สำหรับ `update` จะ fallback ใช้ `using` เดิมเป็นตัวตรวจแถวใหม่ด้วย ซึ่งในที่นี้แคบกว่า insert's gate มาก
- ผลกระทบ: ผู้ใช้แก้ไขรีวิวของตัวเอง (ที่เขียนถูกต้องมาแล้วครั้งหนึ่ง) ให้ retarget `product_id`/`order_item_id` ไปยังสินค้าใดก็ได้ในระบบ รวมถึงสินค้าที่ไม่เคยซื้อเลย — ขัดกับ core security guarantee ของทั้งฟีเจอร์ ("ป้องกัน fake review จากคนที่ไม่เคยซื้อจริง") ตรง ๆ เป็นช่องโหว่ระดับ Critical/blocking ครั้งแรกที่พบในโปรเจกต์นี้ (ต่างจาก Minor/Major ที่เจอมาก่อนหน้าทั้งหมดซึ่งเป็นเรื่อง UI/UX ไม่ใช่ security)
- วิธีป้องกันในอนาคต: ทุกครั้งที่ตารางใหม่มี `insert` policy ที่ซับซ้อน (มี multi-table `exists`/join gate) ต้องตรวจ `update` policy คู่กันเสมอว่ามี `with check` ที่ตรวจ gate เดียวกันหรือไม่ — เขียนไว้ชัดเจนใน `.wyn/learning/LESSONS_LEARNED.md` แล้วว่า "update/delete policy ไม่มี with check ไม่ได้แปลว่าปลอดภัยเท่ากับ insert เสมอไป"
- Regression test ที่เพิ่ม: ไม่มี Flutter automated test ที่ทดสอบ live RLS ได้ (ไม่มี Supabase project จริง deploy อยู่) — แก้ด้วยการเพิ่ม `with check` mirror ของ insert policy เข้าไปใน `update` policy โดยตรง (ดู `.wyn/tasks/bugs/ZOKY-004-review-update-rls-gap.md` หัวข้อ "Debug Output") ยืนยันด้วยการอ่าน Postgres RLS semantics และไล่ query path ของ `ZokyRepository.editReview` ว่าไม่มี behavior ใดที่ app ใช้งานจริงจะถูก policy ที่เข้มขึ้นนี้ปฏิเสธ

### [2026-08-15] Task SCHEMA-001 — `schema.sql` พังทั้งไฟล์เมื่อรันกับ Supabase project ว่างเปล่าจริงเป็นครั้งแรก

- วิธีป้องกันในอนาคต: ทุกครั้งที่แก้ `supabase/schema.sql` โดยเฉพาะการเพิ่มคอลัมน์ให้ตารางเก่าที่ต้องอ้างอิงตารางใหม่ (feature ใหม่ต่อยอด table เดิม เช่น notification type ใหม่, tag/category ใหม่) ต้อง **เพิ่มคอลัมน์ผ่าน `alter table ... add column if not exists` แยกต่างหาก** วางตำแหน่งหลังตารางที่ถูกอ้างอิงถูกสร้างแล้วเท่านั้น ห้ามแก้ไข `create table` เดิมของตารางเก่าให้อ้างอิงตารางที่ยังไม่มีเลย — และต้องรัน `supabase/check_schema_ordering.py` (สคริปต์ regression test ใหม่ที่เพิ่มใน PR นี้) ทุกครั้งก่อนส่ง PR ที่แตะ `schema.sql`
