### [2026-08-22] WYN-027 (Block system) — สร้าง SECURITY DEFINER helper function ใน `public` โดยไม่ grant/revoke ชัดเจน เข้าใจผิดว่า "ไม่ grant = ปิด"
- ข้อผิดพลาด: ตอน implement `is_blocked_either_way(a uuid, b uuid)` (และ 4 sibling author-lookup function) ผู้เขียนโค้ด (self-QA เดียวกับ Coding session) ตั้งใจให้เป็น internal-only helper สำหรับ RLS policy เท่านั้น แต่ไม่ได้เขียน `grant`/`revoke` ใด ๆ กำกับไว้เลย ต่างจาก `block_relationship`/`block_user`/`unblock_user` ที่ตั้งใจเปิดเป็น client RPC และมี `grant execute ... to authenticated;` ชัดเจนทุกตัว — สมมติไปเอง (ผิด) ว่าการไม่เขียน grant statement ใด ๆ จะทำให้ function "ไม่เปิด" โดย default ทั้งที่ Postgres grant `EXECUTE` ให้ `PUBLIC` เป็นค่าเริ่มต้นเสมอตอนสร้าง function ใหม่ และ PostgREST auto-expose ทุก function ใน `public` เป็น RPC endpoint โดยดูแค่ ACL ไม่ใช่ "มี grant statement บอกไว้หรือเปล่า"
- ผลกระทบ: `is_blocked_either_way` รับ 2 พารามิเตอร์เป็น user id ใครก็ได้ (ต่างจาก `block_relationship` ที่ resolve จาก `auth.uid()` เสมอ) ทำให้ authenticated user คนไหนก็เรียก `POST /rest/v1/rpc/is_blocked_either_way` ถามความสัมพันธ์ block ของผู้ใช้อีกสองคนที่ไม่เกี่ยวกับตัวเองได้เลย ทั้งที่ตาราง `blocks` มี RLS `select` policy จำกัดไว้แน่นหนาว่า `auth.uid() = blocker_id` — bypass การป้องกันความเป็นส่วนตัวที่ table เดียวกันตั้งใจสร้างไว้โดยสมบูรณ์ QA อิสระรอบ 1 (session แยกจาก Coding) เป็นคนจับได้ ไม่ใช่ self-QA รอบแรก
- วิธีป้องกันในอนาคต: ทุกครั้งที่สร้าง `security definer` function ใหม่ที่ตั้งใจให้เป็น internal-only (ไม่ใช่ client RPC) ต้องสร้างใน schema ที่ไม่อยู่ใน PostgREST exposed-schema list ตั้งแต่ต้น (โปรเจกต์นี้ตอนนี้มี schema `internal` แล้วจาก WYN-027 fix — ใช้ schema นี้ต่อไปสำหรับ helper function แบบเดียวกันในอนาคต) ห้ามสร้างใน `public` แล้วหวังว่า "ไม่ grant = ปิด" เพราะไม่จริง — AI Coding/AI QA & Security ต้องเช็คทุก `security definer` function ใหม่ด้วยคำถาม 2 ข้อเสมอ: (1) ฟังก์ชันนี้ตั้งใจเป็น client RPC หรือ internal-only? (2) ถ้า internal-only อยู่ใน schema ที่ PostgREST expose ไหม (ถ้าใช่ ต้องย้ายออก ไม่ใช่แค่ไม่ grant)
