## Changes

40 files changed (4123 insertions, 199 deletions) merged into `main` via PR #133 (`982b152..17027ba`):

- **SQL** (`supabase/schema.sql`): `moderation_actions.overturned_at timestamptz` (set only by `decide_appeal()` on approve; extends the existing `expires_at`-based existence checks in `internal.is_posting_blocked()`/`get_my_moderation_status()` with `and overturned_at is null`, without touching the expiry logic itself — the two mechanisms stay orthogonal). `notifications` gains `moderation_action_id`/`moderation_action_type` (both new moderation-related notification types, and the two carried over from WYN-029, now link back to their originating `moderation_actions` row — `MyModerationActionScreen` is the single destination for all 4). New `appeals` table (RLS: appellant sees their own row, any moderator/admin sees all — **no insert/update/delete policy for any role**, writes only ever happen through the two RPCs below). New private `appeal-evidence` storage bucket (RLS scoped by `{uid}/...` path prefix, mirroring the file-owner convention avatar/drop-image uploads already use, not the club-membership convention `club-media` uses). `submit_appeal()` RPC (validates the caller owns the action, the action type is appealable, the reason is non-blank, at most 3 evidence paths each under the caller's own uid prefix; a second appeal on the same action is rejected with a friendly message via a caught `unique_violation`). `decide_appeal()` RPC (`for update` row lock; rejects a non-moderator caller; **self-review guard blocks both approve and reject** when the reviewer is the action's own target, not just approve as the literal minimum the Product spec required; reject requires a non-blank `decision_reason`; approve sets `overturned_at`; both outcomes insert a notification with **`actor_id = NULL` from the very first insert** — the real reviewer identity lives only in `appeals.reviewer_id`, which the target has no SELECT access to — this is the third time this project has protected a moderation-adjacent identity this way, done correctly from the start this time rather than patched in after a QA-caught leak like WYN-029's). `get_my_moderation_status()` extended from 8 to 14 columns (adds `*_action_id`/`*_appeal_status` for restrict/suspend/ban, each resolved with the same expiry/overturn filters as the boolean flag itself — so an approved appeal's status naturally reads back as `none` once the block it applied to is lifted, since the UI that would show `approved` stops rendering at that point anyway). New `get_my_moderation_action()` RPC (deliberately excludes `reviewer_id`/`report_id`).
- **Flutter**: new `app/lib/features/moderation/data/{appeal_status,my_moderation_action,my_appeal,appeal,appeal_repository}.dart` (the appellant-facing model/query, `MyAppeal`, deliberately never selects `reviewer_id` — column-list discipline as the actual privacy boundary, documented explicitly in `AppealRepository`'s class doc comment). New `app/lib/features/moderation/presentation/{appeal_form_screen,evidence_image_viewer,my_moderation_action_screen,appeal_detail_screen,appeal_decision_sheet}.dart`. `RestrictionBanner` gains 3 optional (backward-compatible) params for an appeal entry point, wired into the 4 existing call sites (`CreateDropScreen`, `DropDetailScreen`, `ClubPostDetailScreen`, `CreateClubScreen`). `AccountRestrictedScreen`+`AuthGate`: the highest-risk change in this feature — `signOut()` no longer fires the moment a Suspend/Ban is detected; the session (JWT) is deliberately kept valid while `AccountRestrictedScreen` is showing so `submit_appeal()` (an authenticated RPC) can still succeed, with the actual sign-out deferred to the moment the user taps "ตกลง" (whether or not they appealed first). Documented inline as *not* an auth/RLS architecture change — Suspend/Ban only ever blocked INSERT at the RLS layer, never READ, so a valid token held a little longer doesn't expose anything a signed-in-but-blocked user couldn't already reach before this feature existed. `ModerationQueueScreen` refactored from a single list into a `DefaultTabController` with "รายงาน" (unchanged `_ReportsTab`, same logic just relocated) and a new "อุทธรณ์" `_AppealsTab` mirroring its exact pagination/list/optimistic-removal shape. `AppealDetailScreen`/`AppealDecisionSheet` mirror `ModerationReportDetailScreen`/`ModerationActionSheet`'s shape closely, with the self-review guard hiding both Approve/Reject when `currentModeratorId == appeal.actionTargetUserId` — `currentModeratorId` is injected from `SettingsScreen` (which reads `Supabase.instance.client.auth.currentUser` at its one existing call site), not read from `Supabase.instance` inside the moderation screens themselves, keeping them testable without a live session.
- **New persisted regression test**: `supabase/tests/wyn_030_appeal_system_test.sh` (24 checks, added to the same `supabase/tests/` suite as `wyn_021`/`wyn_027`/`wyn_029`).
- **Tests**: `app/test/appeal_decision_sheet_test.dart`, `app/test/appeal_detail_screen_test.dart` (new, includes explicit self-review-guard coverage in both directions), `app/test/support/recording_appeal_repository.dart` (new fake), updates to `account_restricted_screen_test.dart`/`auth_gate_test.dart` (reflecting the deferred-signOut behavior change), `moderation_queue_screen_test.dart` (Appeals tab coverage), `notification_list_screen_test.dart` (threads through the new `appealRepository` param).
