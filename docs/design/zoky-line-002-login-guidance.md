โดย AI Design | Status: Draft รอ Founder/CTO review ก่อน implement
ที่มา: ZOKY-LINE-002 หัวข้อ 3 รายการ F (P0 ถ้า D ยังไม่อนุมัติ) — ไม่ใช่ auth architecture change; **ไม่เพิ่ม LINE Login** (D-3 รอ baseline + design + Founder approval อีกรอบ) และไม่ใช่ direction visual ใหม่ ใช้ pattern/สีเดิมของ Food และ `/line`

ข้อสังเกตสำคัญ: เมื่อสร้างข้อความ "เปิดในเบราว์เซอร์" ต้องไม่สัญญาว่าตะกร้าจะตามไป เพราะวันนี้ไม่ตาม (ยังไม่มีกลไก handoff) ดังนั้นทางหลักที่แนะนำในมุม UX คือ **อีเมล/รหัสผ่านต่อในหน้านี้เลย** (ตะกร้าไม่หาย) ส่วนเปิดเบราว์เซอร์เป็นทางรอง พร้อมคำเตือนตะกร้าตรง ๆ

## 2. Screen: `/food/login` (มุมมองใน LINE in-app browser)

**Purpose:** ป้องกันผู้ใช้ติดกับดัก Google บล็อก โดยบอกทางออกก่อนกด และไม่ทำให้ตะกร้าหาย

**User Flow**
1. ลูกค้าเปิดจาก LIFF -> ใส่ตะกร้า (guest) -> กดยืนยัน -> `/food/login`
2. หน้า login ตรวจสภาพแวดล้อม:
   - อยู่ใน LINE in-app (`liff.isInClient()` true) -> แสดงกล่องแนะนำเหนือปุ่ม Google และ **ลดน้ำหนักปุ่ม Google** (ยังกดได้ ไม่ซ่อน เพราะ detection อาจพลาด/Google บางกรณีอาจผ่าน) พร้อมเลื่อนฟอร์มอีเมลขึ้นเป็นทางหลัก
   - ไม่ใช่ LINE / ตรวจไม่ได้ -> หน้าเดิมทุกประการ (ห้ามกระทบผู้ใช้เบราว์เซอร์ปกติ/PWA)
3. ผู้ใช้เลือก: (ก) อีเมล/รหัสผ่านในหน้าเดิม -> ตะกร้ายังอยู่ใน session เดิม; (ข) "เปิดในเบราว์เซอร์" -> external browser (ตะกร้าอยู่ฝั่ง LINE ต่อ ไม่ถูกลบ); (ค) กด Google ต่อ -> พฤติกรรมเดิม + ข้อความ error ถ้าล้มเหลว

**Detection (ข้อเสนอ ให้ Architect/Full-Stack ยืนยัน)**
- ลำดับ: เริ่มจาก user agent เบา ๆ (มีคำว่า `Line/` ใน `navigator.userAgent`) เพื่อแสดงทันทีโดยไม่รอ LIFF -> เมื่อมี LIFF ID ที่ตั้งค่าไว้ ยืนยันด้วย `liff.isInClient()` เหมือน `/line` (ใช้ `configuredLiffIds()`/`liffIdFor("food", …)` เดิม ไม่เพิ่ม dependency)
- ถ้า UA บอก LINE แต่ LIFF ไม่ได้ตั้งค่า (เช่น staging) ให้แสดงกล่องข้อความ แต่ **ซ่อนปุ่มเปิดเบราว์เซอร์แบบ `liff.openWindow`** และแสดงข้อความ fallback (ดู 4.4) เพราะไม่มีวิธีเปิด external ที่ยืนยันแล้ว
- ห้ามบล็อกหรือ redirect อัตโนมัติ ห้าม log UA/URL ที่มี token

## 4. Layout และ Microcopy (ภาษาไทย)

### 4.1 โครงหน้าใน LINE in-app (ลำดับบนลงล่าง)
1. Brand + หัวข้อ "เข้าสู่ระบบ WYNOS Food" (เดิม)
2. **กล่องแนะนำ LINE** (ใหม่ แสดงเฉพาะใน LINE)
3. ปุ่ม "เปิดในเบราว์เซอร์" (รอง)
4. ปุ่ม Google (ยังอยู่ แต่เป็นสไตล์ outline เดิม ไม่ถูกซ่อน/ไม่ถูก disable เพราะ detection)
5. ตัวคั่น "หรือ" + ฟอร์มอีเมล/รหัสผ่าน (เดิม)

> ทางเลือกลำดับ: ถ้า Founder ต้องการให้อีเมลเป็นทางหลักในแอป LINE จริง ให้ย้ายฟอร์มอีเมลขึ้นก่อนปุ่ม Google ใน LINE เท่านั้น — ให้ตัดสินตามผล baseline ไม่เดาในรอบนี้

### 4.2 ข้อความหลัก (กล่องแนะนำ)

- หัวข้อ (ตัวหนา): **เปิดใน LINE อยู่**
- เนื้อหา: "Google ไม่อนุญาตให้เข้าสู่ระบบในแอป LINE ใช้อีเมลและรหัสผ่านต่อได้เลย ตะกร้าของคุณยังอยู่ หรือเปิดในเบราว์เซอร์ของเครื่องเพื่อเข้าสู่ระบบด้วย Google"
- คำเตือนตะกร้า (บรรทัดแยก ตัวเล็ก ไม่ซ่อน): "ถ้าเปิดในเบราว์เซอร์ ตะกร้าจะไม่ถูกย้ายไปด้วย ต้องเลือกเมนูใหม่อีกครั้ง"
  - ข้อความนี้ต้องคงไว้จนกว่ามีกลไก handoff ตะกร้าจริง (EC-G2) ถ้า implement handoff แล้วค่อยแก้เป็น "ตะกร้าจะตามไปด้วย" โดยต้องผ่านการทดสอบก่อน
- ปุ่มรอง: **เปิดในเบราว์เซอร์**
- aria-label ปุ่ม (ถ้าต้อง): "เปิดหน้าเข้าสู่ระบบในเบราว์เซอร์ของเครื่อง ตะกร้าจะไม่ถูกย้ายไปด้วย"

### 4.3 ข้อความสถานะ/ข้อผิดพลาด

| สถานการณ์ | ข้อความ |
|---|---|
| กำลังตรวจสภาพแวดล้อม (ถ้ารอ LIFF > ~300ms) | ไม่แสดง skeleton บล็อกหน้า; แสดงฟอร์มเดิมทันที แล้วกล่องแนะนำค่อยแทรกเมื่อพร้อม (ดู 5 เรื่อง layout shift) |
| กำลังเปิดเบราว์เซอร์ | ปุ่ม: "กำลังเปิด…" (disabled ชั่วคราวสูงสุด 3 วินาทีแล้วกลับมากดได้) |
| เปิดเบราว์เซอร์ไม่สำเร็จ | "เปิดเบราว์เซอร์ไม่สำเร็จ ลองกดอีกครั้ง หรือใช้อีเมลและรหัสผ่านต่อได้เลย ตะกร้ายังอยู่" |
| LIFF โหลดไม่ได้ / ไม่ได้ตั้งค่า | "เปิดเบราว์เซอร์จากที่นี่ไม่ได้ กดปุ่ม … ที่มุมขวาบนของ LINE แล้วเลือก เปิดในเบราว์เซอร์ หรือใช้อีเมลและรหัสผ่านต่อได้เลย" (ให้ทีมยืนยันตำแหน่งเมนูบน iOS/Android ก่อนระบุ ถ้าไม่ยืนยันให้ตัดประโยค "ปุ่ม … ที่มุมขวาบน" ออก เหลือ "เปิดหน้านี้ในเบราว์เซอร์ของเครื่อง") |
| Google ล้มเหลว (ข้อความเดิม) | คงข้อความเดิม "เข้าสู่ระบบด้วย Google ไม่สำเร็จ กรุณาลองใหม่" และถ้าอยู่ใน LINE ต่อท้าย: "ถ้าเห็นหน้าปฏิเสธจาก Google ให้ใช้อีเมลและรหัสผ่าน หรือเปิดในเบราว์เซอร์" |
| อีเมล/รหัสผ่านผิด (เดิม) | "อีเมลหรือรหัสผ่านไม่ถูกต้อง" |
| ผู้ใช้ Google ไม่มีรหัสผ่าน (กลุ่มที่ติดจริง) | ลิงก์เดิม "ลืมรหัสผ่าน?" ใช้ตั้งรหัสผ่านได้ — เพิ่มบรรทัดช่วยเหลือเล็ก ๆ ใต้ช่องรหัสผ่านเฉพาะใน LINE: "สมัครด้วย Google มาก่อน? กด ลืมรหัสผ่าน เพื่อตั้งรหัสผ่านด้วยอีเมลเดียวกัน" **สถานะ: ต้อง Full-Stack/QA ยืนยันก่อนว่า flow reset password ใช้กับบัญชี Google ได้จริงและกลับมาที่ `/food/login` โดยไม่เสียตะกร้า ยังไม่ได้ตรวจ ถ้ายืนยันไม่ได้ให้ตัดบรรทัดนี้** |

### 4.4 คำที่หลีกเลี่ยง
ไม่ใช้ศัพท์เทคนิค (`disallowed_useragent`, in-app browser, OAuth) ในข้อความผู้ใช้; ไม่ใช้ "ห้าม/ผิดพลาดร้ายแรง"; น้ำเสียงเป็นกันเองแบบ Food เดิม (ไม่ตำหนิผู้ใช้)

## 5. Interactions และ States

| State | พฤติกรรม |
|---|---|
| default (นอก LINE) | ไม่แสดงกล่อง ไม่เปลี่ยนอะไร |
| detecting | ไม่บล็อกฟอร์ม; กล่องแทรกเมื่อพร้อมโดย**จอง min-height** หรือแทรกเหนือปุ่ม Google โดยไม่ดันปุ่มที่ผู้ใช้กำลังจะกด (หลีกเลี่ยง layout shift ทำให้กดผิดปุ่ม); ถ้าเลื่อนเข้าไปหลังผู้ใช้เริ่มพิมพ์อีเมล ห้ามล้างค่าฟอร์ม |
| in-LINE (พร้อมใช้) | แสดงกล่อง + ปุ่มเปิดเบราว์เซอร์ |
| opening | ปุ่มแสดง "กำลังเปิด…" + `aria-busy`; ไม่ block ปุ่มอื่น (อีเมลยังพิมพ์ได้) |
| opened | LINE ยังคงหน้านี้ไว้ ผู้ใช้กลับมาที่ LINE แล้วใช้อีเมลต่อได้ ตะกร้ายังอยู่ |
| open_error | `role="alert"` ข้อความ 4.3 + ปุ่มกดซ้ำได้ |
| liff_unavailable | ข้อความ fallback 4.3 ไม่มีปุ่มเปิด |
| googleLoading (เดิม) | ตามเดิม ใช้ `wf-mini-loader` |

**ตะกร้า guest ต้องไม่หาย (ข้อกำหนด)**
- กล่องแนะนำ/ปุ่มเปิดเบราว์เซอร์ ต้อง**ไม่เรียก** `clear`/`remove` ใด ๆ ของ guest basket (`GUEST_BASKET_KEY`) และไม่เปลี่ยน route ของหน้าเดิมเมื่อกด (เปิด external เท่านั้น)
- `openWindow` ใช้ URL ของ `/food/login` เองเท่านั้น (ไม่ใส่ตะกร้า/ข้อมูลส่วนตัว/token ใน URL ตาม AC-Q5) และไม่รับ URL จาก query
- ห้ามใช้ `window.location.replace` ไปหน้าอื่นโดยอัตโนมัติ เพราะ reload อาจกระทบ state; ถ้าจำเป็นต้อง reload ให้พิสูจน์ว่าตะกร้ายังถูกอ่านจาก storage ได้
- การกด "ย้อนกลับ" จาก login ต้องเห็นตะกร้าเดิม (EC-G6) — เป็นเกณฑ์ทดสอบ regression
- ผู้ใช้ที่ login สำเร็จแล้ว flow import ตะกร้าเดิมทำงานเหมือนเดิม (ไม่แก้ logic ใน spec นี้)
- ถ้า storage ใช้ไม่ได้ (EC-G3) ไม่ใช่หน้าที่ของ spec นี้ แต่ข้อความเตือนตะกร้าอาจหายต้องไม่ถูกบดบัง

## 6. Responsive Behavior (mobile-first)

- ออกแบบที่ 360px ก่อน; กล่องเต็มความกว้างคอลัมน์ฟอร์มเดิม ไม่มี horizontal scroll
- ปุ่มสูง >= 48px, ระยะห่างระหว่างปุ่ม >= 8px (กันกดผิดในจอเล็ก/นิ้วโป้ง)
- รองรับ safe-area ของ LINE ล่างจอ และการย่อ viewport เมื่อ keyboard ขึ้น (ฟอร์มอีเมลเลื่อนเข้าตำแหน่งตาม browser เดิม)
- เดสก์ท็อป: ไม่แสดงกล่องเพราะ LINE desktop in-app ไม่ใช่เป้าหมาย; ถ้าตรวจพบ LINE desktop ให้ถือเหมือนมือถือ (ข้อความเดิมใช้ได้)
- ตัวอักษรอย่างน้อย 14px สำหรับเนื้อหาหลักของกล่อง (CSS ปัจจุบันของ `wf-auth-note` ใช้ 10-11px ซึ่งเล็กเกินสำหรับข้อความที่ผู้ใช้ต้องตัดสินใจ -> modifier ใหม่ต้องปรับขนาด; ไม่แก้ `wf-auth-note` เดิมที่ใช้ที่อื่น)

## 7. Accessibility

- กล่อง: `role="note"` (หรือ section พร้อมหัวข้อ) ไม่ใช่ `alert` ตอนแสดงครั้งแรก เพื่อไม่ขัดจังหวะ screen reader; ข้อความ error/เปิดไม่สำเร็จใช้ `role="alert"` (ตรงกับ pattern ที่มีอยู่)
- ปุ่มเป็น `<button type="button">` จริง มี focus ring ที่เห็นชัด (อย่างน้อย 3px คล้าย `.zl-primary:focus-visible`); ลำดับ tab: กล่อง/ปุ่มเปิดเบราว์เซอร์ -> Google -> อีเมล -> รหัสผ่าน -> เข้าสู่ระบบ
- Contrast ข้อความ >= 4.5:1 (ตัวเล็กและคำเตือนตะกร้า) ไม่ใช้สีอย่างเดียวสื่อความหมาย (คำเตือนตะกร้ามีข้อความ + ไอคอน)
- ไอคอนประดับ `aria-hidden="true"`
- ปุ่มที่ disabled ชั่วคราว (opening) ใช้ `aria-busy` และประกาศผลเมื่อเสร็จ/ล้มเหลวผ่าน live region
- รองรับการขยายตัวอักษรของระบบ (text size) โดยกล่องไม่ตัดข้อความ
- ภาษา: เนื้อหาไทยทั้งหมด (`lang="th"` ของหน้าเดิม)

## 8. Design Rules

- ยึด WYN/ZOKY เดิม: พื้นขาวเป็นหลัก สีเน้นของ Food เดิม (`--wf-*`) ไม่เพิ่มสีใหม่ ไม่ทำพื้นเขียว LINE ใหญ่ ไม่ใช้ rainbow เพิ่ม (ตาม ds-009/ds-007)
- ไม่ซ่อนหรือ disable ปุ่ม Google เพียงเพราะตรวจพบ LINE (กัน false positive)
- ไม่เพิ่ม dependency; reuse `@line/liff`, `liffIdFor`/`configuredLiffIds`
- ไม่แตะ auth architecture, Supabase session, OAuth callback, หรือ logic import ตะกร้า
- ใช้เฉพาะ `/food/login` ของลูกค้า; Merchant login ไม่เปลี่ยน (D-5)
- ไม่ถือเป็นการอนุมัติ LINE Login; ถ้า D-3 อนุมัติภายหลัง ปุ่ม LINE Login จะเข้ามาแทนกล่องนี้ ต้องมี spec ใหม่

## 9. Acceptance criteria (สำหรับ QA)

1. ใน LINE in-app (มือถือจริง iOS/Android) แสดงกล่อง + ปุ่ม; นอก LINE ไม่เปลี่ยนจากเดิม (snapshot/ตรวจด้วยตา)
2. กดปุ่มเปิดเบราว์เซอร์แล้วเปิด `/food/login` ใน external browser โดย URL ไม่มี token/ตะกร้า; กลับมา LINE ตะกร้ายังอยู่
3. ตะกร้า (options/โน้ต/จำนวน) อยู่ครบหลัง: แสดงกล่อง, กดเปิดเบราว์เซอร์, กดย้อนกลับ, login ด้วยอีเมลสำเร็จ (import ตะกร้าเดิม)
4. ข้อความเตือนว่าตะกร้าไม่ถูกย้ายแสดงตลอดเมื่อมีปุ่มเปิดเบราว์เซอร์
5. LIFF ไม่ได้ตั้งค่า/โหลดล้มเหลว: แสดง fallback ไม่มีหน้าขาว ฟอร์มอีเมลใช้ได้
6. ไม่มี layout shift ที่ทำให้ปุ่มเลื่อนหนีนิ้ว; ไม่ล้างค่าที่ผู้ใช้พิมพ์
7. Screen reader อ่านกล่องได้ ปุ่มเข้าถึงด้วย keyboard/focus ได้; contrast ผ่าน
8. Google/อีเมลนอก LINE และ Merchant login ทำงานเหมือนเดิม (regression); Web Push/LINE notification ไม่กระทบ
9. ทดสอบผ่าน usability test รอบหลังแก้ (ดู `docs/qa/zoky-line-002/usability-test-script.md`)

## 10. Handoff

- Full-Stack: client component เล็ก ๆ ที่ใช้ใน `FoodLoginScreen` (detection + กล่อง) โดย reuse LIFF helper เดิม; อย่าแก้ logic Google/PWA/legacy origin ใน `food-auth.tsx`; เพิ่ม CSS modifier ใน `food.css`
- QA: เคส 9 ข้อข้างบน + `liff.openWindow` บน iOS/Android จริง
- Architect/CTO: ยืนยัน detection (UA vs `liff.isInClient()`), ความเป็นไปได้ของ handoff ตะกร้า (EC-G2) ซึ่งจะเปลี่ยนข้อความเตือนในข้อ 4.2
- ต้องผ่าน release gates เดิม; spec นี้ไม่อนุมัติ implementation

## 11. ยังไม่ได้ตรวจ

- ยังไม่ได้ทดสอบบน LINE จริง/ไม่ได้รันโค้ด; พฤติกรรม `liff.openWindow` external บน iOS/Android และ UA ของ LINE ยังเป็นข้อสันนิษฐาน
- ยังไม่ได้ตรวจ `food.css` ทั้งไฟล์ (ตรวจเฉพาะ `wf-auth-*` บางส่วน) และตัวแปรสี `--wf-*` จริง
- flow reset password สำหรับบัญชี Google ยังไม่ได้ยืนยัน (ข้อ 4.3 แถวสุดท้าย)
- ไม่ได้อ่าน `.wyn/company/*` ครบทุกไฟล์ (อ่านเฉพาะ proposal, design role, design docs ที่เกี่ยวข้อง); ไม่ได้ตรวจ `CONTEXT.md` ว่ามี design system เฉพาะ Food เพิ่มเติม
