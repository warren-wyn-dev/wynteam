- **Food payments/customers:** paginated, date-bounded, read-only recorded payment anomalies (`food:view`) and pseudonymous customer order histories (`food:edit`). Account deletion anonymizes actor references. No uploaded evidence, compensation payment, fraud punishment, email, Push or quiet-hours workflow is added.
- **Banner/featured analytics:** existing public placement selection, in-memory receipt keys, qualified visibility/click attribution, retry dedupe, aggregate-only Admin ranges, bounded optional ingestion and data pruning. No account/IP/location is collected; counts can be lost during contention/outages and are never billing or unique-person metrics. Expiry is checked on use; physical cleanup runs in bounded batches during ingestion, not an independent retention scheduler.
- **Platform Marketing:** a functional Food-home workspace reuses the real banner/featured editors, public selection RPCs and aggregate analytics. Query tabs load only the selected area/task, retain analytics ranges, and distinguish published eligibility from customer location/search filters. Public previews ingest no events. Initial featured fields now reflect the selected store's persisted values. This is Food-home placement management, not a completed cross-platform marketing system.
- **Merchant menu:** create/edit/archive/restore; category add/rename/remove-unused/reorder; per-item option groups/choices; availability, daily limits and pause times; audit/stale protection. Archive denies checkout, hides authenticated catalogue entries and preserves old order snapshots. Restored items stay unavailable. Same-store image selection/preview/removal preserves objects. New image upload now includes server decoding/reencoding, protected immutable publication, progress/cancel/retry and explicit audited menu save; authenticated staging is still required.
- **Maps reports:** real public-place intake, owner status, redacted Maps view/edit queue, versioned human state transitions and retained history. Reports do not edit or hide places. See [Maps evidence](WYNOS-MAPS-REPORTS-2026-10-14.md).
- **Refund reliability:** request tracking compares the original refund state, preserving later webhook outcomes. A confirmed gateway operation is not reported as failed because local tracking failed. Only a signed, account/PaymentIntent/environment-bound `application_fee.refunded` event reverses a full GP fee; receipt and projection commit atomically. Missing mappings return a retryable response. The fee writer locks the parent order before its payment, matching the legacy refund webhook; a reproduced deadlock is resolved and the PaymentIntent binding is rechecked after waiting. Partial fee returns are retained for review and require a separate dated reconciliation ledger.

New consumer Support and Maps Reports are developer-only in both UI and customer RPCs under [.wyn/company/WORKFLOW.md:33](../../.wyn/company/WORKFLOW.md#staged-rollout-เป็นค่าเริ่มต้นสำหรับฟีเจอร์ใหม่-เพิ่ม-2026-09-06). ### New menu image publication, 2026-10-17

- The Admin uploader accepts JPEG/PNG/WebP up to 8 MiB, reads at most the first 256 KiB for a dimension check before browser decoding, and limits source dimensions to 12,000 per side and 32 megapixels. It redraws a JPEG with longest side 1,600 before uploading. JPEGs whose dimension marker lies beyond the bounded header are rejected. The existing selected image remains intact on failure; a successful upload changes only the draft until the existing reason/version-checked menu save publishes it. Store/item/category/reload/save controls cannot race an upload; cancel stays available. Saving, discarding or reloading resets candidate preview and stale draft guidance.
- The existing Supabase Edge runtime validates the user with Auth and invokes the live `merchant:edit` authorization RPC using the caller JWT and public key. Only the final Storage POST uses the runtime service credential. No privileged key is added to Admin. The private actor-wide budget permits ten attempts per ten minutes across stores. An isolate admits one body/decoder job at a time, streams at most 4 MiB with a bounded read, and reports failures without provider diagnostics. Retries/cancellation can leave an unattached immutable object; recovery never deletes possibly referenced media.
- The normalizer verifies container/MIME/dimensions/animation before full decoding; JPEG/PNG/WebP are the only enabled coders. Input is at most 4 MiB, 2,048 per side and four megapixels. It applies orientation, strips metadata and reencodes WebP with longest side 1,024. Memory/cache/profile/disk and processing bounds are explicit. See [the function's build and runtime evidence](../../supabase/functions/admin-merchant-menu-image/README.md). These limits and local timings do not establish hosted performance acceptance.
- New `food-public/admin-menu/<store>/<uuid>.webp` objects cannot be inserted, overwritten, deleted or renamed by browser roles. Three restrictive Storage policies keep this true even if an older permissive policy exists. A retained menu-row guard blocks changed/new foreign, malformed, missing and unsafe image references, while unchanged legacy references survive. The full real-role fixture passes; removing only the restrictive policies reproduces a forged-image failure. Cross-store final-slot quota races, expiry, revocation, rerun and preserving rollback pass.
- New image validation adds **12 integrated Chromium UI cases** and **five real-browser normalization cases** to the earlier 54 scenarios. Mobile widths 320/390 px fit, cancellation and late responses preserve the draft, failed responses cannot replace an image, and removal sends no object deletion. Browser requests use synthetic HTTP fixtures. Sixteen maintained HTTP-boundary tests execute the actual Edge entrypoint with synthetic fetch responses; the decoder is verified separately with actual WASM and offline Edge workers. This is not authenticated managed-platform acceptance.
- Generated decoder assets are pinned by archive/file integrity and excluded from Git. CI runs `tools/prepare_admin_menu_image_vendor.py` before all Edge checks/tests. A Docker-backed bundle with the configured static WASM/license files is required; a direct full npm package or the API/Dashboard bundle path does not fit the relevant size limit. No build helper deploys or modifies a Supabase project.
