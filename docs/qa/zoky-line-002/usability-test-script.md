## 0. ขอบเขตและข้อจำกัด

- เป้าหมาย: วัดว่าลูกค้าติดที่ใดใน flow "สแกน QR / แอด LINE OA -> สั่งอาหารใน LIFF -> ชำระเงิน" ก่อนแก้ เพื่อใช้ตัดสิน D-3 (LINE Login) และปรับ UX guest
- ผู้เข้าร่วม 3-5 คน เป็น qualitative เท่านั้น **ห้ามอ้างเปอร์เซ็นต์หรือนัยสำคัญทางสถิติจาก n นี้** รายงานเป็น "X จาก N คน" เท่านั้น
- ทดสอบบน **staging + OA ทดสอบ + LIFF ทดสอบ + ร้านและเมนูสังเคราะห์** ห้ามใช้ production DB, บัญชีจริงของผู้เข้าร่วม หรือ production secrets
- ต้องใช้เครื่องจริง iOS/Android + แอป LINE จริง (ZOKY-LINE-001 บันทึกว่ายังไม่เคยทดสอบกับ LINE จริง)
- ยังรอ Founder ตอบ (D-7): ผู้ดำเนินการ, วิธีหาผู้เข้าร่วม, OA ทดสอบ; baseline branch/commit; privacy policy ที่ยังเป็น placeholder -> **ห้ามเริ่มรอบจริงจนกว่าข้อเหล่านี้ชัด**
- สมมติฐานที่ทดสอบ (ยังไม่ยืนยัน): (H1) ผู้ใช้ Google ติดที่ login ใน LINE; (H2) ผู้ใช้ไม่รู้ว่าเลือกเมนูได้ก่อน login; (H3) ตะกร้าหายเมื่อออกไปเบราว์เซอร์ภายนอก; (H4) แอด OA ตรง ๆ ไม่พาถึงร้าน

## 2. Script ผู้ดำเนินการ (ภาษาไทย)

### 2.1 เปิด (3 นาที)
> "วันนี้เรากำลังทดสอบ**ระบบ** ไม่ได้ทดสอบคุณ ไม่มีคำตอบถูกหรือผิด ถ้าติดหรืองงคือข้อมูลที่มีประโยชน์ที่สุดสำหรับเรา ช่วยพูดความคิดออกมาดัง ๆ ขณะใช้งานนะคะ/ครับ ข้อมูลในระบบเป็นข้อมูลสมมติทั้งหมด จะไม่มีการสั่งหรือจ่ายเงินจริง คุณหยุดเมื่อไหร่ก็ได้"

- ขอความยินยอมบันทึก (หน้าจอ/เสียง) แยกข้อ ถ้าไม่ยินยอมให้จดมือเท่านั้น
- ถามพื้นหลังสั้น ๆ: ระบบเครื่อง, เคยสั่งอาหารผ่าน LINE/แอปอื่นไหม, ปกติ login ด้วยอะไร (Google/อีเมล/อื่น ๆ)

### 2.2 กติกาผู้ดำเนินการ
- ไม่ชี้นำ ไม่อธิบายปุ่ม ไม่ใบ้ ยกเว้นผู้ร่วมทดสอบไม่คืบหน้าเกิน **2 นาที** -> ให้ hint ระดับ 1 (ถามกลับ: "ตอนนี้คิดว่าต้องทำอะไรต่อ") แล้วบันทึกว่า "ช่วยระดับ 1"; ยังไม่คืบอีก 1 นาที -> ช่วยตรง ๆ บันทึก "ช่วยระดับ 2" และนับงานนั้นเป็น "ต้องช่วย"
- ห้ามบอกว่า "เลือกเมนูก่อน login ได้" หรือ "กดเปิดในเบราว์เซอร์"
- จับเวลาต่อสถานการณ์ เพดาน 8 นาที/สถานการณ์ เกินให้หยุดและบันทึก "หมดเวลา"
- ถ้าผู้ร่วมทดสอบเจอ error ที่เป็นข้อบกพร่องของ staging (ไม่ใช่ UX) ให้จด และรีเซ็ตสถานการณ์ อย่าให้นับเป็นความผิดผู้ใช้

### 2.3 สถานการณ์ทดสอบ

ลำดับ: A -> B -> C -> D (สลับลำดับ A/B ระหว่างผู้ร่วมทดสอบเพื่อลด order effect) ผู้ร่วมทดสอบที่ไม่ใช่ผู้ใช้เดิมข้าม C

| สถานการณ์ | คำสั่งที่อ่านให้ฟัง | จุดเริ่ม | สถานะสำเร็จ |
|---|---|---|---|
| A: QR ร้าน | "คุณเดินผ่านร้านที่มี QR ให้สแกนเพื่อสั่งอาหาร ลองสั่งข้าวมัน 1 จาน รับที่ร้าน" | สแกน QR ร้านทดสอบ (หรือกดลิงก์ที่แชทให้) | ส่งออเดอร์สำเร็จ |
| B: แอด OA เอง | "เพื่อนบอกให้แอด LINE ของ ZOKY แล้วสั่งอาหาร ลองสั่งข้าวมัน 1 จาน จากร้าน [ชื่อร้านทดสอบ]" | ค้นหา/แอด OA ทดสอบ (ผู้ดำเนินการบอกชื่อ OA เท่านั้น) | ส่งออเดอร์สำเร็จ |
| C: มีบัญชี Google เดิม | "คุณเคยสมัคร ZOKY ด้วย Google (ใช้บัญชีทดสอบที่เตรียมให้) ลองสั่งอีกครั้ง" | เปิด ZOKY จาก LINE | ส่งออเดอร์สำเร็จด้วยบัญชีเดิม (เห็นประวัติสังเคราะห์) |
| D: ชำระเงิน | "ชำระเงินหรือส่งสลิปให้เรียบร้อย" (ใช้ช่องทางทดสอบ) | ต่อจากออเดอร์ที่ส่ง | ชำระ/ส่งสลิปสำเร็จภายในเวลา |

### 2.4 ปิด (5 นาที)
คำถามหลังทำ ถามทีละข้อ ไม่ชี้นำ:
1. ช่วงไหนที่งงที่สุด
2. ขั้นไหนที่อยากเลิกที่สุด เพราะอะไร
3. เมื่อถูกขอ login คิดว่าต้องทำอย่างไร และรู้ไหมว่าของในตะกร้ายังอยู่หรือไม่
4. เคยรู้ไหมว่าเลือกเมนูได้ก่อน login (ถามหลังจบเท่านั้น)
5. เทียบกับแอปสั่งอาหารที่เคยใช้ ง่ายกว่า/ยากกว่าอย่างไร
6. ถ้าต้องสั่งจริง คุณจะสั่งผ่านช่องทางนี้อีกไหม เพราะอะไร

SEQ (Single Ease Question) ถามหลังจบ**แต่ละสถานการณ์**: "โดยรวมงานนี้ง่ายหรือยากแค่ไหน" 1 (ยากมาก) - 5 (ง่ายมาก)

## 3. คำถาม/สิ่งที่ต้องสังเกต (ผู้สังเกตติ๊กระหว่างทำ)

### การเข้าและการเลือกเมนู
- [ ] ผู้ร่วมทดสอบเปิดจาก LIFF ได้เองหรือไม่ / ถูกพาไปหน้าร้านหรือต้องหาร้านเอง (สถานการณ์ B)
- [ ] เข้าใจหรือไม่ว่าต้องแอดเพื่อน / กดข้ามหรือยกเลิก prompt แล้วยังเข้าร้านได้หรือไม่
- [ ] เห็นเมนูและเพิ่มตะกร้าได้โดยไม่ถูกบังคับ login (ก่อน/หลังเพิ่มของ)
- [ ] เลือกตัวเลือก/โน้ต/จำนวนได้เองหรือไม่
- [ ] ข้อความใดที่อ่านแล้วตีความผิด (จดคำพูด)

### ขั้นยืนยันและ login
- [ ] ผู้ร่วมทดสอบคาดหวังอะไรเมื่อกดปุ่มยืนยัน ("เข้าสู่ระบบเพื่อยืนยันคำสั่งซื้อ")
- [ ] เลือกปุ่ม Google หรืออีเมล เป็นอันดับแรก
- [ ] เจอ `disallowed_useragent` / หน้า Google ปฏิเสธหรือไม่ (บันทึกภาพหน้าจอ) และทำอะไรต่อ (ลองซ้ำ, อีเมล, เปิดเบราว์เซอร์, เลิก)
- [ ] ออกจาก LINE ไปเบราว์เซอร์ภายนอกกี่ครั้ง และกลับมาเองได้หรือไม่
- [ ] จำรหัสผ่านอีเมลได้ไหม / มีบัญชีอีเมลหรือไม่ / กดลืมรหัสผ่านหรือไม่
- [ ] หลัง login กลับมาเห็นร้านเดิมและตะกร้าเดิมหรือไม่ (ตะกร้าหาย = ความรุนแรงสูง)
- [ ] กดย้อนกลับจากหน้า login แล้วตะกร้ายังอยู่หรือไม่

### ส่งออเดอร์และชำระเงิน
- [ ] กรอกเบอร์/ที่อยู่ได้เอง ต้องกรอกซ้ำหลัง login หรือไม่
- [ ] เข้าใจขั้นชำระเงิน/ส่งสลิป มีจุดที่ไม่แน่ใจว่าออเดอร์ส่งสำเร็จแล้วหรือไม่
- [ ] เข้าใจไหมว่าจะได้รับแจ้งเตือนอย่างไร (Web Push/LINE)

### สัญญาณอารมณ์/พฤติกรรม
- [ ] ถอนหายใจ, หยุดนาน (>20 วินาที), กดย้อนซ้ำ, ปิดแอป, พูดว่า "ไม่เอาแล้ว/ยุ่งยาก"

| ตะกร้าหายอย่างน้อย 1 คนเมื่อออกไปเบราว์เซอร์ภายนอก | ยืนยัน H3 เป็นกรณีที่เกิดจริง (ไม่ใช่สถิติ) | รวมใน EC-G2 และประกอบการตัดสิน D-3/D-6 |
| ผู้ร่วมทดสอบ >= 2 คน (สถานการณ์ B) ไม่ถึงร้านเอง | สนับสนุน H4 | ข้อ 3 (deep link) / copy ใน OA |
| ผลไม่เข้าเกณฑ์ใดเลย | ยังไม่มีหลักฐานเพียงพอ | ห้ามสรุปว่า "ไม่มีปัญหา"; พิจารณาเพิ่มผู้ร่วมทดสอบหรือปรับ script |

หมายเหตุ: ใช้ n=3-5 ได้เพียงเป็นหลักฐานเชิงคุณภาพ ในรายงานให้เขียน "X จาก N คน" และระบุข้อจำกัดเสมอ ห้ามประมาณอัตราในประชากรจริง

เกณฑ์รอบหลังแก้ (รอบ E): ไม่มีสถานการณ์ที่ผู้ร่วมทดสอบส่วนใหญ่ต้องออกจาก LINE เพื่อสั่งสำเร็จ และ drop-off ที่หน้า login ลดลงเทียบ baseline เป้าตัวเลขกำหนดหลังเห็น baseline (**ไม่ตั้งตัวเลขเดา**) ใช้ script ฉบับนี้ซ้ำโดยไม่เปลี่ยนสถานการณ์เพื่อเทียบได้

## 7. ผลที่ต้องส่ง

1. ตาราง funnel ต่อคน (หัวข้อ 4)
2. อันดับปัญหา (ความถี่ x ความรุนแรง)
3. คลิปสั้น เฉพาะที่ได้รับความยินยอม
4. ค่า SEQ ต่อสถานการณ์ (แสดงรายค่า ไม่ใช้ค่าเฉลี่ยเป็นข้อสรุปเชิงสถิติ)
5. ข้อเสนอสั้น ๆ ต่อ D-3 และ UX ข้อ 1/3
6. ข้อจำกัดของการทดสอบ (n, อุปกรณ์, staging)
- ไม่ใส่ชื่อ/เบอร์/อีเมลจริง; ลบวิดีโอ/เสียงตามกำหนดในใบยินยอม; ห้ามเก็บภาพที่เห็นข้อมูลส่วนตัวหรือ token

## 8. สิ่งที่ยังไม่ได้ตรวจ/ยังเปิดอยู่

- ยังไม่ได้ทดสอบจริงบน LINE/staging; staging ปัจจุบันตรงกับ production หรือไม่ ยังไม่ได้ยืนยัน
- เบอร์โทรถูกบังคับที่ขั้นไหน ยังไม่ได้ไล่อ่านโค้ด (แบบฟอร์มจึงมีช่อง "ต้องกรอกซ้ำหลัง login หรือไม่" ให้สังเกตแทน)
- D-7 (ผู้ดำเนินการ/ผู้ร่วมทดสอบ/OA) และ privacy policy ยังไม่ได้รับคำตอบ
