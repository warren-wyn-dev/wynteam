# Merchant startup visual fixes — 2026-10-29

The owner's iPhone Safari recording showed an initial Thai missing-glyph flash,
an empty store shell, outline icons replaced later by artwork, and menu pictures
arriving after their text. The owner requested these fixes and previously
authorized the scoped Merchant performance release. This patch extends the
released application source `e6621cfbdac11454dbbe314901707b6940afee59`.

## Resulting behavior

- The authenticated wrapper reveals only its own view after critical content or
  an actionable error/empty state has painted, with bounded recovery on timeout.
  A replacement client/account returns to loading immediately; removed-view
  notifications cannot reveal another account's view.
- Public Flutter text layout starts the existing Thai fallback alongside data
  reads. Readiness waits for the bounded font result and a completed frame.
  The system-text-font guard remains intact; no text font is bundled.
- The shared icon atlas starts during critical reads. Pink placeholders retain
  the artwork's size instead of flashing black outline icons.
- Menu images show placeholders in their existing 64-by-64 slots, retain the
  original-image error fallback, and remain lazy. No whole-menu image prefetch.
- Bounded local performance marks describe authenticated startup stages without
  account, store, order or credential data.

## Measurement limits

Healthy synthetic browser observations confirmed Thai fallback preparation in
roughly 542–812 ms and content readiness on engine-reused views in 160–372 ms,
with no font timeout in those healthy samples. These are different measurements:
font time starts at engine preparation; content time starts at each Dart view.
They exclude navigation, authentication and engine download/compilation, so they
are not full-load timings or a universal speedup claim.

The 1,200 ms font bound deliberately permits the business app to recover when a
font resource is unavailable. A timed-out result does not confirm glyph readiness.
Retaining the loading cover until meaningful content avoids the empty-shell
flash; the cover alone does not shorten computation or API work. Physical iPhone
Safari and real-store authenticated API latency still require device validation.
